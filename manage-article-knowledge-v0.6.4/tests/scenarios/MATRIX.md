# 离线端到端场景矩阵

目的：不用大模型、不联网、不碰真实项目，按真实调用顺序把一篇文章从 `writing_request` 跑到
写作门禁（第二阶段延伸到终稿接收和 Faithfulness 导入），断言最终状态。真实测试发现的问题先在这里
加一个能复现的场景，再修。发版前全部场景必须通过，或已登记为预期失败。

## 场景怎么跑

每个场景在临时目录里从零造一个最小项目，按下面的顺序只调用官方入口：

1. `writing_bridge.py prepare`：登记写作任务，生成 `10`
2. 按场景登记证据：`record_claim_reuse.py`（复用），或写入本轮核验证据行（新证据）
3. 写入 `20`：由场景脚本按 PR-2 或 PR-1 模板生成，代替 Agent 的判断内容
4. `run_knowledge_workflow.py`：批次编排、恢复器生成 `30/35`
5. `issue_writing_ready.py`：写作门禁

断言只看最终状态（`writing_gate_status`、`writing_ready.json` 是否存在且绑定当前 `30` 哈希，
或预期的阻塞原因），以及少量结构结论（`35` 映射的 Claim 集合、`30` 按大纲逐节列出）。不断言中间
文件的逐字内容，避免文案调整导致场景大面积失败。

## 维度

| 维度 | 取值 |
|---|---|
| 任务模式 | new_article / outline_refresh / knowledge_reuse_rewrite |
| 证据来源 | 本轮核验通过 / 全部复用 Formal Claim / 混合 |
| 大纲格式 | 逐行列表 / 已登记的一行旧大纲（仅既有任务）/ 新建时一行大纲（应被拒） |
| 记录协议 | PR-2（新任务）/ PR-1（旧任务，有独立 `15`） |

全组合有 36 种，其中很多不会真实出现（例如重写模式锁定原大纲，新建任务不会是 PR-1）。下表只保留
真实会走到的组合和已发生过的问题。

## 不在范围内

- 测试包装器、沙箱权限等运行环境问题（如 SK-V063-072）：属于环境，不放进场景矩阵。
- 真实 P-005 数据：只作为可选测试，快照放在仓库外（例如 `D:\mak-fixtures\`），不存在时自动跳过；
  客户资料不进 git。

## 规则

- 场景失败时不改 `scripts/`，标为 `expectedFailure` 并在本表“状态”中登记原因；修复另行进行，
  修好后去掉 `expectedFailure`，场景成为永久回归。
- 每个场景几秒内跑完；全部场景一条命令运行：
  `python -X utf8 -m unittest discover -s tests/scenarios`（在Skill根目录运行；场景较慢，不随`discover -s tests`运行）
