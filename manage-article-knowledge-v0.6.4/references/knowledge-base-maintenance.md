# 知识库维护入口与清单

## 目的

本入口用于整理已经建立的 v0.6 项目，不替代写作、终稿接收、Faithfulness 导入、月度审核或交接流程。它把可确定的结构修复自动落盘，把需要证据或人工决定的事项集中记录，避免问题散落在对话中。

## 变更控制与运行时反馈旁路

Skill本体（`SKILL.md`）、references、scripts、agents配置和changelog是受保护的通用资产。运行任何客户项目时，默认只允许修改该项目自己的Obsidian文件、机器数据和项目运行记录；不得因为项目中发现格式差异、规则遗漏或测试失败就自动修改Skill。测试、演示、模板和规则验证必须在临时项目目录进行，禁止向真实客户项目写入测试Claim、RES、GAP、CUS、ANM、SKFB、处置或手工审核JSON。

用户纠正、重复绕路、规则冲突、模板不可用、校验漏报或自动流程错误显示为通用问题时，Codex应主动在项目SKFB记录候选；用户明确说“记录到Skill反馈台账”“登记SKFB”或同义要求时，也必须登记，不要求用户填写ID、类型、状态或复现字段。Codex先查重，同一根因复用原SKFB并追加复现，再记录人话说明、影响、项目入口、候选修复和是否需要升级。只有维护负责人或用户明确同意“修改Skill/更新v0.6规则”后，才可以改Skill及其更新记录，并完成Skill自测和受影响项目回归。没有明确同意时只做项目级修复或提出建议，不回写Skill。

**运行时反馈旁路规则：**发现Skill本体、交接规则、脚本或模板疑似缺陷时，当前任务不得为了“修Skill”而暂停，也不得把SKFB登记当作任务终点。先在项目Skill反馈台账查重并记录复现、影响、当前临时处置和候选修复；记录动作是旁路审计，不改变文章任务的当前状态、阻塞节点或合同生命周期。记录完成后必须立即回到原步骤继续执行，在不修改通用Skill本体的前提下完成当前任务；只有合同规定的`needs_human`/`handoff_error`、真实工具或权限失败、客户事实冲突或缺少不可替代材料，才允许暂停并向人工说明。后续是否修改Skill属于独立的维护工作，须另行获得明确授权，不得在客户任务运行中顺手改动。

## 两个可直接使用的指令

需要整理或修复既有项目时，直接使用下面的口令。首次整理：

> 整理并维护这个知识库：先检查 Skill 版本、维护设置和项目结构，再读取现有知识库维护清单；先按当前 Skill 统一整理能够确定的固定模板字段/小节、稳定入口与导航、台账主表/详情配对、占位内容和覆盖视图，保留真实内容，不自动删除兼容历史页；然后逐项按当前 Skill 规则和当前项目事实重新核验。能根据现有文件、索引和固定合同确定的直接修复；旧事项若因明确的 Skill 规则更新已不再构成问题，保留历史记录，写明规则变更依据和本次验证结果后关闭，不要继续列为开放错误，也不要为迎合旧规则改写项目；不能确定的不要猜，继续保留开放并更新还缺什么、下一步和最近检查；新问题使用新的 KMR 编号登记。最后更新清单、覆盖视图、运行记录和审核摘要，并汇总已自动修复、因规则更新关闭、待补证据、待人工决定和仍存在的错误。

人工补充后继续：

> 根据知识库维护清单和我刚补充的判断/证据，继续整理这个知识库：先按当前 Skill 统一检查并修复能够唯一判断的固定模板、入口、导航、台账配对、占位内容和覆盖视图，再逐项重新核验所有开放事项；能关闭的关闭，能修复的修复；旧事项若因明确的 Skill 规则更新已不再构成问题，保留历史记录，写明规则变更依据和本次验证结果后关闭，不要为旧规则修改项目；仍不能确定的保留开放并说明下一步；最后更新清单、覆盖视图、运行记录和审核摘要。

两句可以合并为一次请求；任何阶段都不得删除历史记录或把未知事项直接标记为已解决。每次运行都先读取现有维护清单并按当前Skill规则逐项复核，不得只发现新问题而遗留已经失效的旧问题。重复运行必须维护同一张连续清单：复用同一根因的KMR，更新状态、处理、缺项、责任人、关闭依据和最近检查；只有新根因才分配新编号。人工补充判断或证据后，只有明确可执行的事项才能回写、关闭并重建覆盖视图。维护入口不重算历史Faithfulness，不改变历史文章版本、旧GAP或历史报告。

## 固定落盘位置与最小模板

项目目录固定建立：

`05_数据与审核/30_异常与待决定/90_知识库维护/01_知识库维护清单.md`

```markdown
# 知识库维护清单

- 项目ID：
- 最近检查：
- 当前Skill版本/指纹：
- 最近一次维护运行：

| 维护事项ID | 问题 | 涉及文件 | 类型 | 当前状态 | Skill已做处理 | 还缺什么 | 下一步责任人 | 关闭条件 | 最近检查 |
|---|---|---|---|---|---|---|---|---|---|
| KMR-001 |  |  | 自动修复/待补证据/待人工决定 | 待处理 |  |  |  |  |  |
```

状态只能使用：`待处理`、`已自动修复`、`等待补证据`、`等待人工决定`、`已关闭`。维护事项 ID 是项目内单层流水号，不是 GAP、CUS、ANM 或 SKFB 编号。

### 旧事项因规则更新而不再适用

当前Skill明确改变了判断规则后，旧KMR可能不再构成错误。此时不得修改项目去迎合旧规则，也不得删除该KMR。只有同时满足以下条件时才能确定性关闭：当前安装Skill或其更新记录明确说明原条件已被取消、改为正常状态或改成兼容提醒；按当前规则重新校验后该事项不再产生当前错误；没有另一个仍有效的事实、证据、身份或结构问题被同一旧描述遮住。关闭时把状态改为`已关闭`，在“Skill已做处理”写明“规则更新后不再适用”、对应变更ID或规则位置和本次验证结果；“还缺什么”写`无`，并更新最近检查。它只从开放事项和“仍存在的错误”中移除，原问题、涉及文件和历史处理记录继续保留，不得继续计入开放事项。

仅仅因为某次校验没有输出（一次未报错）、文件暂时未被扫描、版本号变化或代码已经修改，不能自动关闭。若当前规则是否真的取消旧要求仍不明确，继续保持开放并转为`等待人工决定`；若规则虽然变化但项目仍违反当前规则，则按当前问题更新原KMR或在根因不同的情况下新建KMR。

## 自动与人工边界

项目维护采用“启动检查 + 接触时微调 + 维护/月度/交接前结构整理”的轻量策略。启动时读取版本入口中的“项目维护设置”；Skill变化只同步指纹、版本入口和SKFB检测摘要，不批量重写项目。普通文章、终稿和Faithfulness动作只对当前实际触及的文件做确定性结构微调；知识库维护、月度审核和交接审核在正式工作前各执行一次项目级确定性结构整理，统一核对当前模板固定字段/小节、稳定入口与导航、台账主表/详情配对、占位内容、覆盖视图和维护设置。维护设置缺失的旧项目按兼容规则运行，并在首次触及或维护/月度/交接审核时补齐。

可自动处理：固定字段、目录和表格结构、稳定入口与导航、主表/详情配对、占位清理、唯一来源引用、已有严格翻译的 30/35 复制、覆盖视图和运行记录。该整理只修复有固定规则可唯一判断的结构，不新增迁移台账或迁移编号。不能确定的 Claim 语义、适用范围、原文证据、多个来源候选、英文严格翻译、客户事实、事实映射、路径归属和业务决定必须进入维护清单或审核结论，不得猜测。事实、证据、Claim语义、历史Faithfulness判断、旧GAP键和历史报告只报告，不自动迁移、重命名、合并或重算。兼容历史页不因新规则自动删除。

当前规则不再生成三个旧式目录页：`03_正式知识/00_正式知识目录.md`、`03_正式知识/10_客户知识/00_客户知识目录.md`和`03_正式知识/20_外部公共知识/00_外部公共知识目录.md`。既有项目中这些文件属于兼容历史入口，不要求继续维护，也不因存在而报错；维护运行不得自动删除它们或为了新规则改写项目。只有用户明确授权迁移具体项目时，才可先检查反向链接并移除旧页。正式知识的唯一人工入口改为`01_工作台/10_项目基础信息.md#七个业务模块入口`，动态状态只读取覆盖视图。

## 审核与交接

月度审核和交接审核必须读取清单。正式生成月报前，以及交接交付前、接收后，先执行一次当前Skill下的确定性结构整理，再按整理后的结果汇总；整理只处理固定模板、稳定入口、导航、台账配对、占位内容和覆盖视图，并把自动修复与仍待人工判断的内容写入对应审核。存在清单时按状态汇总；没有清单但校验发现问题时，报告仍须直接列出问题并注明“项目尚未建立维护清单”，不能写成无问题。交接包包含清单原文件和开放事项摘要；接收方先确认责任人、证据入口和关闭条件，再运行第二阶段指令。月度/交接不会重算历史 Faithfulness、改写历史文章、重命名旧 GAP、删除兼容历史页或凭空补证据。

## 版本门禁

所有会读取或写入已接入项目的动作都必须先做版本门禁，包括新增文章、两种重写、终稿接收、Faithfulness导入、知识库维护、月度审核和项目交接；版本检查必须早于读取任务、旧文章、旧大纲、知识附件或其他业务文件。纯只读咨询不触发。写作流程必须先经过`writing_bridge.py prepare/finalize`，不得由写作Skill直接读取项目文件绕过门禁；`prepare`和`finalize`会先执行该检测，同样是硬门禁。

每次开始运行既有v0.6项目时，第一项后台动作必须运行`scripts/check_skill_update.py --project <Obsidian项目路径>`。脚本比较项目版本入口记录的Skill SHA-256与当前Skill；发现变化时，原子更新版本入口并在Skill反馈台账写入最近版本检测和开放反馈审计摘要；没有变化时不改写项目文件。发现变化并同步后继续当前任务。项目没有版本入口时报告缺失，按报错用`initialize_project.py`补齐缺失文件（只新建、不覆盖）后重跑并继续当前任务，不得跳过或伪造同步。该动作不自动关闭SKFB，不替代Skill专项自测、项目验证或维护负责人决定。版本入口只在Skill版本/指纹变化时更新，不因每篇文章成功而重复追加版本变更行；文章运行成功、失败和终稿接收仍记录在运行记录与接入配置状态中。

## 校验兼容

项目门禁与专用运行账本校验使用同一验证器：schema 1 历史 `partial_success` 只读兼容为 `partial`，新记录仍只写当前合法枚举，不重写历史JSONL。控制/机器历史快照中的管理说明不作为当前事实来源引用重验，归档完整性仍校验；真实正式知识及当前文章的来源引用继续核对，来源通配说明不得截断为不存在的来源ID。

v0.6完整继承v0.5，并继续保留v0.4稳定性审计确定的证据追溯、状态一致性、事务可恢复、环境边界和运行审计约束（这些约束已写入各现行参考；审计原文归档在仓库`changelog/v0.4兼容审计归档/`）；不恢复v0.4已废弃的全量清理、固定范围确认、固定资料会议或固定人工关口。

## SKFB台账维护

Skill反馈台账的主表行与人话详情是一个控制事务；新增、合并或关闭反馈时必须成对更新，主表ID和详情标题不一致或缺失时不得通过项目校验。每条SKFB详情必须写明关闭条件、重开条件和当前关联对象入口；标为`已关闭`时还必须写关闭依据、Skill专项自测和受影响项目验证，且不得残留“未运行/待验证/失败”等相互矛盾的验证记录。文章或控制文件迁移后，SKFB中的关联Wikilink必须同步到当前路径；过期或不存在的文件型入口视为校验错误。

每次获授权修改Skill后，使用`scripts/manage_skill_feedback.py --audit`检查受影响项目的开放SKFB；Skill专项自测通过后推进到`已修复，待项目验证`，原复现项目按关闭条件通过后再推进到`已关闭`。状态工具必须在同一事务同步主表、详情、验证依据和最近更新；没有项目验证证据不得自动关闭。

### 历史程序类ANM的规则复核

维护时立即复核仅因旧分类规则、导入结构或审核记录限制而建立的ANM，无须等待文章重写。按当前语义问题与真实来源重新核对逐条claim关联；知识域数量本身不能否定公共缺口，集合值主张不得为了导入临时重拆。固定复核字段：`原依据`、`当前规则`、`文章/版本/claim_id`、`实际来源与边界`、`程序原因是否失效`、`真实知识事项是否仍待处理`、`后续入口`、`关闭/重开条件`。只关闭已失效的程序依据，不把旧黄色改绿、不改历史分数/50/哈希，也不把未完成的GAP/CUS事项随ANM一起关闭。复核说明更新既有同ID详情及主表，不新增任意说明文件。找不到文章归档去向是独立维护事项，不能作为保留失效ANM分类的理由。
