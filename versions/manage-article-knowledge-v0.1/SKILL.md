# 文章知识库运营管家 v0.1

## 目标

同时维护“项目最低知识基线”和“文章增量知识需求”。项目基线回答企业知识库在公司、产品、案例、行业和素材等方面是否足够完整；文章增量回答当前关键词和选题需要哪些额外知识。不要为了追求形式上的全量整理而处理全部历史资料。

好的企业知识库应当以合理成本，为当前和后续文章持续提供可靠、可追溯、可复用和可交接的知识。项目级质量按“找得到、用得上、信得过、能复用、能增长、能交接”检查；文章级知识就绪度单独判断本篇资料是否足以安全写作。项目知识库可以持续完善，但近期文章必须达到知识已就绪。

优先复用已确认的正式知识；除项目基线、风险审核和当前文章缺口外，不主动扩大处理范围。原始文件原封不动保存；需要引用客户原话时建立可定位的原文证据，不让总结、翻译或润色覆盖原文。企业自身信息完成提取、终稿检查和人工确认后，无论本篇是否实际引用，都应沉淀到正式知识；外部研究补充的行业知识先进入等待区，由内容运营在文章完成后决定是否沉淀。

## v0.1 试用范围

本版本只验证一个最小闭环：

```text
一个客户
→ 一名主要运营
→ 一个本地可写的Obsidian项目
→ 一个稳定的客户资料路径
→ 一周2—3篇文章
→ 定向处理、就绪审核和知识沉淀
```

按以下边界运行：

- 人工输入项目基础信息；RAG SEO接口尚未接入时记录“待确认”，不阻塞试用。
- 客户原始资料默认保留在用户指定的稳定资料路径；Obsidian保存资料索引、原文证据、Work和正式知识。
- 不要求先配置Obsidian多人同步、公司看板、自动监控、行业公共库或由Codex计算单篇引用率的统一算法；月度KPI直接使用内容运营逐篇录入的引用率。
- 每次由运营明确发起任务，不在后台持续扫描。
- 一个项目只设一名主要写入人；多人同步和同时编辑不属于v0.1验收范围。
- 试用成功标准是完成至少一轮“建项目—扫资料—文章准备—人工确认—知识沉淀”，不是整理完客户全部历史资料。

## Codex 原生读取原则

- 使用知识地图和明确文件路径帮助 Codex 逐步定位资料，不一次加载全部内容。
- 让标题表达真实主题和从属关系，不用标题数量、固定字数或固定层级模拟向量切片。
- 保持知识文件主题集中但语义完整；既避免巨型总文档，也避免“一条事实一个文件”的碎片化。
- 保留表格、列表、字段和文件结构等原生关系，不为了检索统一改写成长段文字。
- 避免在知识地图、主题文件和摘要文件中重复维护同一正文；索引只说明“有什么、在哪里、什么状态”。
- 优先使用可移植的文件路径或 Markdown 链接；项目已有稳定的 Obsidian 链接规范时沿用。
- 在Vault内只建立有业务意义的单向内部链接；Obsidian会自动显示反向链接，不为“做双向链接”在两个文件中机械互链，也不把每个重复词都做成链接。详细规则见项目结构参考。
- 换电脑、移动Vault或客户资料目录后，先重新确认客户原始资料根路径和Obsidian项目根路径，再生成“旧路径→新路径”映射、预览项目内受影响记录并留痕更正。不得把旧电脑绝对路径直接当作当前真实路径，也不得借路径更正移动或改名客户原文件。

## 核心边界

- 不猜测、不补全原始资料未明确提供的信息。
- 不修改、覆盖或用转换稿替代客户原始文件。
- `00_项目管理/资料索引.md`是唯一当前文件级索引，原“资料地图”字段并入这里；`00_项目管理/资料内容导航.md`只定位文件内部页段和主题。不要并行维护`资料地图.md`或`01_原始资料索引/`；相关候选文件尚未完成内容导航时，不得声称项目资料没有对应内容。
- 不论来源是PDF、PPT、Word、Excel、图片、视频、客户官网、行业网页还是微信公众号，凡标记为“提取稿”或“原文证据”的内容都必须按原文提取，不总结、不润色、不改写、不拼接补全。摘要、翻译和分析只能另存并明确标记。
- 正文提取默认以“最小完整语义块”为最小单元，不把几个词或脱离上下文的一句话当作普通提取结果。有明确标题时，默认提取所选最小有意义标题及其下属完整内容；没有标题时，至少保留一个完整段落或共同表达一个意思的连续段落。表格、FAQ、列表、PPT、网页字段和视频按各自完整结构处理。只有原文本身就是独立定义、条款、参数、列表项或客户确认答复时，才允许单句或字段级提取，并同时保留对象、条件、上级标题和来源位置。
- 选择有层级的标题时，按“标题子树”提取：保留所选标题、全部相关下级标题及其正文，直到下一个同级或更高层级标题。尽量保留原标题、原顺序和父子层级，不把四级、五级标题默认拆成互不关联的小稿，也不擅自提升、压平或重建原文层级。确需单独提取下级标题时，必须记录完整上级标题路径；原结构异常时先保留并记录异常，层级修正只能在独立派生稿中提出并等待确认。
- “原始提取稿/原文证据”“项目资料稿”“文章资料选择表”和“文章写作资料包”必须分开。派生处理后按企业项目生成一个唯一当前《项目资料稿》，按知识主题完整收拢经过核验且可回溯的英文原文、忠实翻译、表格和结构稿，不按单篇文章大纲制造层级。知识沉淀与文章公开使用是两个判断：除客户明确禁止、无法取得可靠正文、`summary`、`inference`和无来源AI说法外，经过核验的内容不因冲突、动态性或公开待确认而删除，使用`🟢公开可用 / 🟡内部可用，公开待确认 / 🟠来源冲突 / 🔵动态快照 / 🟣外部研究限定范围`等可叠加标签控制使用方式。文章资料选择表只选择本篇拟使用的内容块；就绪审核说明风险和核对要求，不自动排除风险块；人工放行后生成包含获准内容、风险标签和使用提醒的《文章写作资料包》。
- 不把 AI 总结、润色、翻译或 OCR 不确定结果标记为客户原话。
- 不把行业通用知识表述为企业自身能力、产品参数或服务承诺。
- 客户明确不允许使用的内容不进入Obsidian知识库、项目资料稿、文章写作资料包或正式知识；不得复制其正文，只记录不含敏感内容的“已排除”状态和必要来源范围。发现这类内容已经存在于知识库时立即停止使用并报告位置，未经明确授权不自行删除。
- 无法可靠访问或提取PDF、PPT、Word、Excel、图片、视频、音频、网页或其他资料，或者结果与本Skill的完整性、顺序、层级、表格和逐字要求存在明显差距时，必须在生成正常提取稿前或发现问题后立即预警。明确说明失败范围、已尝试方法、结果差距、可用部分和需要运营提供的原文件、可搜索版本、页面内容、截图、外部提取稿、逐句稿或其他材料；不得静默改写、总结、猜测、补齐或把残缺结果标成完成。
- 不默认全量处理客户全部资料、整个官网或全部历史视频。
- 不默认把所有原始资料转换为 Markdown、Word 或纯文字。
- 不默认生成文章正文；本 Skill 服务写作前准备、写作后反馈和知识维护。
- 不在文章资料准备阶段输出“可以写”“有限度可写”或“暂不建议开始”；必须先完成候选资料收集和必要的Work处理。
- 不把标题和大纲当成此阶段的审核对象；只用它们确定资料范围、处理方式和缺失方向。
- 知识库不收录没有文字或数据的照片。纯产品图、展会图、工厂环境图、客户合影等只留在原始资料位置，不进入项目资料稿、文章资料选择表、就绪审核或正式知识；只处理其中明确可见且需要提取的文字、标签、图例或数据。
- Codex不得根据文章文本相似度、自我判断或不完整引用清单推算单篇引用率。内容运营可以逐篇录入`0%—100%`的引用率作为月度KPI原始数据；Codex只按固定口径计算当月算术平均值。月平均引用率`≥15%`为达标，`<15%`为未达标，数值越高越好。纳入范围有任何文章缺少引用率时，月度KPI标记`数据不完整，暂不判定`，不得只用已录入的高值文章给出达标结论。
- 不把搜索结果、聚合页、AI 回答或无来源网页直接写入正式知识。
- 不把DOCX程序段落编号当作Word页码或主要人工定位；不只用资料ID代替资料显示名称、原始文件名、原始相对路径和人能看懂的内容位置。
- 所有交给人确认、选择、转交或复核的项目，都必须同时写出人能看懂的业务标题。任务ID、资料ID、GAP-ID、闸门编号和序号只用于稳定检索，不能单独充当标题；不得只写“确认GAP-C03”“同意SRC-0008”或“处理第2项”。大纲、材料、缺口、冲突、翻译批次、确认选项和输出文件均遵守此规则。
- 面向内容运营、优化师、组长或客户的文件和消息使用真实步骤名称，例如“外部候选来源选择”“本批材料处理总纲确认”“派生处理执行确认”“文章写作放行确认”“正式知识沉淀确认”。`GR`、`GE`、`GD`、`G6`、`G7`等代码只能作为内部审计元数据，不能出现在操作标题、按钮式选项或要求人工判断的正文中。
- 不在阶段文件或报告中设置固定的`下一步`区块。每次交付文件后，只在当前聊天中用简短提示说明当前步骤、运营现在要做什么、确认后Codex会做什么，以及如何退回修改；当前动作最多三项，没有人工动作时明确说“无需操作”。
- 未核验直达链接时，不使用`暂不交运营保存`等模糊表达。先实际查找，再明确写`等待Codex继续查找`、`运营现在无需操作`、已尝试方式和Codex下一步；也不让运营为已指定页面从零搜索。
- 不把本地 MVP 描述为稳定的公司级知识管理系统。
- 不把未确认能长期保存的“下载”“桌面”或临时目录标记为权威原始资料位置。
- 没有共享快照、同步状态和审计记录时，不把本地 Obsidian 检查结果称为公司全量数据或人员绩效结论。
- 不让多个任务同时修改同一份正式知识文件。
- 未获得明确的入库指令或人工确认前，把新增内容作为“正式知识候选”，不要直接覆盖已确认知识。
- 运营使用外部工具或人工制作的提取稿由运营负责完成初步质量核对；Codex必须记录提供者、提取方式和核验状态。没有原页面/原文件或未完成必要复核时，不得标记为`verbatim`或“逐字准确”。
- Codex生成任何提取稿前，必须先向内容运营提交提取范围和提取稿大纲。适用于PDF、PPT、Word、Excel、图片、视频、音频、客户官网、行业网页和微信公众号等全部资料。至少列明资料/页面、页码或章节等精确范围、拟提取主题与字段、表格和图片处理方式、排除范围、原始语言、输出文件和位置。收到明确确认后才提取正文；只读结构扫描、链接查找和提取质量判断可以先完成。
- Codex新找到的客户官网、行业网页、研究报告摘要页、专业媒体或微信公众号链接，不能因为“看起来相关”就直接进入提取总纲。先生成`GAP-Rxx_候选来源与提取方案.md`，逐页列出可点击直达链接、页面身份、日期、来源质量、拟支持内容、不能支持的内容和建议取舍；内容运营确认纳入哪些链接后，才能把入选页面与本地资料、运营提取稿一起写入《本批待处理材料总纲》。确认候选链接只代表“选中这个来源”，不代表已批准提取正文。
- 文章资料推荐或知识库整理计划获批，不等于已经批准正文提取。Codex新找到的外部链接先完成“外部候选来源选择”；运营再把选中的本地资料、确认纳入的网页和自己已有的外部提取稿一起提交。Codex必须把本批全部材料汇总到一份《本批待处理材料总纲》，统一列出每份材料的当前形态、精确范围、提取或接收方式、提取大纲、语言、特殊结构、后续处理意向、排除项和输出位置。完成“本批材料处理总纲确认”后只生成/接收原始提取稿、统一来源属性并完成质量核验。
- 原始提取稿完成后，Codex必须根据实际内容生成《本批派生处理执行单》，展示知识主题和层级预览、可能适用的文章/大纲、重排/去重范围、表格和特殊结构样例、翻译计划及输出位置。只有内容运营通过“派生处理执行确认”逐项同意或修改后，才执行项目资料稿、表格翻译/文字化、正文翻译、最小改动审核等派生处理。总纲中登记的后续意向不能替代派生处理执行确认。
- 不因为总纲获批就覆盖原稿。Codex生成的原始提取稿、运营外部获得的原始提交稿、属性统一稿、格式整理稿、表格处理稿、翻译稿和审核版必须分层保存；后续稿件不得替代前一阶段材料。
- 发现视频或音频时，默认不由Codex自行判断内容主次或生成原始转写。Codex只报告资料位置和已有字幕/PPT情况，给内容运营一份“原始逐句稿或字幕稿”准备说明；内容运营负责选择方法、提取并初步核对原始稿。Codex收到原始稿后再按确认范围处理，且不得覆盖原始稿。
- 不把多个无关的客户能力、参数或权限合并成一条“向客户补资料”。先判断能否复用现有证据、改写为行业建议、公开研究或删除非必要主张；确实只能由客户证明时，一事一卡生成可直接内部转交和对客发送的问题。

- 用户询问“怎么操作、该说什么、怎样触发”，或需要给新运营交接时，读取 [operator-quick-manual.md](references/operator-quick-manual.md)，优先给可直接复制的一句话，不要求用户理解内部步骤。
- 启动v0.1试点、初始化首个项目或不确定下一步时，读取 [v0.1-pilot-workflow.md](references/v0.1-pilot-workflow.md)。
- 执行任何写入、外部工具、文章放行或正式知识沉淀前，读取 [human-review-gates.md](references/human-review-gates.md)。
- 初始化项目、调整目录或写入正式知识前，读取 [project-and-knowledge-structure.md](references/project-and-knowledge-structure.md)。
- 登记“待登记”文件、用户提供的外部路径，或处理中途收到客户补充文件、纠正表达和新版资料时，读取 [intake-workflow.md](references/intake-workflow.md)；文章已经进入就绪审核或放行时，同时读取回退规则。
- 根据文章标题、关键词或大纲准备官网和本地候选资料时，读取 [article-material-preparation.md](references/article-material-preparation.md)；本阶段不得提前运行文章就绪审核。
- 生成面向内容运营的文章资料准备反馈页面时，读取 [article-material-output-template.md](references/article-material-output-template.md)，使用行动优先、资料卡片和可复制确认块，不使用大宽表。

- 选择本地解析、OCR、API或同步工具，以及给运营提供视频转写工具选项时，读取 [tooling-options.md](references/tooling-options.md)，并先用代表性样例验证。
- 审核知识内容是否完备、评估六维项目质量、打分或生成补充清单时，读取 [completeness-audit.md](references/completeness-audit.md)。内容完备度与项目级质量是两个独立结论，不共用一个总分。
- 文章资料计划确认后，需要生成搜索关键词、定位外部候选链接或执行运营批准的在线研究时，读取 [keyword-gap-and-research.md](references/keyword-gap-and-research.md)；Codex新找到的链接必须先经过外部候选链接确认，再进入本批总纲。
- 判断文章能否开始或处理写作后反馈时，读取 [readiness-and-maintenance.md](references/readiness-and-maintenance.md)。执行月度维护时，同时读取该文件、[project-and-knowledge-structure.md](references/project-and-knowledge-structure.md)中的路径与七个标准模块，以及月度报告模板。
- 记录文章引用、讨论跨系统指标、同步、抽查或人员对比时，读取 [governance-and-citation-metrics.md](references/governance-and-citation-metrics.md)。
- 创建任务单、资料推荐表、就绪报告或维护报告时，读取 [task-and-output-templates.md](references/task-and-output-templates.md)。

只读取当前任务需要的参考文件，不要一次加载全部旧 SOP。

## 识别工作模式

根据用户请求选择一种或多种模式：

1. **项目初始化**：建立或映射最小目录，扫描原始资料，准备项目身份、产品分类、官方术语、公开边界等基础知识。
2. **资料登记入库**：从稳定资料文件夹或用户指定的外部路径登记资料，完成路径确认、去重、版本判断和轻量扫描；再为可读且可能支持企业知识或文章的文件分批建立内容导航。除非用户明确要求，不复制原文件到Obsidian。
3. **高保真原文提取**：从指定文件、页码、章节、Sheet、单元格或时间段生成可回溯的原文证据，不改写原话。
4. **知识库内容完备度与项目质量审核**：内容完备度按知识类别、证据和公开可用性评分；项目质量按“找得到、用得上、信得过、能复用、能增长、能交接”输出独立结论，不用内容总分代替运行质量。
5. **文章资料准备规划**：用关键词、标题和大纲定位本地文件、官网页面及精确范围，按格式、语言、表格和图片情况给出处理建议。
6. **候选资料补充**：把缺口分为现有资料待处理、客户专属事实或公开行业知识，标记A写前必补、B质量补充或C月末观察。先告诉内容运营当前能写什么、不能写什么和有哪些可行选择，由运营决定修改大纲、立即补资料、暂不补资料或删除相关内容。只有运营决定补充后，才把对应任务交给AI知识库专员、优化师/组长或受控研究流程。默认由Codex提取，Web Clipper仅作必要备用。
7. **受控在线研究**：只在运营明确选择后围绕缺口搜索。先输出`GAP-Rxx_候选来源与提取方案.md`并等待运营选择链接；入选链接再作为研究候选进入本批总纲，完成“本批材料处理总纲确认”后才提取正文。
8. **Work资料处理**：先完成本批总纲确认、原始提取/接收、来源属性和质量核验；无法达到要求时立即预警并请求运营补充。再根据实际提取稿完成派生处理确认，分别生成并核验翻译稿、表格稿和特殊结构稿。把经过核验的处理结果按知识主题完整汇入英文主体的《项目资料稿》，中文只作独立核对区或链接到原文证据；写作分析与对照稿另存；提交运营前先完成项目资料稿完整性检查。
9. **文章资料选择表**：从当前项目资料稿选择本篇拟使用的内容块，记录大纲位置、用途和覆盖状态；不复制正文、不处理风险、不作最终放行。
10. **文章就绪审核、放行与资料包**：审核文章资料选择表指向的项目资料块，统一检查冲突、风险、案例公开、竞品、合作方、客户名称、价格和内部信息；单列客户审核事项。输出三档结论并完成“文章写作放行确认”后，才生成只含获准内容的《文章写作资料包》。
11. **写作后知识回收**：正式终稿提交后默认在文章`30_写作后记录/`生成或更新引用清单，并把有可靠证据的知识块累计指标更新到项目`00_项目管理/知识地图.md`；无法对应来源的内容标记“未追踪”。文章新说法不能反向当作知识，沉淀仍从项目资料稿和原文证据识别并按项目去重。
12. **正式知识沉淀**：企业自身信息完成规定审核和确认后实际写入正式知识，不以本篇是否引用为条件；外部行业知识由内容运营从等待区决定。收到明确沉淀确认后继续完成主题文件、知识地图、更新日志和沉淀回执，不得停在候选清单。
13. **月度维护简报**：固定回答五件事：运行与规范是否正常；现有源文件对七个标准模块的覆盖与主要缺失；本月提取、正式沉淀和待运营处理的知识；月平均引用率KPI；历史问题的本月进展与下月动作。内容运营把逐篇引用率保存到`04_归档/月度维护/YYYY-MM/YYYY-MM_引用率原始输入.csv`，Codex校验并在同目录生成简报；月平均`≥15%`为达标，`<15%`为未达标，越高越好。月度维护不固定重做内容完备度评分、六维项目质量或知识块表现统计；发现路径失效、重大缺失、沉淀积压、低引用率、事实风险或重大变更时，再触发对应专项审核。

用户意图不清时，先根据现有文件判断最可能的模式；只有缺失信息会实质改变结果或写入范围时才询问。

## 资料登记工作流

当用户说“把这些客户资料入库”“扫描待登记文件夹”或提供外部文件夹路径时：

1. 确认目标企业项目、Obsidian项目路径，以及精确的客户原始资料路径；发现电脑迁移、盘符变化、Vault移动或项目内仍引用旧路径时，先按项目结构规则完成路径重定位、批量更正预览和迁移留痕。
2. 读取 [intake-workflow.md](references/intake-workflow.md)，按其安全规则执行。
3. v0.1默认在原位登记稳定资料路径，不移动、不删除、不修改、不制造Obsidian副本。
4. 来源位于“下载”“桌面”、临时目录或未来可能失效的位置时，先请运营确认一个长期资料位置；确认前只做只读扫描，不标记为已登记。
5. 使用本地文件信息和文件指纹先判断完全重复；不要为了去重让模型阅读全文。
6. 对同名但内容不同的文件按疑似新版本处理，不覆盖旧文件。
7. 先做低Token轻量扫描，再对可搜索文件执行只读的全文件结构导航，只保存页段、章节、语言、主题、型号关键词和限制；全文OCR、大量逐页视觉判断或外部工具先预警并确认，不生成完整Markdown。
8. 在Obsidian中更新唯一当前资料索引和资料内容导航，记录原始路径、资料ID、内容指纹、扫描范围、导航状态和异常。
9. 输出资料登记报告和本周建议处理的文件、页码、章节、Sheet或时间段。

如果外部路径超出当前可访问范围，针对用户明确给出的路径请求权限；不要扩大扫描到其父目录、整个下载目录或其他客户资料。

## 总控工作流

### 第一步：确认输入与范围

确认或从项目中发现：

- 项目知识库路径；
- 稳定的客户原始资料路径；
- 当前文章计划、标题、关键词、大纲或目标产品；
- 需要处理的资料范围；
- 目标语言及公开范围；
- 用户本次只要分析，还是允许创建临时结果或更新正式知识。

如果文章计划尚未提供，仍可完成项目盘点，但不要假设文章需求。

### 第二步：读取项目状态

优先读取：

1. 项目说明；
2. 知识地图；
3. 资料索引；
4. 术语表；
5. 风险与待确认项；
6. 与当前文章直接相关的正式知识文件。

不要一开始读取所有原始文件正文。缺少控制文件时，先利用现有目录完成任务；只有确实能降低后续查找和维护成本时，才在用户允许的范围内生成必要文件，不为模板完整强行建齐。

### 第三步：区分项目基线与文章需求

如果任务是全库审核，按照 [completeness-audit.md](references/completeness-audit.md) 检查项目基线，输出有证据的分项状态、总分和关键缺口。分数不能代替阻断项：核心企业身份、目标产品事实或必要公开权限缺失时，即使其他项目得分较高也必须单独提示。

如果任务来自关键词、文章标题或大纲，先读取 [article-material-preparation.md](references/article-material-preparation.md)。把文章信息作为资料查找和处理约束，不在此时审核大纲质量或运行写作闸门。

### 第四步：制定文章资料准备计划

记录标题、关键词、大纲、目标市场、目标语言、品牌写法、文章视角、篇幅和不得编造的字段。外文大纲必须同时显示“外文原文＋中文理解”：保留原文措辞和层级，中文只作辅助理解，不替换原文；明显丢失换行时只在层级确定的情况下拆分，存在歧义时交运营确认。再为每篇文章识别需要准备的资料类型：

- 企业事实；
- 目标产品、型号及参数；
- 技术原理或行业知识；
- 应用场景、解决方案或案例；
- 必须使用的术语和语言；
- 可能需要的表格、文字型图片或第三方资料。

这一步的输出是资料覆盖点，不是对大纲主张的事实裁决。

### 第五步：定位资料并给出处理建议

按正式知识、项目资料稿、资料内容导航、资料索引与本地文件、客户官网和已保存网页资料的顺序定位候选来源。先用公司/品牌/产品/型号/参数/主题及中英文术语匹配导航，再定向扫描候选页段；不要为了“保险”反复解析已经可靠沉淀的资料。

对每份来源输出：

- 资料ID、资料显示名称、原始文件名、原始资料相对路径或URL；显示名称只用于阅读，不等于重命名原文件；
- PDF页码、PPT幻灯片、DOCX可见标题起止范围/开头文字、Sheet与单元格、时间段或具体页面；无法确定时写`待结构扫描`；
- 格式、原始语言和当前提取质量；
- 表格、扫描页、图表、文字型图片或大量纯图片等特殊结构；
- 推荐由Codex直接读取、定向提取、视觉核对、MinerU或OCR；视频/音频改为提示运营准备原始逐句稿或字幕稿。网页默认由Codex提取，只有登录、会话、动态加载或平台限制导致Codex不能可靠取得正文时，才建议运营提供页面文件、复制原文或最后使用Web Clipper；
- 运营需要确认或执行的动作；
- 预计生成的工作稿。

含大量图片的资料先报告图片所在范围。只整理含明确文字、标签、图例或数据的图片；纯产品、展会、工厂、客户合影等图片只标记位置和`视觉素材，未整理`。

文章要求已经给出客户官网、SPU、产品名称或明确页面类型时，在本轮资料准备中主动查找和核验官网直达链接，不等待运营另行批准“开始查找”。官网已有页面定位属于只读资料查找，不属于外部行业研究。找到链接时同一轮给出页面身份、语言、日期、拟支持内容、不能支持的内容和建议取舍；内容运营确认纳入后，再把页面连同其他材料写入《本批待处理材料总纲》。只有总纲进一步确认精确范围、提取稿大纲、建议文件名和输出位置后，Codex才生成网页来源稿。只有实际查找后仍无法确认时才列入Codex继续查找项。

### 第六步：准备缺失资料的获取方案

对本地资料和客户官网没有覆盖的内容，输出：

- 缺失主题；
- 来源类型：现有资料待处理、客户专属事实或公开行业知识；
- 紧急程度：A写作前必须补齐、B质量补充或C月末观察；
- 2—5组可直接使用的中英文搜索关键词；
- 推荐来源类型；
- 建议由运营手动搜索、Codex受控研究，或生成客户沟通卡；
- 客户专属事实的内部处理人：AI知识库专员复核，或优化师/组长对客沟通；
- 建议使用Codex网页提取、运营提供URL/页面文件、必要时Web Clipper或客户答复的获取方式；
- 候选资料的保存位置。

此时只生成补充方案。只有运营明确选择后才在线查找候选来源。Codex完成候选定位后先生成`GAP-Rxx_候选来源与提取方案.md`，内容运营确认纳入的直达链接后，才进入本批材料总纲；总纲确认后才提取正文。在线结果默认进入临时研究层，不自动成为客户事实或正式知识。受控研究可以使用免费行业报告和付费报告的免费公开摘要页，但只使用公开内容并执行时效与来源审核。

客户沟通卡必须一张只处理一个可以独立回答的客户事实或能力。卡片至少写明涉及文章、为什么要问、准备支撑的具体表述、可直接转发的客户问题、客户可提供的资料示例、最低可接受答复、确认人/日期/公开权限、未回复时如何处理，以及建议内部接收人。内容运营只负责转交和记录状态，不要求其自行组织客户话术或直接联系客户。

### 第七步：确认外部候选链接并收齐本批材料

资料推荐页完成后，让运营先选择：

- 本批采用哪些原始文件、网页和资料范围；
- 哪些缺失内容批准Codex在线定位候选来源；
- 哪些客户沟通卡交给相应角色；
- 哪些材料本周不处理。

Codex完成在线定位后，先提交`GAP-Rxx_候选来源与提取方案.md`。每个候选页面必须给出真实可点击直达链接、页面主体、发布/更新日期、质量和时效判断、它能支持什么、不能支持什么、是否建议纳入，以及无法找到直接证据时的明确结论。内容运营逐页选择`纳入本批 / 不纳入 / 继续查找`。未经确认的候选链接不得进入本批处理总纲，也不得提取正文。已经由用户直接提供并明确要求处理的URL视为已完成来源选择，但仍需进入总纲确认提取范围。

外部候选链接确认后，同时接收内容运营已经通过其他工具、人工复制或外部平台获得的Markdown、网页稿、逐句稿、字幕稿或其他提取稿。此时只登记和保护原始提交稿，不统一标题、不整理格式、不翻译、不改写。

资料推荐或整理计划的确认只表示“选择这些材料”，不等于GE正文提取批准。网页能够由Codex读取时不把保存任务转交运营；只有Codex无法可靠读取时，才要求运营提供页面文件、复制原文或必要时使用Web Clipper。

### 第七A步：生成并确认《本批待处理材料总纲》

材料收齐后，读取 [batch-material-processing-outline.md](references/batch-material-processing-outline.md)，把所有后续要处理的材料放在一份总纲中。每份材料必须写清：

- 服务哪篇文章和哪个知识缺口；
- 资料ID、显示名称、原始文件/URL和位置；
- 当前形态：原始资料 / Codex待提取 / 运营外部提取稿 / 已有来源稿；
- 精确处理范围；
- 最小完整语义块、原始标题路径、标题子树起止边界，以及获准的单句/字段级例外；
- Codex提取方法或运营稿接收与核验方式；
- 拟提取或后续处理大纲；
- 原始语言和已批准的语言操作；
- 表格、图表、图片、OCR、视频等特殊结构；
- 标题与属性统一方式；
- 格式整理、逻辑归类、去重、表格、翻译或审核等后续处理意向；GE只登记，不授权执行；
- 明确排除项；
- 各阶段输出文件和位置；
- 完成、抽样和人工复核标准。

正文提取前进行“本批材料处理总纲确认”。确认记录写入单篇文章或本批总控的`00_任务与确认/本批待处理材料总纲.md`。确认后只能生成/接收批准范围的原始提取稿、统一来源属性并核验质量；新增资料或扩大提取范围时重新确认受影响部分。层级整理、去重、重排、表格翻译/文字化、正文翻译、审核版和项目资料稿必须等待“派生处理执行确认”。总纲确认不是文章写作放行或正式知识入库。

在同一个企业知识库项目内使用多个独立任务，不为每个文件复制一个新项目。独立文件或互不依赖的任务可以并行；存在先后依赖的任务按“提取 → 整理 → 确认 → 翻译/入库”顺序执行。环境支持任务分发且用户要求并行时，分派独立任务；否则生成任务队列并顺序执行。

### 第八步：先完成原始提取，再确认派生处理

严格按以下顺序执行：

1. **生成或接收原始稿**：Codex只提取“本批材料处理总纲确认”批准的原始资料范围；运营外部获得的提取稿原样保存到待核验区。
2. **统一标题和属性**：在不修改原始正文的副本上增加资料ID、显示标题、原始标题/文件名、原始URL/路径、语言、范围、提供者、提取方式、关联文章/缺口、日期和核验状态。
3. **完成原始稿质量核验**：检查漏段、乱序、乱码、工具总结改写、数字、型号、单位、表格关系和来源可回溯性。
4. **生成派生处理执行单**：读取 [article-usable-draft-rules.md](references/article-usable-draft-rules.md)，根据实际提取稿列出建议生成的英文翻译稿、结构保真/翻译表格稿、特殊结构稿、项目资料稿和写作分析与对照稿，以及知识主题预览、重排/去重范围、特殊结构样例、翻译计划、哪些处理结果将进入项目资料稿及输出位置。
5. **等待派生处理执行确认**：内容运营逐项选择`同意`、`修改为`或`本批不执行`。确认前不得开始实质派生处理。
6. **生成并汇编项目资料稿**：只执行“派生处理执行确认”批准的标题规范、逻辑归类、精确去重、表格/图表处理、翻译和最小改动审核。翻译稿、表格稿、特殊结构稿分别另存并核验，不写回原始稿；再按稳定知识主题汇入企业项目唯一当前《项目资料稿》。资料稿完整保留可回溯的冲突版本和公开权限待确认内容并标记状态，不在本层作文章禁写或放行判断。
7. **完成资料稿完整性检查并建立文章资料选择表**：检查基础错误、来源映射、企业与产品字段、翻译和结构完整性；相似和冲突内容不得误删。客户已明确禁止使用的正文从知识库输出中排除。内容运营确认资料稿完整收拢后，Codex只建立一次《文章资料选择表》；未覆盖的大纲位置只在覆盖表和缺口区记录，不创建空标题。
8. **等待文章就绪审核**：内容运营确认本篇映射范围后，直接对映射指向的项目资料块运行就绪审核；此时不生成文章写作资料包。
9. **报告完成与异常**：列出完成文件、失败项、未处理范围、修改/删除记录和需要重新确认的新增事项。

统一检查：

- 来源位置是否完整；
- 所有提取稿是否保持原文措辞和顺序，没有混入总结、润色或推断；
- 普通正文是否按最小完整语义块提取；所选标题的下属内容是否完整，原标题路径、原顺序和父子层级是否保留；单句或字段级例外是否确属原生独立信息并带足对象、条件和定位；
- 运营提交的外部提取稿是否保留原始提交版本，并记录提供者、原来源、提取方式和运营初检状态；
- 属性统一是否只增加外层标题和来源字段，没有改写、删减或重排正文；
- 《本批派生处理执行单》是否基于实际提取稿生成，并记录“派生处理执行确认”；
- 格式整理、表格处理、翻译和审核是否分别另存；
- 运营提供的视频逐句稿或字幕稿是否保留为不可覆盖的原始提交稿，并记录提供者、提取方法、时间码和初检状态；
- 原文、OCR结果、翻译、整理和总结是否被明确区分；
- 项目资料稿完整性检查是否覆盖基础错误、企业与产品字段、翻译、结构和来源；冲突、风险或公开权限待确认内容是否被保留并标记，而不是提前删除；
- 项目资料稿是否为企业项目唯一当前入口，按知识主题完整收拢英文内容，中文核对区是否与英文块对应，是否避免整篇使用引用格式；
- 文章资料选择表是否只保存选择、用途、限制和覆盖状态，没有复制完整正文或建立空大纲标题；
- 就绪审核是否只检查映射指向的资料块，并单列客户审核、冲突、风险、禁写和放行判断；
- 放行后生成的文章写作资料包是否只包含本篇获准使用的资料块；每块是否可回到项目资料稿和原始证据，风险块是否保留标签和使用提醒，是否排除明确禁用、无可靠正文、`summary`、`inference`、无来源AI句子和无法回溯的跨来源综合；
- 当前文章写作资料包是否在人工放行后生成且唯一，历史版本是否已明确归档；项目内相对链接是否可解析，是否仍残留已确认失效的旧电脑绝对路径；
- 多来源`structured-source-derivative`是否具有逐行或逐字段核验记录；内容核验状态与Codex技术访问状态是否分开记录；
- 型号、参数、数字和单位是否对应；
- 表格的行列和层级关系是否保留；
- 是否混淆企业事实与行业知识；
- 是否存在冲突、敏感信息或不可靠推断；
- 是否满足任务单的知识缺口。

不合格结果退回原任务补充，不直接进入正式知识。

### 第九步：判断文章就绪度

只有必要候选资料已经收集并完成本轮Work处理、当前项目资料稿完成完整性检查、内容运营确认文章资料选择表范围后，才读取 [readiness-and-maintenance.md](references/readiness-and-maintenance.md) 并运行正式文章就绪审核。审核直接读取选择表指向的项目资料块和来源，不以文章写作资料包作为前置条件。

按照参考规则给出以下唯一主结论之一：

- **可以写**
- **有限度可写**
- **暂不建议开始**

同时列出可写范围、限制条件、缺失信息、需处理资料和客户待确认项。客户审核事项单独列出案例公开、竞品品牌与内容、合作方或合作商名称、客户名称、价格和内部信息；没有发现时明确写“未发现”。目标语言为英文且存在英文原稿或翻译稿时，把英文原稿检查和中英翻译对照检查并入本次就绪审核；只列问题和修改建议，不直接重写全文。不要只给分数而不解释影响。

大纲位置未被当前知识覆盖时，不把决定全部交给AI知识库专员。先用直接、简短的语言告诉内容运营：

- 这个位置现在能写什么、不能写什么；
- 项目资料稿中哪些具体资料块可以直接使用；
- 已经定位但尚未提取的本地文件或官网页面有哪些；
- 是否仍需继续找新资料；
- 可以删除、改写、补资料或带限制继续的选项。

推荐替代大纲时，必须同时写明改成什么、由哪些现有资料块和来源覆盖、是否还要处理已定位资料、是否仍要继续找资料、改后还有什么不能写。不能说明实际覆盖来源的标题，不得称为“可提高引用率或覆盖率”的替代方案。

由内容运营决定后返回对应步骤：改成现有知识可覆盖的内容时更新大纲和文章资料选择表；需要使用尚未提取的项目资料时返回来源选择、提取和派生处理；保留原主张并补资料时返回缺口分析、客户补充或受控研究；保留原主张但本次不补时继续文章分析，同时保留未覆盖限制，不得把缺口写成已有证据。新增或改变的部分完成后重新审核受影响章节；影响全篇主张、公开风险或多个章节时重新运行整篇就绪审核。

内容运营完成文章写作放行确认后，才从获准的项目资料块生成《文章写作资料包》。公开待确认、来源冲突、动态快照和限定范围的外部研究可以随运营选择进入资料包，但必须保留风险标签、不同来源版本和具体核对要求，不得写成已确认事实；只有明确禁用、无可靠正文、`summary`、`inference`和无来源AI说法排除。

内容运营、客户或审核人员提出新资料、纠正表达、翻译修改、大纲变化或新意见时，用户只需提供企业项目和材料路径；知道时再补充新旧关系、影响文章和公开限制，不要求用户手工修改索引或判断返回步骤。Codex按变化类型返回原文证据、派生处理、来源选择或文章资料选择步骤，只重做受影响部分。事实、参数、翻译、来源、公开范围或使用边界发生变化时，把旧资料包和旧就绪报告转为历史，当前结论标记`needs-rereview`，文章写作放行状态恢复`pending`；重新审核和放行后再生成新资料包。

同一知识缺口再次出现时，提醒内容运营它已经影响多少篇文章、此前如何处理、现在是否仍未补充。内容运营可以选择仅记录、纳入月末汇总或立即补充；不得按固定次数自动升级。月末只把需要集中处理或持续观察的缺口汇总给AI知识库专员。

### 第十步：处理写作后反馈

正式文章终稿一经提交，默认在`03_文章任务/[周期]/[文章ID]/30_写作后记录/[文章ID]_文章引用清单.md`生成或更新《文章引用清单》，不需要用户另行提出；先记录文章ID、版本、正文文件和内容指纹，再记录：

- 实际使用了哪些正式知识和临时资料；
- 哪些知识没有找到；
- 出现了哪些新问题、冲突或客户确认结果；
- 哪些内容值得形成正式知识候选；
- 哪些临时结果可以归档而无需入库。

引用清单应覆盖能够可靠定位的事实主张和来源；确实无法建立可靠对应的内容逐项标记“未追踪”，不得因此跳过整份清单，也不得凭文本相似度猜测来源。用户明确说明文章是测试稿且不要求发布审查时，可以只登记能可靠映射的引用，把明显超出资料范围的内容集中记为“未追踪/测试观察”，不逐句挑错、不撤销写作放行、不让旧就绪报告恢复待审核。文章只是发现候选的线索，沉淀时仍以项目资料稿为主要入口并回到原文证据核对；不能因为生成了写作后反馈或引用清单就结束知识回收。

只记录文章、任务日志、引用清单或人工反馈能够证明的使用情况；没有可靠记录时标注“未追踪”。按稳定知识块ID记录映射文章数、实际使用文章数、有效使用次数、最近使用时间和问题标记次数；同一知识块在同一篇文章中多次使用，实际使用文章数只增加1。内容运营输入的单篇引用率必须标记为`operator-provided`并记录文章版本、统计月份、输入人、输入日期和数据来源；Codex不得把该值冒充自身计算结果。需要由Codex计算单篇引用率或讨论跨系统可比性时，读取 [governance-and-citation-metrics.md](references/governance-and-citation-metrics.md) 并检查统一文本、引用清单和评分器；条件不足时不得自行给出单篇百分比。

### 第十一步：沉淀正式知识

公司信息、产品、服务、解决方案、FAQ、认证与能力、案例以及企业提供的行业知识，在来源可追溯、终稿检查通过并获人工确认后，应尽量完整沉淀到正式知识，不以本篇是否实际引用为条件。冲突版本并列保存，公开待确认、动态信息和限定范围内容分别打风险标签；标签控制后续核对和使用方式，不自动阻止沉淀。客户明确禁止、无法取得可靠正文、`summary`、`inference`和无来源AI说法除外。

公开资料、搜索或AI辅助当前文章新补充的行业知识先进入等待区。没有真实来源的AI内容不得成为知识候选；有可靠来源的内容由内容运营在文章完成后选择`沉淀正式知识 / 继续观察 / 不沉淀`。

正式知识需要以项目现有风格保留来源、风险标签、状态和更新时间；YAML 元数据是可选方式，不为统一格式批量重写已有文件。标签可叠加；对冲突内容保留不同版本及其来源，不擅自裁决。

沉淀完成后记录稳定知识块ID、实际写入文件与标题位置、更新现有文件或新建文件的理由、重复检查结果、来源与确认状态，并同步知识地图和更新日志。只生成候选但尚未写入时不得标记为“已沉淀”。

### 第十二步：更新项目状态

更新适用的控制文件：

- 资料索引；
- 知识地图；
- 任务队列；
- 风险与待确认；
- 术语表；
- 更新日志。

只更新本次任务实际改变的状态，不制造虚假的“已处理”记录。

## 高保真原文底线

- 原始文件保持内容和格式不变，以内容指纹验证未被替换。
- 默认把“最小完整语义块”而不是零散句词作为证据单元。有标题时按标题子树提取所选标题及其下属完整内容；无标题时至少保留完整段落或连续语义段。只有定义、条款、参数、列表项、术语字段或客户独立答复等原生原子信息可以单句/字段级提取，并保留上级标题、对象、条件和来源位置。
- 原文证据尽量保留原标题文字、顺序和相对层级。技术容器要求调整Markdown标题级别时，只能让整个子树等量移动，并记录原始标题路径和原始级别；不得压平、重新挂接或把下级标题默认拆成孤立证据。层级整理属于独立派生处理。
- 原文证据逐段记录资料ID、资料显示名称、原始文件名、原始相对路径和精确位置；PDF用真实页码，PPT用幻灯片，DOCX优先用可见标题起止范围和开头文字，Excel用Sheet与单元格范围，网页用URL与获取日期，视频用时间段。DOCX程序段落序号只作可选的后台辅助定位，必须注明非Word页码。
- 区分 `verbatim`、`ocr-verbatim`、`source-original-english`、`table-structure-preserved`、`table-translation`、`structured-source-derivative`、`cleaned-transcript`、`translation`、`summary` 和 `inference`。前八类在满足核验与来源映射要求后可以进入项目资料稿；完成文章就绪审核和人工放行后，获准内容连同风险标签和使用提醒进入文章写作资料包。只有原始来源类型可以称为客户原话；`summary`和`inference`不得进入。OCR低置信或人工修订处必须标记。
- 提取稿正文只允许保留原文。为便于定位可以增加标题、资料ID和来源字段，但不得在引用块或原文区改写、总结或补全。
- 运营提供的外部提取稿必须标明`provided_by: operator`及核验状态；运营负责核对其是否完整、无改写并与原页面一致，Codex在未取得原来源或未完成抽查前只能按`operator-supplied-unverified`使用。
- 保留表格的行列、表头、单位和合并关系。可增加说明，但说明不能替代表格证据。
- 表格翻译和表格文字化是两个独立派生操作；未通过“派生处理执行确认”时不得执行。
- 提取失败或无法核对时保留定位并标记待确认，不用语言模型补齐。

详细执行和抽样复核规则见 [verbatim-evidence-rules.md](references/verbatim-evidence-rules.md)。

## 表格默认策略

- 小而清晰且需要长期复用的参数表或对比表：保留 Markdown 表格；只有标题和表头不足以说明用途时才增加简短说明。
- 多型号、多参数表：保留表格，不全部改写成长段文字。
- 超宽表、多层表头或合并单元格：标准化、拆分或转为长表，同时保留原文件位置。
- 大型 Excel：保留 Excel/CSV 作为权威数据，按需直接读取；Markdown 只保存必要的索引、字段说明和高价值摘要。
- 图片或扫描表格：只处理可识别文字和数据，提取后结合原页面视觉核对；纯视觉图片只记录位置。

不得让说明文字取代表格中的精确对应关系。详细规则见资料处理参考文件。

## 人工确认节点

按 [human-review-gates.md](references/human-review-gates.md) 执行人工闸门。至少遵守：

- 每个确认项使用`编号｜人能看懂的业务标题`，正文继续说明确认对象和影响；不让人工只凭编号判断；
- 项目、资料路径或写入范围不明确时先确认；
- Codex新找到的外部链接先完成“外部候选来源选择”；内容运营选定其余材料并提交自己已有的外部提取稿后，先生成一份覆盖全部材料的《本批待处理材料总纲》；确认前不提取正文、不整理格式、不处理表格、不翻译；
- 所有资料生成正文提取稿前，在总纲中确认精确范围、提取方法、拟提取主题与字段、特殊结构盘点、排除项、提取稿大纲和原始稿输出位置；后续处理只登记意向；
- 原始提取稿完成并核验后，先生成《本批派生处理执行单》；“派生处理执行确认”前不整理层级、不重排或去重、不翻译、不处理表格/图表，也不生成项目资料稿；
- 准备上传外部API、使用付费工具或把客户资料交给第三方前必须确认；
- 企业事实、参数、版本、表格、OCR或公开范围不可靠时停止相关分支；
- “有限度可写”和“暂不建议开始”必须进入“文章写作放行确认”，由运营按真实业务选项决定下一步；
- 正式知识沉淀前必须获得人工批准；
- 等待确认时继续完成不受影响的只读或低风险工作，把问题合并提问，不因一个异常阻塞全部文件。

## 完成标准

完成一次资料登记任务时，至少交付：

1. 成功登记、重复跳过、疑似新版本和异常文件清单；
2. 每个成功登记文件的权威原始路径和Obsidian索引位置；
3. 已更新的资料索引；
4. 轻量扫描结果和建议处理优先级；
5. 明确说明本次是否读取了正文，以及未执行的深度处理。

完成一次文章资料准备任务时，至少交付：

1. 面向运营的行动摘要，以及已有官网和本地候选资料；
2. 每份资料的具体位置、格式、语言、表格和图片情况；
3. Codex提取、运营提供页面内容、必要时Web Clipper、OCR、视频逐句稿/字幕稿准备或暂不处理等建议；
4. 缺失资料的搜索关键词、来源方向和建议执行人；
5. 等待运营选择的材料、外部候选链接和外部提取稿提交要求；
6. 明确说明外部链接完成“外部候选来源选择”且材料收齐后还会生成《本批待处理材料总纲》，当前确认不等于开始提取；
7. 明确说明尚未执行文章就绪审核。

完成一次本批材料处理总纲任务时，至少交付：

1. 本批全部原始资料、网页、Codex待提取项和运营外部提取稿清单；
2. 每份材料的当前形态、精确范围、最小完整语义块、原始标题路径与标题子树边界、提取或接收方法、语言、特殊结构和质量状态；
3. 每份材料的提取大纲、标题与来源属性统一方式、后续处理意向和排除项；
4. 原始稿和属性统一稿的输出位置，以及后续派生稿的预计位置；
5. 可复制的“本批材料处理总纲确认”块，并明确该确认不批准后续派生处理。

完成一次派生处理执行单任务时，至少交付：

1. 已完成的原始提取稿、核验状态和已知问题；
2. 文章中英文大纲与资料块的层级映射预览；
3. 分别列明英文翻译稿、结构保真/翻译表格稿、特殊结构稿、项目资料稿和写作分析与对照稿，并说明哪些核验后的处理结果会进入项目资料稿；
4. 每类特殊结构的代表样例、表格两步处理及翻译分批计划；
5. 各派生稿输出位置、原文层与AI派生层的隔离检查，以及可复制的“派生处理执行确认”块。

展示时一份本地资料使用一张资料卡，一个知识缺口使用一张行动卡。表格只用于少量固定字段的简短对比，不把文件名、路径、范围、格式、建议和运营动作塞入同一张大宽表。

完成一次文章就绪审核时，至少交付：

1. 每篇文章的唯一就绪结论；
2. 已处理Work和可用证据；
3. 可以放心写的内容、有风险但可由运营决定使用的内容，以及明确排除的内容；
4. 适用时并入英文原稿检查和中英翻译对照检查；
5. Codex或内容运营可以自行处理的任务；
6. 知识覆盖缺口和需要内容运营决定的事项；
7. 必须交给优化师/组长联系客户的事项；
8. 一事一卡的知识缺口、冲突、限制和待确认项，并写明暂时安全写法；
9. 最终需要人工选择的放行方案；
10. 本次未覆盖范围和已知限制。

面向内容运营的缺口卡优先使用“现在能写什么、不能写什么、可改成什么、请选择怎么处理”的直白结构。内部再记录返回步骤、重新审核范围和月末汇总状态，不把后台流程术语堆在操作说明里。

每次面向运营交付文件后，只在聊天中给出简短的交接提示，不把固定提示写入Markdown文件。说明当前步骤、运营现在要做什么、确认后Codex做什么，以及如何退回修改。

完成一次知识内容完备度审核时，至少交付：

1. 分项证据、覆盖度、证据质量和公开可用性；
2. 总分、分类分和评分版本；
3. 无论总分高低都必须提示的关键缺口；
4. 一事一卡的“客户资料或确认”和“可在线研究”两类补充动作；
5. 本次未扫描或无法判断的范围。

完成一次项目级知识库质量审核时，至少交付：

1. “找得到、用得上、信得过、能复用、能增长、能交接”六个维度的状态、证据、影响和处理建议；
2. 当前文章就绪状态与项目长期质量的明确区分；
3. 控制文件、当前入口、风险记录、交接信息和重复处理成本的检查结果；
4. 阻断项、关注项和本次未检查范围；
5. 不与内容完备度总分混算的独立结论。

完成一次月度维护时，至少交付：
1. 运行与规范状态，覆盖路径、负责人、标准目录、文件/文章命名、当前与历史版本及追溯链；
2. 七个标准模块的源文件覆盖现状、主要缺失和本月变化；
3. 本月处理的源文件、新增/更新的正式知识，以及已提取但未沉淀且需要运营决定的事项；
4. 纳入文章数、有效录入数、缺失文章、月平均引用率、`15%`达标线和KPI结论；
5. 新增与遗留问题的本月进展、当前状态及下月行动；发现几项就记录几项，并按优先级排序。逐篇引用率明细保留在月度CSV；固定简报不附带无异常依据的全面评分或知识块指标。

完成一次高保真提取任务时，至少交付：
1. 原始资料ID、内容指纹和处理范围；
2. 按最小完整语义块提取的原文、原标题路径、标题子树层级及精确位置；
3. 提取方式和 OCR/人工修订状态；
4. 表格、图表或图片的保真处理说明；
5. 抽样核验结果、失败项和未处理范围。
输出以内容运营能直接行动为准，避免只描述处理过程。
