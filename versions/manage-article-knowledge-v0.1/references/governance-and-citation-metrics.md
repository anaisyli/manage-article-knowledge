## 1. 能力边界

本Skill可以：

- 审核当前可访问的项目或共享快照；
- 检查目录、索引、证据、完备度和维护状态；
- 生成项目审计报告；
- 记录文章实际使用的知识来源；
- 接收内容运营逐篇录入的引用率并计算月平均引用率KPI；
- 检查引用计算所需数据是否齐备。

本Skill本身不能：

- 在没有同步工具时自动看到所有人员电脑；
- 保证多端实时同步、冲突处理、权限和备份；
- 从没有检索日志的RAG SEO系统还原真实知识使用情况；
- 让生成文章的AI自行给出可信引用率；
- 把一次本地扫描结果或Codex推测值直接用于人员绩效。

## 2. Obsidian项目治理要求

每个项目至少记录：

| 字段 | 说明 |
| --- | --- |
| project_id | 跨电脑和系统稳定的项目ID |
| client_name | 客户名称 |
| owner | 当前负责人 |
| vault_path | 本地或共享库位置 |
| shared_snapshot | 公司审计使用的共享位置 |
| last_sync_at | 最后成功同步时间 |
| sync_status | 正常、延迟、冲突、未配置、失败 |
| audit_standard | 完备度标准版本 |
| last_audit_at | 最近审核时间 |
| unresolved_conflicts | 未解决同步或知识冲突 |

路径变化不能改变project_id。人员交接时先检查同步、未接收资料、未解决冲突和最近备份。

## 3. 同步和集中审计的最低条件

在选择Obsidian Sync、企业网盘、版本控制或其他技术前，先要求方案满足：

- 所有纳入管理的项目有唯一ID和负责人；
- 公司有可访问的共享副本或审计快照；
- 能知道最后同步时间和失败状态；
- 不会静默覆盖多人修改；
- 能恢复误删或错误版本；
- 有客户级访问权限；
- 能排除缓存、临时文件和不应同步的敏感内容；
- 审计时能固定一个时间点的快照；
- 能记录同步冲突和处理人。

未满足这些条件时，只能称为个人本地知识库，不能声称已实现公司集中管控。

候选方案可参考Obsidian官方的[跨设备同步说明](https://obsidian.md/help/sync-notes)：

- Obsidian Sync适合官方远程库和共享库场景；
- OneDrive等云盘方案要确保库文件始终保留在本地，避免按需下载造成缺失；
- Git适合版本追踪，但默认需要明确的提交、推送和拉取流程；
- 不要让同一个库同时由多种同步服务管理；
- 同步不能替代独立备份。

选型结论必须经过多人并发、冲突、离线修改、大文件、权限和恢复演练，不能只依据个人教程。

## 4. 人员与项目比较边界

可以比较：

- 使用同一审核标准和版本的项目；
- 来自同一审计时间窗的共享快照；
- 有明确审核范围、缺失范围和同步状态的结果；
- 完备度、阻断缺口、过期冲突、处理及时性等可核对指标。

不得直接比较：

- 一个已完整同步项目和一个同步失败项目；
- 不同客户资料基础、不同项目阶段却没有分组说明的总分；
- 仅凭文件数量、字数或Markdown数量；
- 没有人工抽样或申诉机制的自动评分。

培训和绩效应先区分普遍流程问题、客户资料客观不足、工具失败和个人执行问题。

公司可以把本文件第6B节的月平均引用率作为月度知识使用KPI，但该KPI使用内容运营逐篇录入的数据，不等于Codex从文章文本计算或验证了单篇引用率。若用于人员绩效，还必须统一人员归属、文章范围、数据来源和缺失处理，不能只比较一个人的已录入高值文章与另一个人的完整文章范围。

## 5. 文章引用清单

固定保存路径：`03_文章任务/[周期]/[文章ID]/30_写作后记录/[文章ID]_文章引用清单.md`。单篇文章的引用明细只在这里维护。

正式文章终稿提交时，必须默认生成或更新机器可读的引用清单，不需要用户另行提出。已有清单时按`article_id`、`article_version`和正文内容指纹更新；确实无法建立可靠来源对应的具体主张标记`未追踪`，不得跳过整份清单或凭文本相似度猜测：

| 字段 | 说明 |
| --- | --- |
| article_id | 文章稳定ID |
| article_version | 被计算的文章版本 |
| claim_id | 文章中的事实或观点单元 |
| article_location | 段落、句子或字符范围 |
| claim_type | 企业事实、行业事实、案例、参数、观点等 |
| source_id | 知识文件或原始资料ID |
| source_location | 页码、Sheet、URL、时间段或证据ID |
| support_type | direct-quote、paraphrase、derived、context |
| verification | 自动匹配、人工核对、未核对 |

没有文章版本和来源定位的清单不能用于稳定比较。

## 6. 指标拆分

不要把所有概念混成一个“知识库引用率”。至少区分：

### 知识支持率

文章中需要证据的事实性主张，有多少拥有有效知识库来源。

候选定义：

```text
有有效来源支持的事实性主张权重
÷
全部事实性主张权重
```

主张如何切分及权重如何设定仍需固定规则和测试集，否则不同AI会产生不同结果。

### 客户原文使用率

文章正文中有多少内容能够与已审核的客户原文证据建立直接文字对应。

候选定义：

```text
与已审核客户原文形成非重叠有效匹配的正文字符或词元
÷
纳入统计的文章正文字符或词元
```

必须由确定性程序规定文本规范化、最短匹配、通用短语排除、重复匹配和中英文分词，不能由写作AI目测。

### 来源使用覆盖

推荐给文章的高价值知识中，有多少确实被采用。该指标用于改进资料推荐，不等于文章质量或引用率。

## 6A. 知识块使用记录

累计指标固定保存在项目`00_项目管理/知识地图.md`。文章引用清单提供本篇证据，知识地图负责跨文章累计；正式知识正文不保存这些计数。

为需要长期维护的知识块分配稳定`knowledge_block_id`。只有文章映射、引用清单、任务日志或人工反馈能够证明时才更新：

| 字段 | 定义 |
| --- | --- |
| `mapped_article_count` | 该知识块被纳入资料映射的不同文章ID数量 |
| `used_article_count` | 有可靠记录证明实际使用该知识块的不同文章ID数量 |
| `valid_usage_count` | 具有不同文章位置或事实主张的有效使用记录数量 |
| `last_used_at` | 最近一次有效使用日期 |
| `issue_flag_count` | 被记录为错误、冲突、过期、敏感或不适用的次数 |
| `usage_tracking_status` | `tracked`或`untracked` |

同一知识块在同一篇文章中出现多次，`used_article_count`只增加1；如果对应不同、可定位的文章位置或事实主张，`valid_usage_count`可以分别增加。重复运行同一文章版本、重复导入同一清单或同一位置的多次匹配不得重复计数。

不要用文章文本相似度推断实际使用，也不要把“被推荐”“被映射”和“实际使用”混为一类。没有可靠数据时标记`untracked`。低使用只能作为维护优先级信号，不能单独证明知识无价值或触发删除。

## 6B. 内容运营输入的月度引用率KPI

每月固定使用两个归档文件：

- 原始输入：`04_归档/月度维护/YYYY-MM/YYYY-MM_引用率原始输入.csv`；
- 汇总简报：`04_归档/月度维护/YYYY-MM/YYYY-MM_企业知识库月度维护简报.md`。

内容运营提供的逐篇数据先记录或同步到对应文章引用清单；月末由Codex汇出当月CSV快照，再据此更新同目录报告。内容运营直接提供整月CSV时，Codex按文章ID和版本同步对应引用清单后再计算。原始输入不得被报告中的汇总表替代，也不要在项目根目录另建当前统计表。

月度KPI不要求Codex计算单篇文章的引用率。内容运营为统计月内每篇正式完成文章录入一个引用率，Codex只校验输入和计算月平均值。

### 单篇输入字段

| 字段 | 要求 |
| --- | --- |
| `project_id` | 项目稳定ID |
| `article_id` | 文章稳定ID；同一统计月只纳入一次 |
| `article_version` | 被考核的最终文章版本 |
| `statistics_month` | `YYYY-MM` |
| `citation_rate` | 内容运营输入的`0—100`百分数 |
| `rate_provenance` | 固定记录`operator-provided` |
| `rate_source` | 引用率来自哪个系统、表格或人工记录 |
| `input_by` | 内容运营输入人 |
| `input_at` | 输入日期 |
| `include_in_monthly_kpi` | `yes / no`；`no`必须写排除原因 |
| `exclusion_reason` | 不纳入时的具体原因；纳入时可留空 |

默认范围是统计月内全部正式完成文章。测试稿、取消稿和未完成稿默认不纳入；确需纳入时由内容运营明确标记。不得为了提高均值临时排除低值文章。

### 计算规则

```text
月平均引用率
= 当月所有有效纳入文章的单篇引用率之和
÷ 当月有效纳入文章数
```

- 每篇文章等权，不按字数、项目或负责人二次加权。
- 同一文章同一统计月只使用一个最终版本；重复版本先由内容运营确认保留哪一条。
- 保留原始输入值，报告中的平均值四舍五入到小数点后2位。
- 月平均引用率`≥15%`：`达标`。
- 月平均引用率`<15%`：`未达标`。
- 指标方向：`越高越好`；本Skill不自行增加“优秀、卓越”等额外档位。
- 与达标线差值按`月平均引用率 - 15%`记录。

### 缺失和异常

- 任何纳入文章缺少引用率、文章ID或文章版本时，列出缺失文章，KPI状态为`数据不完整，暂不判定`。
- 可以显示基于已录入文章的`暂算平均值`，但不得据此标记达标。
- 引用率小于0或大于100、同一文章重复纳入、月份不一致时停止计算并要求内容运营修正。
- 当月没有正式完成且纳入的文章时，状态为`当月无可考核文章`，不记0分。

该KPI是月度考核指标，但不替代项目六维质量、知识内容完备度、事实准确性或文章发布审核。高引用率不能覆盖来源冲突、公开限制、错误引用或项目阻断项。

收到包含上述字段的CSV时，运行`../scripts/calculate_monthly_citation_kpi.py <csv> --month YYYY-MM`；按项目过滤时增加`--project-id PROJECT_ID`。脚本只校验和汇总运营输入，不生成单篇引用率。

## 7. 统一计算的前置条件

以下条件适用于由系统或Codex计算单篇引用率、比较跨系统算法结果的场景；不阻止第6B节使用内容运营已录入的单篇值计算月平均KPI。RAG SEO和Codex/Obsidian想得到可比的自动计算结果，至少需要：

1. 相同的文章正文版本；
2. 相同的纳入和排除范围；
3. 跨系统稳定的文章ID、项目ID和来源ID；
4. 可定位的引用清单或检索使用日志；
5. 独立于生成模型的同一评分程序及版本；
6. 固定文本规范化、主张切分或匹配规则；
7. 一组人工标注的基准文章；
8. 重复运行稳定性、准确率和误差测试；
9. 算法版本、运行时间和输入指纹记录。

产研未提供RAG检索日志或引用接口时，不得声称已准确统计RAG SEO的知识使用。

## 8. 当前可执行与待产研实现

### 当前可执行

- 生成引用清单；
- 检查来源是否可回溯；
- 统计有明确记录的来源使用；
- 接收并保存内容运营输入的单篇引用率；
- 按第6B节计算月平均引用率、与15%达标线的差值和KPI状态；
- 按知识块ID统计映射文章数、实际使用文章数、有效使用次数、最近使用时间和问题标记次数；
- 标记“未追踪”；
- 准备人工标注样例；
- 比较算法版本的测试结果；
- 拒绝AI自报百分比。

### 待产研或数据侧实现

- RAG SEO引用和检索日志接口；
- 统一来源ID映射；
- 确定性评分脚本或服务；
- 基准数据集和一致性测试；
- 公司级同步、权限、备份和冲突机制；
- 集中看板、抽查和绩效数据链路。

这些能力未实现前，报告中必须写明限制，不能用Codex估算百分比替代内容运营输入。第6B节的月度KPI必须始终标明单篇值为`operator-provided`。
