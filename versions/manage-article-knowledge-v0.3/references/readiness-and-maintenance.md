## 1. 文章前知识审核前置条件

只有以下条件满足后才生成正式审核：

- 文章要求、大纲和其他限制已记录；
- 当前文章需要的提取稿已齐备并核验；
- 提取范围与代表处理样本已由人工确认；
- 官网数量与交互范围已闭合，Office嵌入子资料和关键图片均已登记或明确排除；
- 确认范围已完成原文提取和必要派生处理；
- 本地资料处理后形成的真实缺口已完成必要调研或明确保留；
- 正式知识、项目资料稿和外部调研均能回溯来源；外部调研同时存在原文证据和独立整理稿；
- 已完成整理并通过核验的客户资料、官网页面和外部调研均已登记到`10_知识候选分流.md`，没有因为“文章未使用”停留在待决定；
- 候选分流只使用`待核验 / 可自动沉淀 / 部分可沉淀 / 异常待处理 / 已沉淀 / 不沉淀`，其中`可自动沉淀`在本轮结束前必须完成沉淀事务或转为有证据的异常；
- 处理结果中的异常已列明。
- 零散表面修正已有源文件级处理记录；影响事实、公开使用或知识沉淀的源文与事实异常已有唯一异常ID、集中台账记录和受影响`CLAIM`；
- 审核Agent已提交实际读取、未读取、证据定位、反例和不确定点清单；
- v0.3项目校验未发现正式知识目录落位、`CLAIM`字段、逐块来源定位、模块总览矛盾、沉淀状态、断链、模板变量、表格列数、旧电脑路径、重复当前稿或旧状态路径等阻断错误。

如果条件不满足，输出缺少的具体条件和应返回的步骤，不生成虚假的“部分审核”结论。

## 2. 审核内容

文章前知识审核至少检查：

### 需求覆盖

- 标题、关键词和每个大纲部分是否有知识支持；
- 支持内容是否实际存在于处理稿或正式知识；
- 是否把计划提取误写成已经提取；
- 缺口是否会影响核心主张。

### 来源与事实

- 企业事实是否来自客户文件、客户官网或客户确认；
- 外部行业知识是否来自可靠直接来源；
- 外部调研结论是否能定位到独立保存的网页/文章原文，而不是只有链接、摘要或Codex总结；
- 企业提供行业知识与Codex外部调研是否分开；
- 文章拟用事实能否定位到具体页码、章节、字段或网页区块；
- 审核表每个回溯位置是否只有一个最有用的可点击链接，优先指向清理稿并带PDF页码；
- 审核是否错误地把尚未生成的文章写作输入当作来源；
- 是否存在无来源AI推断。

### 一致性

- 数字、型号、单位、时间、参数和术语是否一致；
- 不同版本是否冲突；
- 动态数据是否标明日期；
- 翻译是否改变事实、范围或强度。

### 公开与风险

- 客户名称、合作方、案例、订单、评价是否允许公开；
- 价格、MOQ、产能、认证、效果数据和承诺是否可靠；
- 是否出现“第一、最好、保证”等高风险表述；
- 是否把行业能力写成客户自身能力；
- 禁用内容是否被排除。

### 写作输入可用性

- 获准知识是否足以生成目标语言的本篇知识库附件；
- 来源定位、数据日期和必要使用边界是否明确；
- 写文章Skill在收到运营另行填写的文章要求后，是否只需上传`30_文章写作输入.md`，无需再打开其他项目文件。
- 写作输入是否严格按文章大纲组织，而不是按源文件堆放；
- 每个段落或连续知识块是否有来源链接和精确位置；
- 是否存在为了补齐大纲而生成的无来源场景、过渡、卖点或结论。

## 3. 审核结论与回退

只使用三档：

- `可以进入写作`；
- `处理指定问题后可以进入写作`；
- `暂不能进入写作`。

不使用百分制、总分、分类分或六维评分。

每个问题记录：

- 问题标题；
- 受影响大纲和主张；
- 当前依据；
- 风险；
- 需要的材料或决定；
- 返回节点；
- 处理后复核结果。

客户专属事实缺失时，生成单主题客户沟通卡，不把多个无关问题混在一起。至少记录：

- 人能看懂的客户问题；
- 为什么值得询问；
- 客户回复前怎么安全处理；
- 当前阶段和下一步由谁做。

Codex先判断是否可以通过现有正式知识、尚未处理的本地资料、官网或改写大纲解决。仍然缺失时只建立候选事项，阶段为`待判断要不要问`；知识库专员负责判断是否真的需要客户补充。确认需要询问后，阶段进入`准备客户话术`，主Agent生成可直接发送的话术草稿；知识库专员确认话术并指定优化师后进入`等待发送`。内容运营只作为文章需求或发现来源，不默认承担必要性审核或对客沟通。

客户事项长期正文统一维护在`05_数据与审核/30_异常与待决定/10_企业知识异常待处理/01_待客户补充事项.md`。文章审核只保留问题ID、项目级链接和本篇处理决定。内容运营或Agent说“以后问客户”时只设为`待判断要不要问`，不得提前填写话术、发送日期或回复字段；文章完成不结束事项。同一事实再次影响其他文章时更新原问题的关联范围，不重复建卡。

客户事项只维护一个阶段字段：`待判断要不要问 / 无需询问 / 准备客户话术 / 等待发送 / 等待客户回复 / 收到回复，待核实 / 已完成`。选择`无需询问`时写明现有资料、安全改写或排除已经足够的原因；进入`等待发送`前必须有知识库专员确认的话术和指定优化师。发送日期与渠道只在实际发送后出现，回复证据只在收到回复后出现；证据核验和受影响文章/正式知识更新完成后才可设为`已完成`。

客户事项阶段与源文异常阶段分别维护。客户回复、解决方案或新版本资料到达后，主Agent必须关联已有问题ID和异常ID，不为同一事实新建第二条异常；登记资料版本/指纹、提供者、日期、证据位置、允许公开范围和替代关系后，把客户事项设为`收到回复，待核实`，把异常设为`处理中`。异常阶段只使用`待判断 / 等待材料 / 处理中 / 部分解决 / 已解决 / 已完成处置（原文未修复）`，并另记`原文是否修复：未修复 / 部分修复 / 已修复 / 无法判断`。

返工只重跑受影响范围：资料处理Agent更新提取稿、`source-normalized-english`或其他派生稿和候选分流；审核Agent独立对照新旧证据检查语义漂移与静默改动，并实际打开异常台账中的保存原文证据、原始来源和现场截图/原页链接，核对逐字原文、原始结构、必要上下文及“经核验仍可使用的原文或原始结构”。主Agent同步当前正式知识、目录、沉淀记录、项目资料稿和进行中的写作输入。已完成文章不静默改写，登记受影响文章、历史主张、风险和是否需要另行修订。原文被新证据真正修复时才能设为`已解决`；原文没有修复但排除、限制、下游更新和历史影响已经做完时设为`已完成处置（原文未修复）`。完成记录永久保留；达到重开条件时恢复原异常ID。

提取稿问题回节点3，范围问题回节点4，知识/公开问题留在节点5。只重跑受影响部分。审核通过后生成新的`30_文章写作输入.md`，旧版进入历史版本。

## 4. 月度维护简报

每月底自动从项目当前文件和集中数据生成`05_数据与审核/50_月度维护/YYYY-MM/YYYY-MM_企业知识库月度维护简报.md`。

固定包含五部分：

### 一、运行与规范

检查：

- 源文件路径、官网和Obsidian路径；
- 当前负责人；
- 标准目录是否存在；
- 文件夹、文章ID、标题和版本命名；
- 内部链接；
- 正式知识来源追溯；
- 每份已核验的整理结果是否在`10_知识候选分流.md`有唯一去向，候选状态、预定路径与实际正式文件是否一致；
- 是否存在以“文章未使用”“等待终稿”为理由阻止知识沉淀，或把正常外部调研长期放在待决定区；
- `部分可沉淀`是否已经把合格`CLAIM`写入正式知识，只将冲突、证据不足或禁止公开的`CLAIM`留在异常区；
- 产品介绍和行业知识模块根目录是否只保留总览，知识文件是否进入规定子目录；
- 每个正式知识文件是否包含完整`CLAIM`字段并逐块映射来源与精确位置；
- 模块总览、正式知识目录、集中沉淀记录与实际正式文件是否一致，是否存在“已有文件但总览写无”或“记录已完成但文件不合格”；
- 正式知识是否按稳定实体或主题组织，是否出现按文章、选品组合、批次或日期重复建文件；
- 产品SPU/型号知识ID是否唯一，价格库存等动态字段是否与稳定产品正文分开；
- 是否只有一份正式知识目录和一份项目资料稿，是否出现重复索引或重复知识正文；
- 当前沉淀状态是否集中记录在`20_知识沉淀记录.md`，沉淀事件是否追加到`40_正式知识沉淀记录.csv`，是否继续堆积逐知识回执；
- 文章引用清单是否逐个`CLAIM`记录`尚未核对 / 已确认使用 / 未使用 / 未追踪`；`尚未核对`是否被错误计入使用次数；
- `20_知识块使用明细.csv`与`30_知识块使用总表.md`是否一致；同一文章同一`CLAIM`多处出现是否只计一次，实体总次数是否按确认使用的不同文章去重；
- `05_数据与审核/`中的每个非Markdown受管文件是否已在`20_知识使用与引用/01_数据说明.md`登记可点击链接、用途、维护责任、人工编辑权限、更新触发、查看方式、编码/格式和最近校验；是否错误地把全部CSV行复制到Markdown；
- `04_资料与证据/`中的PDF、图片、截图、音视频及其他附件是否能从当前源文件总表、内容导航或相关证据/异常页找到；客户Vault内是否混入脚本、缓存、临时文件或其他无Markdown回链的非Markdown文件；
- 是否出现未经记录的覆盖或修改。
- 管理层文件是否默认使用中文，是否残留英文管理字段、模板变量或旧电脑绝对链接；
- 已完成文章的目录、总览、列表、工作台和集中数据是否一致。
- `20_当前待办.md`是否仍是唯一当前状态正文；`30_版本与变更入口.md`是否只链接当前待办并记录项目级变更，是否残留与文章目录或沉淀记录矛盾的自由文本状态；
- 待客户补充事项是否使用唯一问题ID和单一阶段字段，`待判断要不要问`是否明确交给知识库专员，`等待发送`是否已有确认话术和优化师，`等待客户回复`是否有日期/渠道，`收到回复，待核实`是否有可点击证据；
- 源文与事实异常是否使用唯一异常ID，客户事项阶段与异常阶段是否分开，源文件级小修正是否被错误拆成大量长期异常；
- 源资料处理事项是否使用唯一`MAT`、是否链接资料ID和源文件总表、待判断事项是否明确交给AI知识库专员、处理稿是否回链原资料及版本；
- 本月收到的新材料是否已关联原异常、完成版本/来源/公开范围登记、受影响范围返工、独立复核和下游同步；
- 源文与事实异常是否包含可点击保存原文证据、原始来源（可取得时）、精确位置、实际取得的逐字原文/原始结构、必要上下文和现场截图/原页（视觉结构问题）；
- 已解决或已完成处置的异常是否同时具备通俗结论、原文现场证据包、审核核对、可点击完成证据、下游更新和历史影响记录；原文未修复的事项是否明确标成`已完成处置（原文未修复）`，是否存在应重开但仍留在历史区的事项；
- Skill反馈是否区分`Codex自动发现 / 人工提出`，自动项是否有总结依据，人工项是否保留人工原意；未关闭反馈是否从工作台和检查入口可达，并回链相关文件、文章、`CUS`、`ANM`、`MAT`或校验结果；
- 本月实际运行Skill与项目登记的版本、日期和指纹是否一致；若发生新版迁移，是否已自动补齐控制结构、运行当前校验、逐条回归所有未关闭Skill反馈并记录项目级迁移事件；
- 当前执行电脑和Windows账号是否已加载MinerU API Token与到期日；到期日、剩余天数、本月在线检查时间/结果、最近失败类型、API负责人和备用负责人是否明确。在线检查以当前Windows用户为单位，本月已通过时跨项目复用，不重复消耗测试额度；距到期7天提醒一次，距到期1天再次提醒，其他时间不提醒；

没有历史指纹、快照或日志时写`无法确认是否被修改`。

### 二、知识库基础情况

按七个标准模块列出：

- 候选资料，区分客户原文件和客户官网；
- 当前缺口；
- 已处理内容；
- 使用限制；
- 支撑已处理内容的来源；
- 建议补充资料。

此处是事实清单，不做完备度评分。

### 三、本月提取与知识沉淀

列出：

- 本月新增/更新源文件；
- 本月新增、已处理、暂不处理、仍待判断和阻塞文章的`MAT`；待处理视频、压缩资料、提取困难及不确定重复/版本关系逐项链接详情；
- 本月完成的提取、翻译和结构处理；
- 本月自动沉淀的正式知识；
- 本月仅更新使用数据而未重复沉淀的既有知识；
- 本月新增的动态数据快照、政策当前版本和归档历史版本；
- 已提取但处于异常待处理的企业知识；
- 因来源冲突、证据不足、无法验证或禁止公开而处于异常待处理的外部知识；
- 已沉淀但尚未被文章使用、累计使用次数为0的正式知识；
- 需要内容运营或知识库专员处理的项目。

### 四、月度引用率

- 应纳入文章；
- 已录入引用率文章；
- 缺失文章；
- 月平均引用率；
- 与15%标准的差值；
- 与上月的变化；
- 数据完整性和异常。

月平均`≥15%`为正常，`<15%`为未达标。数据不完整时不得判定达标。

### 五、问题与闭环

对每个问题记录首次发现、上月状态、本月进展、当前状态、影响、负责人/处理对象和下一步。发现几项记录几项，不限制数量。

## 5. 月度问题与行动

月度简报不是评分报告，也不默认生成知识块使用排名。下月行动来自未闭环问题：

- 路径或负责人异常；
- 源文件重大缺失；
- 提取/沉淀积压；
- 引用率低于15%；
- 文章引用率缺失；
- 正式知识不可追溯；
- 正式知识按文章或提取批次重复建立；
- 相同SPU/型号存在多个知识ID或重叠产品正文；
- 动态价格库存进入稳定产品正文；
- 项目资料稿、正式知识目录或证据索引出现重复内容；
- 已核验知识长期停留在`可自动沉淀`，或因“文章未使用”被错误放入异常区；
- `CLAIM`级使用明细、使用总表与文章引用清单互相矛盾；
- 待客户补充事项长期未由知识库专员审核、已确认询问但未生成/确认话术、缺少优化师、长期未发送、长期未回复或已回复未知识复核；
- 源文与事实异常只有问题概括而没有逐字/原样现场证据，来源只有文件名或资料ID而没有可点击链接，或视觉/结构问题没有原页/截图；
- 源文与事实异常长期停留在待核验/审核中、收到新材料后未返工、已解决但未完成下游更新，或关闭后出现满足重开条件的新证据；
- 视频/音频长期未由AI知识库专员判断、疑似文字稿未核验对应关系、确认处理稿没有时间码/来源映射，或内容运营被要求自行提取字幕、音轨和转写；
- 压缩包未登记子资料、外部解压目录未与包内文件逐项比对、加密/损坏/规模异常仍被强行展开，或包内与外部相同文件被重复生成派生稿；
- 指纹完全相同的副本没有指向主资料、一个重复组生成多份当前稿，或指纹不同的相似/疑似版本文件被自动合并、覆盖或删除；
- 重复出现的事实冲突或使用问题。

不要为了凑数量创建行动，也不要限制最多三项。

## 6. 项目负责人交接审核

负责人变化时生成`05_数据与审核/60_项目交接审核/YYYY-MM-DD_项目交接审核.md`。检查：

- 项目ID、企业名称、原负责人、新负责人和生效日期；
- 官网、源文件根路径和Obsidian路径能否访问；
- 路径变化映射；
- 当前文章任务和所处节点；
- 缺少的提取稿；
- 已确认但未完成的提取范围与代表处理样本；
- 企业知识异常待处理；
- 待客户补充事项及其当前阶段、下一步负责人、最近更新；已发生的话术、发送或回复记录按阶段交接；
- 源文与事实异常及其通俗说明、原文是否修复、当前阶段、受影响`CLAIM`、新材料、下游影响和重开条件；
- 未完成源资料处理事项及其资料ID、介入原因、AI知识库专员决定、已有产物、文章影响、下一步和重开条件；
- 未关闭Skill反馈及其提出来源、当前阶段、影响、关联项目问题、AI知识库专员决定和下一步；
- 外部知识异常待处理及其证据缺口；
- 已核验但尚未完成自动沉淀的候选；
- 引用率缺失；
- `01_数据说明.md`及其受管文件链接、维护责任、查看方法和最近校验是否完整，新负责人是否能据此找到并正确打开全部机器明细；
- 证据附件是否有Markdown导航入口，客户Vault内是否存在孤立非Markdown文件或脚本、缓存、临时文件；
- 最近月度问题和阻断；
- 新负责人实际使用的电脑和Windows账号是否能读取MinerU API变量，到期日和剩余天数是否明确，在线检查是否在新环境通过，API负责人/备用负责人及待解析资料是否交接；Token不得通过项目文件、聊天或邮件直接交接；
- 新负责人是否能找到项目说明、当前待办、版本与变更入口、项目资料稿、正式知识目录、Skill反馈和人工检查入口。

结论只使用：

- `可以交接`；
- `处理列明问题后可以交接`；
- `暂不能交接`。

不打分。原负责人和新负责人只确认负责人、路径、当前任务和未解决事项，不重新审批所有历史知识。

API不可用本身不阻断立项或不依赖MinerU的工作。没有待处理PDF/PPT时记录问题并继续；存在紧急PDF/PPT时，只阻断相关资料的自动提取，其他扫描、网页处理和知识工作继续。Token缺失、过期或鉴权失败由API负责人按运营手册新建/更换；429按额度或频率处理；网络超时/5xx由Codex重试两次后稍后再试；上传403检查脚本、电脑时间和预签名请求；单文件失败检查格式、大小、页数和内容；输出质量差时回看原文件、定点OCR或请运营补点名资料，不把所有故障都当作换Token。

## 7. 立即处理事项

以下问题不等待月末：

- 源文件或Obsidian路径失效；
- 正式知识出现重大事实错误；
- 单位、公式、法规正文、参数对应或来源冲突被静默修复并进入正式知识或写作输入；
- `source-normalized-english`改变原意、增加事实，或被标记为客户原话；
- 公开风险或禁用内容被误用；
- 正式知识无法追溯；
- 正式知识放在产品介绍或行业知识模块根目录，或来源类型与行业子目录不一致；
- 正式知识只有摘要、缺少`CLAIM`字段或没有逐块精确来源；
- 总览、目录、沉淀记录与实际文件互相矛盾；
- 已核验知识没有候选去向，或仍停留在`可自动沉淀`；
- 以文章是否使用、是否提交终稿作为正式知识沉淀条件；
- `尚未核对`被标记为实际使用，或多个型号/多个`CLAIM`合并为一条无法定位的使用记录；
- 文章使用了无来源企业事实；
- 最终文章引用率或正文无法匹配任务。

先隔离受影响内容并记录位置，再请求最小必要人工处理。未经授权不自行删除客户资料或历史记录。
