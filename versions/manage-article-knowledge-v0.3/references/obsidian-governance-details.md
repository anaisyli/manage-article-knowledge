## 1. 状态分离

文件至少分别记录：

- 登记状态；
- 内容导航状态；
- 提取/处理范围；
- 核验状态；
- 正式沉淀状态；
- 公开使用状态。

`已登记`不等于`已整理`，`已提取`不等于`逐字准确`，`已沉淀`不等于`可公开`。部分处理是正常状态，未处理范围不得被误标为完成。

## 2. 路径与电脑迁移

换电脑、盘符变化、Vault移动、云盘根目录变化或负责人交接时：

1. 重新确认客户源文件稳定根路径；
2. 重新确认Obsidian项目根路径；
3. 检查官网和外部链接；
4. 生成旧路径到新路径的映射；
5. 预览受影响的索引、证据、文章任务和正式知识；
6. 只修改知识库中的路径记录，不借机移动或改名客户源文件；
7. 抽样打开修改后的链接；
8. 在更新日志记录日期、旧路径、新路径、修改范围、执行人和未解决项。

不得把旧电脑绝对路径直接当作当前真实路径，也不得把桌面、下载或附件缓存作为长期权威位置。

## 3. 当前文件与历史版本

- 一个控制对象只有一个当前入口。
- 文章任务目录所在状态层是文章状态的唯一事实来源；文章总览、工作台和完成列表都是派生入口，不得各自维护不同状态。
- 同名不同内容按疑似新版本处理，不覆盖旧文件。
- 当前项目资料稿、文章写作输入、文章审核和最终文章都绑定版本。
- 被替换文章文件移入`90_归档/10_文章历史版本/`；项目运行记录统一追加到`90_归档/20_项目运行历史/项目运行账本.jsonl`，不按次新建JSON。
- 历史文件标记替代时间、替代文件和原因。
- 事实、参数、翻译、来源、公开范围或使用边界变化时，旧文章审核和写作输入同时失效。
- 没有快照、指纹或更新日志时，写`无法确认是否被修改`，不能写`未被修改`。

状态迁移采用“全部成功才完成”：先预览需更新的链接和索引，移动同一个完整文章目录，再同步文章总览、状态列表、工作台、终稿、写作输入、清理稿范围链接、集中数据和版本入口中的项目级变更，最后运行项目校验。出现断链、旧状态路径或控制文件不同步时回退为未完成，不允许一半已完成、一半仍进行中。

## 4. 控制信息

现行v0.3目录中的控制信息至少覆盖：

- `01_项目基础信息.md`：项目ID、企业、官网、稳定路径、负责人、语言和公开限制；
- `20_当前待办.md`：唯一项目级当前任务入口，记录当前人工节点、异常、处理对象、首次/最近发现时间和状态；
- `30_版本与变更入口.md`：登记实际运行的Skill版本/指纹、项目级变更和运行历史入口；当前状态只链接`20_当前待办.md`，不复制状态正文；
- `01_源文件总表.md`：唯一当前文件级索引；
- `10_项目基础情况.md`：七个模块的候选资料、缺口、已处理内容、使用限制、来源和建议补充资料；
- `10_知识候选分流.md`：结构稿中每个知识候选的主归属、关联模块、处理状态和原因；
- `20_知识沉淀记录.md`：知识从来源到正式位置的状态；
- `01_正式知识目录.md`：唯一正式知识入口，只列知识ID、主题、模块、位置和状态；
- `[项目ID]_项目资料稿.md`：正式知识、处理中材料和异常的链接地图，不复制知识正文；
- `40_正式知识沉淀记录.csv`：正式知识的新建、更新、冲突保留、归档和仅记使用记录；
- `30_知识块使用总表.md`：跨文章使用和问题记录。
- `01_待客户补充事项.md`：客户专属事实缺口的唯一长期台账，主表只记录想确认什么、为什么需要、回复前怎么处理、当前阶段、下一步由谁做和最近更新；话术、发送和回复信息只在实际发生后写入详情。
- `02_源文与事实异常台账.md`：实质异常的唯一长期台账，主表只显示通俗说明、原文是否修复、现在怎么处理、当前阶段、责任人和下一步；原文现场证据与内部技术追溯放在详情。
- `01_Skill反馈台账.md`：Skill运行问题和改进建议的唯一项目级记录，明确区分Codex自动发现、人工提出和可选的人工认可，并回链相关业务文件和问题ID。

内容运营或Agent提出“以后问客户”时，立即新建或复用问题ID，当前阶段设为`待判断要不要问`。知识库专员确认需要询问后设为`准备客户话术`，主Agent生成话术；话术经知识库专员确认并指定优化师后才能进入`等待发送`。同一事实影响新文章时只增加关联文章和大纲位置，不新建重复问题。

文章审核只保留项目级事项链接和本篇安全处理；`01_工作台/20_当前待办.md`只链接未完成事项；月度和交接从项目级台账读取。优化师发送时才登记日期与渠道。客户提供文件时，把文件登记为客户来源并按正常来源流程处理；只提供明确答复时，记录可点击回复证据。证据核验和受影响文件更新完成后才能设为`已完成`。不要创建内容重复的第二套当前台账。

逐字原文中出现`%%`、形似Wikilink的文本、HTML标签或其他Obsidian/Markdown控制语法时，必须放进带语言标记的围栏代码块（通常使用`text`）。不得把裸露的`%%`放在普通段落、引用块或表格中，否则Obsidian可能把后续内容解析成注释并显示为灰色或隐藏。

`05_数据与审核/01_检查入口/01_当前待办.md`只提供到工作台、知识沉淀、引用数据、客户事项、源文异常和Skill反馈的链接，不复制项目状态、文章列表或正式知识数量。

## 5. Markdown与标题

- 所有需要人工阅读、确认或处理的任务，都必须同时提供可读的业务标题；ID只用于稳定检索与追踪，不得让内容运营仅凭编号判断任务内容。
- 面向内容运营的提示直接说明“哪篇文章、哪份材料、哪一部分、需要确认什么”，不得暴露旧版门禁代码，也不得只写“确认某ID”或“处理第2项”。
- 标题表达真实主题和从属关系，不用固定标题数量或字数控制切片。
- 标题通常保持层级连续；原文跳级时证据层保留，派生层只在影响理解时修正并记录映射。
- 可以使用五级或六级标题；长期需要过深层级时考虑按稳定主题拆分。
- 能独立检索、复用或维护的主题使用标题；局部提示使用加粗、列表或表格。
- 避免“其他信息”“相关介绍”等模糊标题。
- 文件名使用自然业务名称；产品文件优先使用“产品名称＋型号”，不只写型号或ID。
- 七个正式知识模块必须建立模块概览；除概览外，不为了模板完整建立空知识文件或空大纲标题。
- 管理层目录、标题、字段、审核、状态、异常和处理记录默认使用中文；只允许源正文、目标语言写作输入、产品/术语、原始标题和机器CSV字段按需使用英文。

## 6. 内部链接

内部链接回答“知识在哪里、来自哪里、被哪篇文章使用”，不追求数量。

最小单向链路：

1. 项目入口或项目资料稿 → 正式知识主题；
2. 源文件总表/文章引用清单 → 原文证据或来源稿；
3. 文章任务 → 实际使用的证据、派生稿或正式知识；
4. 正式知识 → 支撑它的权威证据或来源稿；
5. 月度简报 → 集中引用率数据、待办和相关问题。

Obsidian会自动显示反向链接，不为“做双向链接”在两边机械互链。

链接规则：

- 同一项目采用一种主要写法；新项目优先可移植的相对Markdown链接；
- 已稳定使用Wikilink时可以沿用，Vault内路径使用`/`；
- Vault外客户文件记录稳定绝对根路径加相对路径，不强行写Wikilink；
- 文件改名或移动前先检查链接；
- 不把公司名、产品名或每次关键词出现都做链接；
- 同一段不重复添加相同链接；
- 不为只有模糊相关性的文件互链；
- 默认不用Obsidian块链接，精确定位优先稳定标题、页码、Sheet、时间码和证据ID；
- 链接到具体标题时，`#`后必须使用目标Markdown中真实存在的完整标题，不得只截取标题中的ID臆造短锚点；标题改名时同步更新入链。
- 需要长期稳定定位且标题可能变化时，可以在目标段落末尾设置唯一`^block-id`并使用块链接；块ID必须在目标文件中真实存在，不得重复。
- Markdown表格行不会自动生成标题锚点。候选ID、问题ID或其他表格单元格值如果没有对应标题或块ID，只链接到文件，并在链接别名或相邻正文中注明该ID；不要为了制造锚点把固定表格机械拆成大量标题。
- 链接不能替代资料ID、URL、位置和核验状态。
- 不保存指向旧电脑用户目录的Markdown链接；Vault内使用相对链接，Vault外使用稳定根路径加相对路径并在迁移时重映射。
- Vault内非Markdown文件不能只靠“维护人员知道它在”。`05_数据与审核/`中的受管机器文件从`20_知识使用与引用/01_数据说明.md`逐项链接；`04_资料与证据/`中的PDF、图片、截图、音视频和其他附件从源文件总表、内容导航或相关证据/异常页链接或嵌入。图片、原页或截图承担审核证据时，必须在具体审核位置直接嵌入或提供可点击链接。
- 不为可发现性把CSV全部复制成Markdown。CSV保存明细，Markdown保存用途、维护方法、汇总和异常。`.obsidian/`、`.git/`等内部文件不进入业务索引；脚本、缓存、临时文件及调试产物不得放进客户Vault。唯一受管例外是`90_归档/20_项目运行历史/项目运行账本.jsonl`：使用`scripts/record_project_run.py`按行追加，每项目最多一份，不在工作台复制明细。
- 每次文件移动、改名、标题变更、写作输入生成和任务关闭前运行断链检查；文件存在但标题锚点或块ID不存在也属于断链。失效链接、未替换模板变量和旧状态路径未清零时不得进入下一状态。

## 7. 同步、并发与备份

- 同一项目一次收到多篇文章时，在`01_工作台/20_当前待办.md`汇总各文章状态和依赖，不并行维护第二套任务队列。
- 文章任务目录内互不依赖的文件可以并行处理；项目级控制文件、集中CSV、统计文件、正式知识目录和同一正式知识文件必须串行写入。
- 相同来源证据按稳定来源身份只生成一份；多篇文章通过链接复用，不按文章复制证据。
- 一个项目明确一名主要写入负责人；其他人通过待办、审核或交接记录协作。
- 不同时使用两种同步服务处理同一个Vault。
- 云盘按需下载可能造成“文件存在但本地不可读”，月度和交接时检查本地可用性。
- 同步不等于备份；需要独立恢复策略。
- 多人并发、离线修改、大文件和误删恢复没有测试前，不把本地Vault描述成公司级稳定协作系统。
- 没有共享快照、同步状态和审计记录时，不把本地检查称为公司全量数据或人员绩效结论。

## 8. 来源和状态字段

每条来源至少保留：

- 资料ID；
- 人能看懂的显示名称；
- 原始文件名；
- 原始相对路径或URL；
- 精确位置；
- 语言；
- 提取方式和工具版本；
- 核验状态；
- 数据日期或获取日期；
- 内容类型；
- 公开状态；
- 关联文章。

推荐状态：

- `confirmed`；
- `pending`；
- `conflict`；
- `outdated`；
- `draft`；
- `excluded`。

AI处理结果不是独立事实来源，必须指回原文件或原页面。审核后也不删除来源标记。

## 9. 已有项目的Skill版本迁移

已有项目每次开始新一轮工作时，先比较项目版本入口、实际运行Skill和可取得的维护源指纹。不同或无法确认时先执行版本迁移，不等到月度维护，也不把任务交给内容运营。

迁移采用“预览差异后原子完成”：先列出新增或变化的控制文件、固定入口、表头、状态和校验要求，再保护业务正文，串行补齐控制结构，运行最新版校验并回归未关闭`SKFB`，最后追加项目级迁移事件。任一环节失败时保持未完成状态，不能只更新版本号或指纹。

每次更新只在版本记录中说明本次新增、变更、废弃项和转换方法；当前完整结构以项目结构、模板和校验器为准，避免维护第二份逐渐失真的总清单。详细流程读取[版本迁移与Skill自动维护](version-migration-and-skill-maintenance.md)。
