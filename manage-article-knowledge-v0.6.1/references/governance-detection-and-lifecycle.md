# 知识缺口与CUS/ANM检测协议

本协议把“发现后登记”改成每篇文章和每次来源处理都必须执行的检测动作。它不增加人工确认节点，也不限制文章写作；它只决定缺少或异常的事实进入哪个现有治理入口。

## 1. 固定检测时点

Codex在以下时点主动检测，不等待内容运营指出问题：

1. 来源首次登记、刷新、正文提取或Claim核验时，检测资料处理问题和ANM信号；
2. 文章前五层检索完成后、决定是否开展第六层新外部调研前，按标题、主问题及一级/二级主要大纲逐项检查覆盖，检测CUS、MAT、ANM和公共知识缺口并先完成登记；允许且必要的外部调研完成后复核覆盖状态，再生成`20_文章前知识审核.md`；
3. Faithfulness导入前，把全部`unsupported`先按稳定知识问题归组，复查前五层，再检测并登记写作者新引入的CUS、MAT、ANM或公共知识缺口；导入完成后只对新增`待外部调研`项执行独立知识维护，`观察中`不调研，且不回写当前文章；
4. 客户回复、新版本或新来源到达时，复核原事项，更新受影响Claim、文章资料包和状态；月度与交接只汇总现有结果，不代替前三个检测时点。
5. `outline_refresh`只在本轮六层检索完成后，根据当前大纲和新取得证据独立识别公共问题；归档`50`、旧GAP和旧版知识文件不提供问题清单、状态、结论或文章映射。本轮确认具体问题后，才查询当前缺口台账去重；仍相关且达到调研门槛的，在写作前完成本轮调研。不得以历史状态触发或跳过调研。

## 2. 统一分类顺序

对每个未覆盖、冲突或可疑事实先匹配范围确实一致的已有事项，再依次判断，命中后停止向下分类。已有Formal Claim的完整支持范围和当前`30`的真实证据优先核对，不能先把它们误登记成缺失知识：

1. **只是写作内容**：纯标题结构、过渡、CTA、修辞、不可复用观点或其他不能判断真假的内容，不登记；行业常识、一般原理、技术解释、方法判断和采购建议只要可以判断真假或跨文章复用，就不是“只是写作内容”；
2. **已有可用知识但没有进入本篇`30`**：记为`资料包覆盖遗漏`（机器分类 `package_omission`），不重复建立缺口或外部调研；必须列出已经存在、已核验且能完整覆盖该主张的具体 Formal Claim ID，并说明它为何本应进入当前 `30`。仅有相近主题、同一客户、同一材料或同一网页标题不构成覆盖。当前已审核文章保留其真实写作上下文，后续同主题任务修正检索和资料包准备。只有用户明确修订当前文章版本时，才归档旧任务、重建`30/35`并重新执行Faithfulness。
3. **当前`30`已有证据正文但主体归属不清**：仅按下述条件使用`evidence_context_gap`；来源真实冲突或客户事实需确认时仍进入ANM/CUS。
4. **本地资料存在但尚不能可靠处理**：进入MAT；处理后才发现事实或证据风险时再关联ANM；
5. **来源或事实异常**：进入ANM；需要客户补充材料或确认真实值时再关联CUS；
6. **客户专属事实缺失或需确认**：进入CUS；
7. **公共知识缺失**：进入唯一`10_知识缺口记录.csv`；核心章节或高风险事实首次直接`待外部调研`，普通公共知识首次`观察中`、第二篇不同文章出现时升级；

若当前 `30` 已经有逐字证据，但证据中的 `we/our`、品牌、产品线或其他主体归属无法从该证据块唯一确认，记为 `evidence_context_gap`。该分类必须引用当前 `30_本篇知识库资料.md` 第 1—3 节“证据正文（供Faithfulness核验）”中的逐字引文和精确行号；“主体归属说明”、来源链接、管理元数据和写作总结不算证据。当前 `30` 没有相关证据，不能用 `evidence_context_gap` 代替 MAT、ANM、CUS 或公共知识缺口；导入器会拒绝没有真实证据的归组。两类分类都只解释 unsupported 的治理去向，不改变原 Faithfulness 的 `unknown` 结果。

同一事实问题复用原`CUS ID`、`ANM ID`或`gap_key`。新增CUS、MAT、ANM或SKFB时，必须在同一事务写入真实主表行和同ID详情；正式项目页不得复制或保留`[项目ID]-...`、`DEMO-*`参考示例，也不得存在有主表无详情或有详情无主表的对象。无真实事项时只保留空主表和详情区标题。公共知识缺口按一个稳定、可由同一组证据解决的知识问题归组，`gap_topic`说明对象及缺少的关系、条件、步骤或适用边界；同一问题跨文章复用原ID。一个归组可以包含任意数量的相关Claim，不按数量拆分，但“都属于包装方法”或同一行业不足以合组。对每个黄色/红色claim_id写出其如何落入该具体问题；需要不同证据回答、不同解决范围或不同责任边界时拆组。文章版本递增不增加出现文章数。

`已解决`只表示该`gap_topic`明确登记的范围已由可回读RES和正式公共Claim回答，不表示整个宽泛主题或此后文章的黄色主张已解决。新主张先核对已有Claim的对象、关系、条件及适用范围：已覆盖但漏进本篇`30`的，记录`资料包覆盖遗漏`及具体Formal Claim ID，不把原Faithfulness黄色改绿；同一稳定问题仍有未覆盖范围的，写明新边界并重开为`部分解决`（已有RES仅覆盖一部分）或`待外部调研`（原证据已失效）；不同知识问题另建gap_key。不能为了保留已解决状态将多个新问题附加到原ID。`已关闭`也必须先记录重开依据。部分解决须保留已覆盖范围和待补范围，待全部必要范围得到证据后才可改`已解决`；没有新证据不因文章再出现而自动关闭或解决。历史文章的Faithfulness判断和版本不追溯修改。


### `writing_only`硬边界

`writing_only`是“不是知识问题”的排除类，不是“本篇暂时不想处理”的兜底类。只有一组内全部内容同时满足以下条件才可使用：

- 不包含可以判断真假的事实、因果、比较、适用条件或方法结论；
- 不能形成跨文章复用的行业、技术、采购或合规知识；
- 不涉及客户事实、技术、方法、法规/标准、认证、安全/限值、检测有效性、采购选型或动态事实；
- 能具体说明为什么它只承担结构、过渡、CTA、修辞或一次性观点作用。

任一条件不满足就继续按MAT、ANM、CUS、公共知识缺口或资料包覆盖遗漏分类。事实内容与纯写作内容混在同一组时必须拆组，不能用组内少量CTA或观点把整组事实排除。法规、标准、认证、安全、限值、检测有效性、采购选型和动态事实只要在unsupported原文中形成实质判断，禁止归为`writing_only`。

## 3. CUS主动检测

CUS不是“发现明显缺资料后才建立”的例外事项。每篇文章在文章前审核时都必须固定检查六类客户专属事实：客户能力、规格、认证、案例、商业条件和公开授权。检测结果必须写入`20_文章前知识审核.md`的CUS行；没有触发时也要写明六类均已检查及所查来源。这里的“固定检查”是治理防漏动作，不代表六类都必须出现在文章中，也不构成文章发布分数门槛。

Faithfulness比例不触发CUS复核，也不设置任何分数线。CUS、ANM、MAT、公共知识缺口或资料包覆盖遗漏只根据具体“尚未确认”或“明确冲突”主张的对象、事实类型、来源状态和风险信号建立；总分高低不能代替逐条语义归组。

### 3.1 检测对象

对下列客户专属事实逐项提问“当前证据能否唯一回答，且公开/使用范围是否明确”：

- 企业身份、组织关系、联系人、地点和市场/服务区域；
- 客户产品或型号的规格、性能、产能、认证、兼容性和可用范围；
- 客户案例、客户名单、效果、承诺、价格、MOQ、交付和售后政策；
- 未公开信息是否可以写、客户原话的真实含义、客户提供材料之间无法自行决定的真实值；
- 文章标题、主问题或一级/二级章节不可缺少的其他客户事实。

### 3.2 排除检查

建立CUS前必须完成并记录以下排除：

- 已有Formal Claim、客户源资料索引、客户官网、已确认关系的客户关联网站和既有客户回复是否已回答；
- 是否只是本地资料未处理；是则MAT，不先问客户；
- 是否属于可公开调研的行业知识；是则公共知识缺口，不用外部资料证明客户能力；
- 是否是来源冲突、原文错误或危险外推；是则ANM；
- 是否可以删除、缩小或中性改写且不再需要该客户事实；是则不建CUS，并在文章审核写明处理。

排除后仍需客户提供材料、确认真实值或授权公开，才复用或建立CUS。CUS详情至少保存：稳定问题、受影响文章/大纲/Claim、已检查来源和未命中依据、为什么必须由客户回答、回复前安全处理、下一责任人、回复证据、核验结果、下游更新和重开条件。

### 3.3 生命周期

`待判断要不要问 → 无需询问`，或`待判断要不要问 → 准备客户话术 → 等待发送 → 等待客户回复 → 收到回复，待核实 → 已完成`。只有回复身份、来源和适用范围核验完成，并更新受影响Claim、文章审核、`30/35`和当前待办后，才能`已完成`。新证据冲突、回复范围改变或相关文章再次依赖时复用原ID并重开。

## 4. ANM主动检测

### 4.1 检测信号

来源登记、提取、Claim核验、文章前审核和Faithfulness归组时，逐项检查：

- 文件加密、损坏、缺页、版本不明，或来源无法打开和精确定位；
- 漏行、乱序、跨栏串行、表格字段错位、标题层级或父子附件关系错误；
- 数字、型号、单位、小数点、公式、脚注或不同版本之间不一致；
- OCR相似字符、低置信文字、截图/图表的空间关系被当作普通文本；
- 原文与规范化值、翻译、结构化值或Claim正文不一致或含义不唯一；
- 两个权威来源冲突、内容部分重合但版本关系未确认、旧事实仍被当作当前事实；
- 残缺证据被写成完整结论、来源边界被扩大、公共资料被外推成客户事实；
- 最终文章新增高风险或客户专属结论，且与现有证据冲突或发生危险外推。

`unsupported`本身不是ANM证据。只有完成位置核对或来源比对后出现上述信号，才能登记ANM。单纯“资料存在但无法提取/需要工具决定”先进入MAT；处理后确认有事实风险时关联ANM。

### 4.2 自动修复与登记边界

能由原始证据和固定规则唯一修复的链接、编码、确定性拼写或格式问题自动修复并留处理记录，不建立长期ANM。会改变事实含义、公开使用、Claim、文章资料包或版本选择，或者无法唯一决定的异常，必须复用或建立ANM。

ANM详情必须保存最小原文现场、资料名称、可点击来源或稳定路径、精确位置、必要上下文、证据完整性、受影响Claim/文章、当前限制和下一步。视觉或结构问题链接原页或截图；不得把残缺文本改写成完整句。客户禁止保存正文时只保留不含敏感正文的定位、禁用依据和处理状态。

### 4.3 生命周期

`待判断 → 等待材料 / 处理中 → 部分解决 → 已解决`，或在风险已隔离但原文没有修复时进入`已完成处置（原文未修复）`。`已解决`要求真实值或事实关系已确定且下游完成更新；`已完成处置（原文未修复）`要求限制、替代证据、历史影响和重开条件已记录。新版本、新材料或同类冲突命中重开条件时复用原ID。

## 5. 文章前固定落盘

`20_文章前知识审核.md`必须包含大纲覆盖表、CUS/ANM结果汇总表和逐项核对明细表。固定字段与来源模板见[项目结构与模板](project-structure-and-templates.md)中的15和20，不临时创造同义表头。

新请求按`GC-1`在15的“CUS / ANM来源核验记录”保存逐类别回源记录，20逐项引用其GC-ID。15记录只负责定位：核验器必须回读受管原件、当前官网正文凭证或RES原文，并核对身份、位置、当前运行和SHA-256；禁止用`本轮原件核验现场.md`等任务自建笔记证明自己的引文。需求原文只能说明某类事实不适用，不能证明事实已确认；每类分别写适用边界，不能机械复用无关排除理由。缺记录或可修复映射由知识库继续补齐，不转交人工填写；真正缺不可替代原件或存在事实冲突时才按原治理规则分流。历史无GC-1标记保持原合法来源兼容，未知非空协议不能降级。

### 大纲知识覆盖检查

| 大纲章节 | 知识问题 | 覆盖状态 | 已有证据/Claim | 缺口或治理事项 | 本篇处理 |
|---|---|---|---|---|---|

`覆盖状态`只用`已覆盖 / 部分覆盖 / 未覆盖 / 无需事实支持`。标题、主问题及一级/二级主要章节必须逐项出现；一个章节有多个独立事实问题时分行。`部分覆盖/未覆盖`必须链接既有或新建的`gap_key`、CUS、MAT、ANM，或者写`不构成知识问题：`并说明它只是结构、过渡、CTA或不可复用内容。不能以“可以合理扩写”代替覆盖判断。

### CUS / ANM检测结果

| 检测对象 | 已检查信号与来源 | 分类结论 | 事项与证据入口 | 本篇处理 |
|---|---|---|---|---|
| CUS候选检测 | 客户专属事实及六层检索排除结果 | 未触发 / 已复用 / 已登记 | 无 / CUS入口 | 省略、缩小、等待或按已确认事实使用 |
| ANM异常检测 | 版本、定位、提取、数值、单位、OCR、冲突和外推信号 | 未触发 / 自动修复并留痕 / 已复用 / 已登记 | 无 / 处理记录 / ANM证据包 | 排除、限制、等待或按核验结果使用 |

两行都必须填写具体检查结果；不得只写“已检查”或“无异常”。没有触发时也应写已检查的主要来源和信号范围。

## 6. Faithfulness后的归组

所有语义状态为`unknown`或`contradicted`的claim_id必须恰好进入一个归组，不能遗漏或重复；机器兼容字段中两者仍合称`unsupported`，但人读治理不得混淆黄色“尚未确认”和红色“明确冲突”。归组优先复用文章前的缺口或治理事项；项目已有经核验的客户正式知识但漏进`30`时才归为资料包覆盖遗漏，并写明具体 Formal Claim ID、核验范围和遗漏位置；若 `30` 有逐字证据但主体归属仍不唯一，才归为资料包证据归属不清，并写明 `30` 证据正文行号和逐字引文。没有 `30` 证据时不得使用后一分类。行业常识、一般原理、选型、方法和运营判断必须按稳定知识问题进入公共知识缺口，不能批量塞入资料包覆盖遗漏。写作者新增的稳定客户事实进入CUS，未处理本地资料进入MAT，来源异常进入ANM；只有通过本协议`writing_only`硬边界的纯写作内容才记排除理由。Codex把归组结果写成符合Faithfulness交接合同的处置JSON，并逐组声明语义状态、是否含事实判断、是否可跨文章复用、知识领域和排除理由；导入器验证全部黄色/红色claim均恰好出现一次、`writing_only`声明互相一致，并核对公共缺口或CUS/MAT/ANM入口已经真实存在，缺失时拒绝完成导入。

`50_文章知识使用与Faithfulness记录.md`按归组把`分类、分类依据、关联事项/入口、当前处理、下一步`分开显示，不再把入口、处理和状态挤在同一格，也不再把全部unsupported笼统写成“单篇观察，无后续动作”。处置JSON中的公共缺口组必须有一个具体的`scope_review.knowledge_question`及覆盖每个claim_id的`claim_matches`，逐条说明为何属于同一稳定问题；品牌、结构、材料、验证、物流或采购等多个维度只要由同一个方法问题和同一组证据共同回答，就保持一组。不得按关键词域数量或Claim数量机械拆分；只有证据问题、适用边界或解决范围不同才拆组。导入器校验映射完整性和终态引用，Codex负责逐Claim语义复核。已解决/已关闭的ID不能作为黄色/红色主张的`existing_gap`直接导入。Faithfulness不改变文章是否可以交付，也不得从终稿反向建立Formal Claim。


### 审核过程记录限制（audit_process_limitation）

逐条区分真实证据缺口、语义分歧与审核记录缺陷，不把unknown本身登记为ANM。schema 1.1可使用`audit_process_limitation`，该类别只保留黄色结果、说明记录限制，不签发事实支持，也不据此自动创建GAP/CUS/ANM。适用范围：两轮原始语义均为entailed，最终unknown，收敛原因仅为组件记录校验问题。首轮unknown、双轮分歧、真实missing、冲突或无来源一律不得使用此类别；混合组必须拆开。

沿用处置group的全部固定字段及fact_check；追加固定模板：

```json
"process_review": {
  "claim_records": {
    "C001": {
```
