# 知识库维护入口与清单

## 目的

本入口用于整理已经建立的 v0.6 项目，不替代写作、终稿接收、Faithfulness 导入、月度审核或交接流程。它把可确定的结构修复自动落盘，把需要证据或人工决定的事项集中记录，避免问题散落在对话中。

## 两个可直接使用的指令

首次整理：

> 整理并维护这个知识库：先检查 Skill 版本、维护设置和项目结构，再读取现有知识库维护清单；先按当前 Skill 统一整理能够确定的固定模板字段/小节、稳定入口与导航、台账主表/详情配对、占位内容和覆盖视图，保留真实内容，不自动删除兼容历史页；然后逐项按当前 Skill 规则和当前项目事实重新核验。能根据现有文件、索引和固定合同确定的直接修复；旧事项若因明确的 Skill 规则更新已不再构成问题，保留历史记录，写明规则变更依据和本次验证结果后关闭，不要继续列为开放错误，也不要为迎合旧规则改写项目；不能确定的不要猜，继续保留开放并更新还缺什么、下一步和最近检查；新问题使用新的 KMR 编号登记。最后更新清单、覆盖视图、运行记录和审核摘要，并汇总已自动修复、因规则更新关闭、待补证据、待人工决定和仍存在的错误。

人工补充后继续：

> 根据知识库维护清单和我刚补充的判断/证据，继续整理这个知识库：先按当前 Skill 统一检查并修复能够唯一判断的固定模板、入口、导航、台账配对、占位内容和覆盖视图，再逐项重新核验所有开放事项；能关闭的关闭，能修复的修复；旧事项若因明确的 Skill 规则更新已不再构成问题，保留历史记录，写明规则变更依据和本次验证结果后关闭，不要为旧规则修改项目；仍不能确定的保留开放并说明下一步；最后更新清单、覆盖视图、运行记录和审核摘要。

两句可以合并为一次请求；任何阶段都不得删除历史记录或把未知事项直接标记为已解决。重复运行必须维护同一张连续清单：复用同一根因的KMR，更新状态、处理、缺项、责任人、关闭依据和最近检查；只有新根因才分配新编号。

## 固定落盘位置与最小模板

项目目录固定建立：

`05_数据与审核/30_异常与待决定/90_知识库维护/01_知识库维护清单.md`

```markdown
# 知识库维护清单

- 项目ID：
- 最近检查：
- 当前Skill版本/指纹：
- 最近一次维护运行：

| 维护事项ID | 问题 | 涉及文件 | 类型 | 当前状态 | Skill已做处理 | 还缺什么 | 下一步责任人 | 关闭条件 | 最近检查 |
|---|---|---|---|---|---|---|---|---|---|
| KMR-001 |  |  | 自动修复/待补证据/待人工决定 | 待处理 |  |  |  |  |  |
```

状态只能使用：`待处理`、`已自动修复`、`等待补证据`、`等待人工决定`、`已关闭`。维护事项 ID 是项目内单层流水号，不是 GAP、CUS、ANM 或 SKFB 编号。

### 旧事项因规则更新而不再适用

当前Skill明确改变了判断规则后，旧KMR可能不再构成错误。此时不得修改项目去迎合旧规则，也不得删除该KMR。只有同时满足以下条件时才能确定性关闭：当前安装Skill或其更新记录明确说明原条件已被取消、改为正常状态或改成兼容提醒；按当前规则重新校验后该事项不再产生当前错误；没有另一个仍有效的事实、证据、身份或结构问题被同一旧描述遮住。关闭时把状态改为`已关闭`，在“Skill已做处理”写明“规则更新后不再适用”、对应变更ID或规则位置和本次验证结果；“还缺什么”写`无`，并更新最近检查。它只从开放事项和“仍存在的错误”中移除，原问题、涉及文件和历史处理记录继续保留。

仅仅因为某次校验没有输出、文件暂时未被扫描、版本号变化或代码已经修改，不能自动关闭。若当前规则是否真的取消旧要求仍不明确，继续保持开放并转为`等待人工决定`；若规则虽然变化但项目仍违反当前规则，则按当前问题更新原KMR或在根因不同的情况下新建KMR。

## 自动与人工边界

可自动处理：固定字段、目录和表格结构、稳定入口与导航、主表/详情配对、占位清理、唯一来源引用、已有严格翻译的 30/35 复制、覆盖视图和运行记录。普通文章或终稿流程只处理当前触及文件；知识库维护、月度审核和交接审核开始前，才按当前Skill统一检查项目内这些确定性结构。不能确定的 Claim 语义、适用范围、原文证据、多个来源候选、英文严格翻译、客户事实、路径归属和业务决定必须进入清单，不得猜测。兼容历史页不因新规则自动删除。测试或模板验证只能使用临时项目目录；不得把测试Claim、RES、GAP、CUS、ANM、SKFB、处置或手工审核JSON写入真实客户项目。

当前规则不再生成三个旧式目录页：`03_正式知识/00_正式知识目录.md`、`03_正式知识/10_客户知识/00_客户知识目录.md`和`03_正式知识/20_外部公共知识/00_外部公共知识目录.md`。既有项目中这些文件属于兼容历史入口，不要求继续维护，也不因存在而报错；维护运行不得自动删除它们或为了新规则改写项目。只有用户明确授权迁移具体项目时，才可先检查反向链接并移除旧页。正式知识的唯一人工入口改为`01_工作台/10_项目基础信息.md#七个业务模块入口`，动态状态只读取覆盖视图。

## 审核与交接

月度审核和交接审核必须读取清单。正式生成月报前，以及交接交付前、接收后，先执行一次当前Skill下的确定性结构整理，再按整理后的结果汇总；整理只处理固定模板、稳定入口、导航、台账配对、占位内容和覆盖视图，并把自动修复与仍待人工判断的内容写入对应审核。存在清单时按状态汇总；没有清单但校验发现问题时，报告仍须直接列出问题并注明“项目尚未建立维护清单”，不能写成无问题。交接包包含清单原文件和开放事项摘要；接收方先确认责任人、证据入口和关闭条件，再运行第二阶段指令。月度/交接不会重算历史 Faithfulness、改写历史文章、重命名旧 GAP、删除兼容历史页或凭空补证据。

## 版本门禁

维护入口以及所有会写入既有项目的管理动作，必须在读取业务文件前运行 `scripts/check_skill_update.py --project <Obsidian项目路径>`；写作桥接 `prepare`/`finalize` 同样是硬门禁。只有只读咨询不触发版本检查。


### 历史程序类ANM的规则复核

维护时立即复核仅因旧分类规则、导入结构或审核记录限制而建立的ANM，无须等待文章重写。按当前语义问题与真实来源重新核对逐条claim关联；知识域数量本身不能否定公共缺口，集合值主张不得为了导入临时重拆。固定复核字段：`原依据`、`当前规则`、`文章/版本/claim_id`、`实际来源与边界`、`程序原因是否失效`、`真实知识事项是否仍待处理`、`后续入口`、`关闭/重开条件`。只关闭已失效的程序依据，不把旧黄色改绿、不改历史分数/50/哈希，也不把未完成的GAP/CUS事项随ANM一起关闭。复核说明更新既有同ID详情及主表，不新增任意说明文件。找不到文章归档去向是独立维护事项，不能作为保留失效ANM分类的理由。
