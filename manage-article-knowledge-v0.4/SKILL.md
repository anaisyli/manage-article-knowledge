# 文章知识库运营管家 v0.4

## 目标

以文章需求驱动客户知识库持续增长。项目初始化只建立可追溯的文件总表和内容导航，不为形式上的完整而全量提取所有历史资料。每篇文章优先复用正式知识，再处理尚未提取的客户资料，再复用已有外部调研，最后才开展新调研。

让人工只介入确实需要业务判断的位置。正常处理、归类、翻译、派生、沉淀、引用清单、知识块使用记录和月度汇总由Codex自动完成。

固定四层职责，任何文件不得越权：源文件级清理稿负责保真和复用；文章写作输入负责回到证据层，筛选已批准的完整来源段落并按大纲重排；正式知识是按稳定实体或主题组织的“已核验事实、规则、适用范围与逐块来源登记簿”，在资料整理、CLAIM候选校验和文章前知识审核完成后自动沉淀，负责检索、边界判断和追溯；文章终稿只核对实际使用的`CLAIM`并更新使用记录。知识是否被文章使用、文章是否已经达到可写状态，都不影响来源合格CLAIM是否应当沉淀。文章写作输入、文章摘要、AI总结和最终文章都不能成为正式知识的事实来源。

## 不可突破的边界

- 保持客户源文件原封不动；不移动、不重命名、不覆盖、不删除。
- 客户源文件与客户官网都是可信的客户一手来源；源文件默认可以在人工确认的范围内提取，无需先由官网或外部来源佐证。
- 把原文证据、翻译、结构化派生、分析和正式知识分层保存。
- 不把摘要、润色、翻译、OCR不确定结果或AI推断标记为客户原话。
- 客户明确禁止使用的正文不进入Obsidian处理层、写作输入或正式知识；只保留不含敏感正文的排除记录。
- 不把外部行业知识写成企业能力、产品参数、案例或服务承诺。
- 不把最终文章本身当作企业事实的原始来源。
- 不根据文本相似度自行推算单篇引用率；只记录内容运营提供的值。
- 不生成知识库完备度分数、六维评分或月度知识块绩效分。
- 不设置“浅扫描/深扫描”选项；项目初始化统一执行规定扫描。
- 不把外部候选链接逐页交给运营批准；只在访问失败、来源冲突或事实风险时要求人工处理。
- 开始新的外部调研前必须按文章或批次向用户说明真实缺口、调研范围和使用边界；正常公开调研是非阻塞通知，不逐链接等待批准。
- 不设置独立的派生处理确认或正式知识沉淀确认。
- 面向内容运营的目录、管理字段、审核、状态、异常和处理记录默认使用中文；只在源正文、目标语言文章输入、专有名词和机器CSV字段中按需保留英文。
- 知识库生成并维护的CSV统一使用`UTF-8 with BOM`；Python写入使用`encoding="utf-8-sig", newline=""`，读取使用`encoding="utf-8-sig", newline=""`，分隔符保持英文逗号并使用标准CSV引号转义。不得写成Excel按本地ANSI/GBK猜测的无BOM UTF-8，也不得为解决乱码改变固定列名或字段值。客户提供的原始CSV保持原样，只在生成受管派生CSV时执行本规则。
- 客户Obsidian项目内的非Markdown文件不得成为孤立文件。`05_数据与审核/`中的受管CSV及其他机器文件必须逐项登记到`20_知识使用与引用/01_数据说明.md`，保留可点击文件链接、用途、维护责任、人工编辑权限、更新触发、查看方式、编码/格式和最近校验；CSV继续作为机器明细唯一事实源，Markdown只保存说明、汇总和异常，不复制全部数据行。`04_资料与证据/`中的PDF、图片、截图及其他证据附件必须由源文件总表、内容导航或相关证据/异常页链接或嵌入。脚本、缓存和临时文件不得进入客户项目目录；唯一例外是`90_归档/20_项目运行历史/项目运行账本.jsonl`，它是可持续追加的内部审计记录，不属于临时运行产物。
- 不按文章复制运营提交稿、来源证据或清理稿；一份来源同一版本只有一个项目级当前稿。
- 不让内容运营承担视频/音频的字幕提取、音轨提取、转写、标题核验或准确性审核。初始化只登记媒体身份和可可靠取得的基础信息；由AI知识库专员在月度维护或文章即时需求中决定是否处理、处理范围和方法。
- 不依据文件名或语义相似度自动合并、删除、覆盖或替换客户资料。自动重复判定只使用内容指纹完全相同；相似、同名不同内容和疑似版本只提示复核。
- 不把内容运营提出的“以后问客户”当成客户已确认，也不把它只留在即将归档的文章审核中；同一客户事实只在项目级待客户补充事项中维护一份当前记录。
- 不在`30_版本与变更入口.md`复制当前项目状态。`01_工作台/20_当前待办.md`是项目当前节点、文章状态、阻塞和下一步的唯一事实源；版本入口只登记实际运行的Skill版本/指纹、链接当前待办并追加项目级变更历史。
- 不把Skill缺陷、规则歧义、模板可用性、校验遗漏或流程改进建议写入客户补充事项或源文与事实异常台账。此类问题使用独立`Skill反馈台账`和`SKFB`编号；项目客户补充、事实异常和源资料处理分别使用`CUS`、`ANM`和`MAT`编号，彼此只做关联。
- 不把Skill问题交给内容运营判断、修复或关闭。Codex自动完成复现、执行性维护、回归和受影响项目验证；涉及多个合理规则方向、产品方向或无法从证据确定的业务选择时，由人工AI知识库专员或维护负责人决定。
- 固定区分人工岗位与自动执行方：`AI知识库专员 / 内容运营 / 维护负责人 / 审核人`只表示真实人工岗位；`manage-article-knowledge Skill / Codex主Agent / 资料处理Agent / 调研Agent / 审核Agent`只表示自动执行方。任何控制文件都分别记录`业务决定人 / 自动执行方 / 独立审核方`，不得使用“AI知识库专员自动处理”或“Skill人工确认”等混合主体。
- 所有项目默认允许把任务所需最小范围的客户资料上传到团队已批准的第三方技术解析服务；当前默认批准范围包括本Skill配置的MinerU官方API。该授权只用于技术解析，不等于允许对外公开、模型训练、任意第三方转发或把企业事实写入公开文章。只有项目存在明确禁止或服务不在批准清单时才暂停并升级，不得逐项目重复询问默认授权。
- 不把写作输入做成知识点卡、资料摘要或AI综合结论。可以按大纲筛选和重排来源内容，但选中的段落、连续语义块、表格和公式必须完整保留；不得以更短的改写替代。
- 不把正式知识做成自由摘要、整份清理稿副本或多来源混写文章。每个正式知识文件必须由可独立核验的`CLAIM`块组成，并登记知识ID、稳定实体/主题键、知识类型、已核验事实或规则、适用范围、不可外推范围、直接来源、精确位置、数据日期和使用前复核条件。
- 普通`[[内部链接]]`只提供导航和追溯，不会自动把被链接正文送入下一次大纲或写作。链接到具体标题或块时，`#`后的标题或`^block-id`必须在目标Markdown中真实存在；表格单元格中的ID不是锚点，不得据此臆造短锚点。再次提交大纲时，先用正式知识的`CLAIM`块检索和判断边界，再沿来源与精确位置回到清理稿或原文证据，提取完整语义块生成写作输入。

## 固定项目/文章节点

只设置以下六个项目/文章节点；节点3必做但默认为后台自动检查，不是固定人工确认口：

1. **项目基础信息**：人工填写项目中文名称、项目英文名称、运营组、内容运营负责人、官网、行业、客户源文件材料路径和Obsidian项目路径；行业缺省时由Codex根据官网补充。
2. **文章需求**：人工提供本周文章的关键词、标题、大纲和其他要求。
3. **待提交资料与就绪检查**：Codex先复用已有合格稿，再对所需PDF/PPT自动调用MinerU、对可访问网页自动提取并核验。全部就绪时只在后台更新检查文件，不要求内容运营查看或确认；只有自动取得失败、质量不合格或需要授权时，才点名具体文件/网页并请运营把原样生成的`.md`直接发给Codex。稿件进入Obsidian后仍只归为`Codex提取`或`运营提交`。
4. **提取范围与处理样本**：Codex依据真实文档结构列出文件、章节、页码/PPT页、网站交互状态、嵌入附件、图片、字段、排除项、各类复杂结构的代表处理样本、预计真实缺口及条件式外部调研范围；人工按文章和范围版本一次确认范围、样本及`若本地处理后缺口仍存在是否开展外部调研`。Skill不得替代人工确认。
5. **文章前知识审核**：Codex生成审核；人工只处理缺口、冲突、公开风险或客户事实问题，并确认能否进入写作。
6. **写作后提交**：人工提交最终文章标题、完整正文和该篇文章引用率；此提交自动触发`CLAIM`级使用核对、引用率及相关数据更新，不触发常规知识沉淀。

另在**每月底**和**项目更换负责人**时执行项目审核。月度与交接审核均不打分。

每台需要运行MinerU的电脑首次部署或更换Token时，由API负责人双击`scripts/initialize_mineru.cmd`，隐藏输入Token和到期日，并以脚本完成`probe`及无敏感信息`health-check`。同一Token当月已有完整成功记录时直接复用；新环境正常应完成Token、上传、解析和下载验证。若本机配置成功但MinerU网关或外部网络临时不可达，初始化器标记`在线验证待自动重试`并完成本机部署，不要求重输或更换Token；Codex在实际需要时自动重试，确定性鉴权、过期或请求错误才阻止部署。内容运营不配置变量、不运行脚本或命令，日常提交文章需求后由Codex自动调用MinerU。进入新项目、当前Codex进程首次需要MinerU、Token更换后、每月维护和负责人交接时，Codex先运行`scripts/run_mineru.py probe`；当月尚无成功记录或出现鉴权疑问时运行`health-check`。同一Windows用户本月已通过时复用本机状态，不为不同客户项目重复消耗测试额度。临时失败写入最近失败记录，不得覆盖最近真实成功。状态缓存不可读写时必须降级到可写临时目录，不得阻断API调用，并把本机状态、Token、Codex网络权限、外部网络、上传、解析、下载和归档错误分层报告。出现`WinError 10013`或同类套接字权限错误时，Codex必须识别为沙箱网络权限，立即以`run_mineru.py`最小命令前缀申请沙箱外重试；不得记为MinerU服务失败、重复普通网络重试或要求内容运营改用手工MinerU。授权弹窗只由管理员处理，内容运营不判断技术权限。距到期7天时提醒API负责人一次，距到期1天时再次提醒并避免开启大批量解析；其他时间不提醒，已过期时停止自动调用。Token及其完整指纹不写入客户项目、Skill、对话或运行账本；每台电脑仅在当前用户本地保存一份不含客户资料的API检查状态。

不得把正常自动步骤拆成新的人工关口。发现异常时，把异常合并到最近的固定节点；只有无法安全继续时才临时请求具体材料或决定。

人工决定只对当次明确展示的节点、文章ID、范围版本、范围ID和样本组ID有效。`可以继续`、`继续处理`等笼统回复只有在同一轮已经完整展示当前待确认对象时才可作为该节点决定，不得继承为后续节点授权，也不得由Skill转写成用户未明确批准的范围、样本、外部调研或审核结论。

同一项目一次提交多篇文章时，允许把同类人工节点集中展示，但必须按文章ID和具体范围分别记录确认结果；不得用一次笼统确认替代各文章的范围、审核、终稿或引用率记录。

## 核心工作流

执行任何阶段前，先读取[内部运行清单](references/runtime-execution-checklist.md)中对应小节，在后台完成开始前检查、现有Agent自动调度、结束前检查和机器校验；该清单不得复制到客户项目，也不形成新的运营表单或人工确认节点。能够由现有证据和固定规则唯一修复的结构、链接、编码、状态同步和确定性提取错误，由Codex自动修复并重检；不得把机器可修复问题转交内容运营。清单只规定执行顺序，不替代本文件和专项参考中的业务规则。

### 0. 进入已有项目并自动迁移版本

每次对已有项目开展文章、资料、维护或交接工作前，先读取`01_工作台/30_版本与变更入口.md`中的Skill版本、版本日期和指纹，并计算本次实际运行`SKILL.md`的SHA-256。版本、指纹、固定控制结构或校验基线任一不一致或无法确认时，先执行版本迁移事务，不把迁移推迟到月底，也不要求内容运营处理。

版本迁移固定执行：`识别实际运行副本 → 对照维护源或发布基线 → 预览结构与字段差异 → 保护业务正文和证据 → 补齐或转换控制结构 → 运行当前版本校验 → 回归未关闭SKFB → 记录项目级迁移事件`。迁移只修改当前版本要求的控制文件、入口、固定表头、合法状态和必要索引，不借机改写正式知识、客户原文、证据或已完成文章正文。任何一步失败时保持`迁移未完成`并列出剩余项，不得声称项目已升级。

每次新版Skill应用到项目时，自动读取全部未关闭`SKFB`：先按原复现依据检查新版规则、模板和校验器是否已经覆盖，再运行对应回归及全项目校验。已修复且项目验证通过的反馈自动记录修复版本、证据和影响范围并进入`已关闭`；源版已修复但项目尚未验证时进入`已修复，待项目验证`；仍可复现则保持未关闭并自动进入维护，不找内容运营确认。

读取[版本迁移与Skill自动维护](references/version-migration-and-skill-maintenance.md)和[Obsidian治理细则](references/obsidian-governance-details.md)。

### 1. 初始化项目

收到初始化输入后立即开始，不再询问是否扫描或选择扫描深度。固定字段为：

- 项目中文名称；
- 项目英文名称；
- 运营组；
- 内容运营负责人；
- 官网；
- 行业；
- 客户源文件材料路径；
- Obsidian项目路径。

除行业外，字段缺失时明确要求补充，不自行编造。行业未填写时，根据官网的公司介绍、产品和应用场景自动填写，并标记`Codex根据官网推定`；官网不足以判断时写`未确认`并说明原因，不为此增加独立审批节点。

执行只读文件扫描，记录文件身份、相对路径、格式、大小、修改时间、指纹、重复/版本关系、主要语言、页数、幻灯片数、视频时长、压缩包结构、可读性、处理状态、可能归属模块和使用限制或异常。对ZIP、RAR、7z及Office容器先只读列目录，建立父子资料清单；只在系统临时目录安全解压需要处理的子文件，不改动客户目录。压缩包旁已有解压目录时，逐文件比较包内路径、外部路径和指纹，区分完整解压副本、部分解压、解压后修改和外部新增。视频/音频只登记原文件名、格式、时长、指纹、`仅据文件名初判`和疑似配套文字稿，不要求内容运营处理。无法自动处理、需要专员判断的视频/压缩资料、疑似配套稿和不确定版本关系统一进入`03_源资料处理待办.md`并分配`MAT`编号。图片按装饰图、附件图标、信息截图和复杂图示分类；流程图、复杂表格、图表或关键截图即使没有连续文字也必须登记和判断，纯装饰图只记录排除结论。为可能支持知识库或文章的资料建立页面、幻灯片或章节级内容导航，并自动生成不打分的《项目基础情况》，按七个模块说明候选资料、当前缺口、已处理内容、使用限制、来源和建议补充资料；初始化不全量归档正文，但必须读取可读文件的最小结构和语义摘要。导航的“内容说明”必须写页面、章节、表区、字段或时间段的实际主题；尚未提取正文时，只把“待文章定向提取”等文字放在“提取状态”或“定位限制”，不能代替内容说明。导航数据行不得使用未替换变量；无法可靠判断时写真实失败原因并建立MAT。

Word内图片另外保留父资料ID、标题路径、附近文字/题注、内部媒体路径或关系ID及载荷指纹。同载荷多处出现时保留全部位置，只复用一套派生处理；图文共同表意时不得只留文字；附件图标按嵌入子文件登记；无法可靠导出或判断时进入`MAT`。

读取[项目与知识结构](references/project-and-knowledge-structure.md)、[来源扫描与提取规则](references/source-processing-rules.md)和[Obsidian治理细则](references/obsidian-governance-details.md)。

### 2. 接收文章需求并查找资料

建立文章任务后，按固定顺序检索：

1. `02_正式知识/`；
2. 客户源文件和客户官网中尚未提取的相关部分；
3. 过去已经调研但尚未完成核验或尚待迁移的外部知识；
4. 仍有真实缺口时开展新的外部调研。

一次收到同一项目多篇文章需求时，为每篇分配独立文章ID并建立独立任务目录，不合并大纲、审核、写作输入、终稿或引用率。把批次内各文章的当前节点、依赖、阻塞和下一步汇总到`01_工作台/20_当前待办.md`，不另建第二套任务队列。

项目初始化、流程回退或重开、Skill版本迁移、文章完成或重开、正式知识首次批量沉淀或结构迁移、项目级台账结构迁移、负责人或稳定路径变化属于项目级变更。完成这些事务时，在`30_版本与变更入口.md`追加日期、变更、依据、执行人、关联对象和影响范围；普通单条客户事项或异常阶段变化只更新各自台账和当前待办，不写成第二套项目流水。版本入口的`当前状态`只链接`20_当前待办.md`，不得写自由文本状态。

相同源文件、网页、提取稿和项目级证据只处理一次，由多篇文章链接复用。互不依赖的文章局部工作可以并行；有先后依赖的步骤按依赖顺序执行；同一项目级控制文件、集中数据文件或正式知识文件必须串行写入。一篇文章受阻时，不阻塞没有共享依赖的其他文章。

大纲只用于判断相关性和需求覆盖，不作为源文件提取大纲。正式知识命中只代表“可进入候选”，不代表其摘要文字可直接进入写作输入；必须沿每个命中`CLAIM`的来源和精确位置返回证据层，选取完整段落、连续语义块、表格或公式。读取[文章工作流](references/article-workflow.md)和[调研与知识沉淀](references/knowledge-research-and-deposition.md)。

### 3. 确认待提交资料齐备

先检查当前文章实际需要的输入：

- 当前文章范围内的每份PDF/PPT是否已有同版本合格Markdown稿；没有时使用`scripts/run_mineru.py extract`从环境变量`MINERU_API_TOKEN`读取凭证并调用MinerU官方API，在系统临时目录完成上传、轮询、下载和基础检查，记录API版本、实际参数、页数和原文件指纹；不得显示、回传或写入Token；团队批准的MinerU技术解析默认授权适用于所有项目，只有项目明确禁止时才停止；
- 当前文章依赖的视频/音频是否已有与对应版本匹配、经核验且可回到时间码的字幕稿、转写稿或处理稿；没有时链接`MAT`并立即交AI知识库专员决定，不要求内容运营自行转写；
- Codex无法稳定取得、动态加载或需要固定证据的具体网页是否有Web Clipper或人工保存的正文；
- Office容器中的相关嵌入附件是否已登记，内嵌PDF/PPT是否已有或可自动生成对应Markdown稿；
- 原文件是否仍可访问并能与提取稿对应。

自动MinerU只把最终使用的主Markdown归入项目级`Codex提取`，不得归档MinerU批量`assets`目录。主Markdown中的本地图片引用在发布前移除或替换为可回到原PDF/PPT页的定位说明；视觉核验以原文件为权威。确需长期保存的最小截图由证据流程单独挑选和登记，不沿用MinerU整批附件。调试JSON、布局PDF、缓存和临时输出不进入Obsidian。脚本的基础检查通过不代表证据已就绪；Codex仍须对照原文件检查页段、顺序、数字、表格、公式和图示。自动取得或复用的所有输入都合格时，在后台更新`10_待提交资料清单与就绪检查.md`并自动进入下一步，不向内容运营展示或等待确认。

只在自动取得失败、结果不合格或需要授权时向运营列出本篇必须提交的具体材料，写明原因和操作方法，不让运营自行判断、改名、归档或登记。运营只需把MinerU或Web Clipper生成的`.md`原样发给Codex。收到后，Codex核对来源和版本，按稳定资料ID命名并保存到项目级`运营提交`，一份来源同一版本只保存一次，同时登记运营发来时的原文件名和关联文章。MinerU、OCR或其他解析工具只作为技术手段，不单独建立Obsidian分类。

每次完成具有可追溯价值的项目运行时，使用`scripts/record_project_run.py`向`90_归档/20_项目运行历史/项目运行账本.jsonl`追加一行。每个项目只维护这一份账本，不按运行、工具或文章新建JSON文件。记录本次输入、实际读取文件与指纹、Skill版本/指纹、开始结束时间、工具调用与版本/参数、输出、重试、失败位置和人工介入原因；Token、模型与成本只在能取得真实值时记录，否则保留`null`，不估算。

### 4. 确认提取范围与处理样本

提取正文前，生成`15_提取范围与处理样本确认.md`。按每份材料列出：

- 人能看懂的资料名称和资料ID；
- 原文件与提取稿路径；
- 网页来源的页面标题和可直接打开的具体页面链接；
- 原始语言；
- 章节、页码、PPT页或网页区块；
- 拟提取主题、字段和最小完整语义块；
- 表格、图示和特殊结构处理方式；
- 父子附件关系和图片清单；
- 网站入口、导航路径、页面类型、发现数量与站点总数、分页或动态加载、交互区块及排除理由；
- 每个网页交互状态的状态ID、控件名称、切换动作、状态标识、完整表头、文章相关完整数据行数、单位、脚注和取得状态；
- 按处理结构与版本划分的样本组、代表样本和拟处理结果；
- 明确排除范围；
- 预计真实缺口，以及`若本地处理后缺口仍存在：开展 / 不开展 / 仅研究指定问题`的人工决定；
- 预计输出及存放位置。

人工确认记录必须包含真实人工姓名、确认时间、范围版本、逐篇批准范围ID、批准样本组ID、外部调研决定和必要原话摘要。人工确认后，只对批准范围正式提取，并把已确认代表样本的处理方法复用于同结构同版本资料。新增材料、扩大范围、新增外部调研问题或出现新结构时，只重新确认受影响部分。任何Agent的一致意见、自动检查结果或节点3的继续授权都不能替代这次人工确认。

客户源文件与客户官网同属客户一手来源，官网不自动高于源文件。源文件默认可以在确认范围内提取，无需官网佐证；按照内容相关性、版本日期、详细程度和适用场景选择。可信性与公开权限分别判断：可信内容仍可能因保密或未公开而不能写入对外文章。两者冲突时并列保留依据并进入审核，不用官网静默覆盖源文件。

### 5. 自动提取、派生与本地知识处理

范围确认后自动执行：

- 原样接收运营提交稿并归入`运营提交`，或生成其他逐字原文证据并归入`Codex提取`；
- 原文件与提取稿对照核验；
- 忠实翻译；
- 表格、列表、FAQ、参数和标题层级整理；
- 精确去重与来源属性统一；
- 项目资料稿更新；
- 把每份已处理资料拆成可独立判断的知识候选，登记到唯一`知识候选分流`队列；完成来源、范围和限制校验后生成待沉淀CLAIM草稿与事务计划，先进入文章前知识审核，不提前写入正式知识；
- 处理结果和异常展示。

每份源文件只维护一份当前清理与字段统一稿，可以只覆盖文章已确认页段。清理稿必须恢复自然段、标题层级、Markdown表格、公式和页码定位；不得生成文章话题稿，不得把多份PDF合并成巨型清理稿。处理结果、差异和旧稿进入处理记录或归档。

源文件级清理稿必须声明`原始语言 / 清理正文语言 / 内容类型`，且清理正文保持来源语言；任何语言的源文都先按源语言提取和清理，不得把英文源文写成中文总结，也不得把非英文源文直接改写成英文清理稿。来源语言不是英语时，对批准范围建立独立英语忠实翻译稿并逐段、逐表核验；来源本身为英语时保留原英文，不重复翻译。翻译、摘要和边界说明不得替代源语言清理正文。

文件指纹完全相同的多个客户原文件全部保留路径和登记记录，按“已有合格处理稿或已使用资料优先，否则最早登记资料优先”确定一个主资料ID，其余写`完全重复副本→[主资料ID]`；主资料一经确定不得随意更换，只生成一套当前内容导航、提取稿、清理稿和知识候选。指纹不同的同名、相似或疑似新旧版本必须分别登记资料ID，不得自动合并；无法确认时进入`MAT`。原始证据层保留重复段落、页面和表格的全部实际位置；只允许在清理稿和正式知识层精确去重，并记录保留位置、去重位置、依据和来源映射。

原文证据永不静默修正。资料处理Agent把发现分为`提取错误 / 英文源文表面问题 / 确定性规范化 / 语义不确定或事实风险 / 来源冲突`：提取错误按原文件纠正；客户提供的英文存在拼写、语法或措辞问题且含义唯一时，保留原英文并另建`source-normalized-english`派生稿，不推断其由机器翻译或存在未取得的中文原文；格式或单位表示只有在规则明确、含义唯一且可复算时才允许规范化，并同时保留原值、规范值和规则。缺失或含混单位、受损公式、残缺法规、参数或陈述冲突不得自动补写。零散表面修正按源文件汇总到`04_资料与证据/30_整理与翻译稿/90_处理记录/`；会影响事实、公开使用或知识沉淀的异常分配唯一异常ID，登记到`05_数据与审核/30_异常与待决定/10_企业知识异常待处理/02_源文与事实异常台账.md`，只挂起受影响`CLAIM`。

每条源文与事实异常先用普通话回答“发生了什么、为什么有风险、现在怎么处理、为什么本轮结束或还在等什么”，再保存原文现场证据包和内部追溯。主表只保留异常ID、通俗说明、原文是否修复、现在怎么处理、当前阶段、谁需要做什么及下一步/重开条件；技术ID、指纹、Agent记录和下游更新放在详情中，不用空字段占位。证据包提供可点击的保存原文证据链接、原始文件或网页链接（可取得时）、版本/指纹、精确位置、证据完整性、实际取得的逐字原文或原始结构及必要上下文；视觉/结构问题同时链接原页、截图、原表或公式现场。逐字原文含`%%`、Wikilink、HTML标签或其他可能触发Obsidian解析的控制语法时，使用`text`围栏代码块原样展示，不放在普通段落、引用块或表格中。不得用“存在截断”“单位错误”“证据不足”“明确排除”等流程词代替通俗解释。审核Agent必须实际打开链接核对异常记录与原始现场一致。客户明确禁止保存的正文继续只保留不含敏感内容的排除记录。

主Agent调度资料处理Agent完成客户资料处理，必要时调度调研Agent补公开知识缺口，并调度审核Agent独立对照原文件、运营提交稿、网站范围和处理结果查漏查错。资料处理Agent负责发现并分类提取错误、源文质量问题和事实风险，生成有来源映射的修正版或派生稿；审核Agent只读检查是否发生语义漂移或静默改动；主Agent负责异常ID、控制记录、正式知识和升级决定；调研Agent只补真实公开知识缺口，不修复客户企业事实。只有主Agent可以合并结果、向用户作出流程决定并写入正式知识；三个子Agent不得互相以结论代替证据。读取[多Agent分工与独立审核](references/multi-agent-orchestration.md)。

不再设置派生处理执行确认。结构、数字、术语、公开权限或来源出现实质风险时，在处理结果中标出，并进入文章前知识审核。

生成证据、翻译、表格、结构稿、项目资料稿或正式知识候选时，同时读取[高保真原文证据细则](references/verbatim-evidence-rules.md)和[派生资料、表格与翻译细则](references/derived-materials-and-translation.md)。需要选择或验证提取工具时读取[工具选择与质量验证](references/tooling-options.md)。

### 6. 确认真正缺口并自动调研

未处理的本地候选资料不是“知识缺失”。只有相关本地资料全部处理后仍不能覆盖文章需求，才建立外部调研任务。

开始新调研前，主Agent核对节点4中该文章的条件式外部调研决定。决定为`开展`或覆盖当前问题的`仅研究指定问题`时，按文章或批次向用户发送一次非阻塞通知后开展；决定为`不开展`时保留缺口并进入文章前审核，不得自动调研。节点4未作决定或新出现的问题超出已批准范围时，只补充确认新增调研范围。每项调研必须分别保存网页或文章的可取得原文证据与调研整理稿，不能只保存Codex总结。登录、付费墙、反爬、页面损坏或无法取得完整正文时，明确说明失败页面和所需内容，请运营用Web Clipper或其他方式提供正文。

### 7. 文章前知识审核

审核文章需要的知识，而不是给整个项目打分。至少检查：

- 大纲各部分是否有可用知识支持；
- 企业事实是否有客户来源；
- 参数、日期、型号、单位和案例是否一致；
- 外部来源是否可靠且仍然有效；
- 企业提供的行业知识与外部调研是否分开；
- 公开范围、客户名称、价格、认证、效果和承诺是否有风险；
- 是否存在无来源推断、冲突或不能写的内容。

审核Agent必须独立寻找遗漏页、第二页或隐藏交互、未登记附件、复杂图表误读和与主处理结论相反的证据，并返回实际读取、未读取、证据定位、反例和不确定点清单；审核结论只允许`有证据通过`、`带明确排除通过`或`升级人工处理`，不得以多个Agent意见一致作为通过依据。文章前审核通过后，主Agent先生成写作输入草稿，审核Agent再逐块对照确认范围、清理稿、官网原文和正式知识，检查是否把已选正文压缩为摘要、遗漏限定条件或融合成无来源的新结论。生成草稿前和交付写作输入前都必须运行v0.4项目校验，机器错误未清零或保真复核未通过时不得交付。

内容运营或Agent提出“以后问客户”时，主Agent为该事实分配唯一问题ID，并在`01_待客户补充事项.md`用简明表登记“想确认什么、为什么需要、回复前怎么处理、当前阶段、下一步由谁做、最近更新”。当前阶段只使用`待判断要不要问 / 无需询问 / 准备客户话术 / 等待发送 / 等待客户回复 / 收到回复，待核实 / 已完成`，不再并列维护必要性审核、话术状态和沟通状态三套字段。候选从`待判断要不要问`开始；知识库专员判断是否值得询问，确认需要后主Agent生成普通客户能直接理解的话术，知识库专员确认并指定优化师后才能进入`等待发送`。发送日期、渠道和回复证据只在实际发生后写入详情；未发生阶段不放空字段。内容运营只作为需求或发现来源。客户回复后进入`收到回复，待核实`，只重跑受影响节点；证据核验和下游更新完成前不得标记`已完成`。

问题只返回其来源步骤。处理完成后重新审核受影响部分，不重跑全部流程。文章前知识审核完成且审核发现的来源级/CLAIM级问题已经修正后，立即原子沉淀全部来源合格CLAIM，不受文章结论是否为“可以进入写作”影响；只有审核结论允许进入写作时，才在同一提交阶段生成`30_文章写作输入.md`。两条输出分别完成专项校验，互不拿对方当事实来源。

### 8. 生成唯一写作输入

把`30_文章写作输入.md`生成为可直接上传给写文章Skill的本篇知识库附件。内容运营在写文章Skill中另行填写关键词、标题、大纲和其他写作要求；附件本身只保留文章身份、目标语言、按大纲组织的获准正文、来源定位、数据日期和必要使用边界，不混入处理过程或完整审核报告。不得按源文件堆放；一个大纲位置可以组合多份来源，但不同来源分别成块，每个段落或连续知识块都必须附一个最有用的来源链接和精确位置。

写作输入执行“筛选，不总结”：可以从确认范围中去掉与本篇无关的完整段落，也可以把不同来源的相关段落移到对应大纲位置；一旦选中某段或连续语义块，就保留其完整解释、条件、例子、例外和上下文。非英语来源使用已核验的英语忠实翻译，英语来源直接保留原英文；不得压缩、概括、润色成知识点卡或把多来源融合成AI综合正文。Codex派生的比较框架、结论建议、FAQ组织和风险提醒只能放在单独的`写作边界与可选组织提示`中，不能替代来源正文。

翻译内容只放经过核验的英语版本。非英语原文默认留在后台证据层，不进入英语写作输入；仅在译法歧义、关键术语或数字风险确实需要时，补充最小范围源文核对信息并明确标为`仅供核对`。复杂参数或对比表保留英语Markdown表格的结构、数字、型号、单位和限定条件，并附不增加新事实的简短写作可用说明；简单表格可转成列表或文字。

源文件、Codex提取、运营提交稿、完整原表、中文原文、整理稿、审核记录和正式知识继续保留用于追溯和返工，但不要求写作者逐个打开。写作输入草稿生成后，审核Agent逐个来源块核对采用范围、未迁入内容及理由、正文完整性、表格/公式和就地来源；通过后主Agent把`20_文章前知识审核.md`中的`当前写作输入`更新为当前文件链接并记录保真复核结论，再把文章移入等待终稿。需求、来源、知识或大纲变化时，把旧写作输入移入`90_归档/10_文章历史版本/`并重新生成。

资料处理或外部调研每完成一个当前结果，先准备独立知识沉淀事务：`登记候选 → 验证人工范围确认与来源门禁 → 判断就绪状态 → 确定稳定键和硬映射路径 → 生成CLAIM草稿 → 专项校验 → 等待文章前知识审核完成`。文章前知识审核完成后，先修正并复核审核发现的来源级/CLAIM级问题，再对全部来源合格CLAIM执行：`暂存事务 → 原子写入正式知识及集中记录 → 全项目校验 → 标记已沉淀`。若文章结论允许进入写作，则在同一提交阶段生成唯一写作输入；若文章因其他知识缺口、文章要求或公开风险暂不能写，已有合格CLAIM仍照常沉淀。状态只使用`待核验 / 可自动沉淀 / 部分可沉淀 / 异常待处理 / 已沉淀 / 不沉淀`。候选必须记录范围确认文件、范围版本、批准范围ID、文章前审核文件、审核完成与受影响CLAIM处理状态、原文证据状态、网页交互覆盖、表格完整性、源语言清理状态和独立审核状态；任一必需前置失败时不得进入`已沉淀`。部分内容存在异常时，合格`CLAIM`照常沉淀，只有异常`CLAIM`进入待处理。沉淀不等待文章终稿或文章实际使用；外部调研是否最终被文章采用不参与沉淀判断。

区分两个门禁：`知识沉淀就绪`要求人工范围确认、完整直接证据、源语言清理与来源审核通过；`英语写作就绪`在此基础上还要求非英语来源的英语忠实翻译通过。普通源语言正式知识不因英语翻译尚未完成而失去沉淀资格；只有正式知识本身写入英语翻译版本时，已核验翻译才是该翻译CLAIM的沉淀前置。

### 9. 写作后引用核对闭环

收到最终文章标题、完整正文后自动闭环；正式引用率有则记录，没有则写`未提供`，本地连续词组覆盖率不得代替。自动：

1. 匹配文章任务并锁定版本、正文指纹；
2. 逐段对照写作输入、正式知识和原始来源，把每个文章主张映射到具体`CLAIM ID`；未完成逐段回对时只标记`尚未核对`，不得标记`已确认使用`或`已核验`；
3. 生成单篇文章引用清单，记录文章位置、`CLAIM ID`、正式知识位置、原始来源位置和使用判断；无法对应时标记`未追踪`，不得猜测；
4. 更新`20_知识块使用明细.csv`，一行表示一个文章版本对一个`CLAIM`的确认使用关系；写作输入中出现但终稿未使用的内容不得计数；
5. 重算`30_知识块使用总表.md`：累计使用次数按确认使用该`CLAIM`的不同文章数计算，同一文章多次出现只计一次；
6. 记录内容运营或正式平台提供的单篇引用率；未提供时写`未提供`，不自行估算；
7. 对终稿中新出现且没有正式知识或原始证据的主张登记异常，不把终稿反向沉淀为知识；
8. 运行v0.4全项目校验，修复CLAIM级映射、使用状态、累计次数、断链、占位符、表格、旧电脑路径和管理语言问题；
9. 校验错误清零后原子移动完整文章目录并同步状态列表、工作台、终稿、写作输入、清理稿范围链接、集中数据和版本入口中的项目级完成记录；全部成功后关闭文章任务。

正式知识不得按文章标题、文章选品组合、文章写作输入、提取批次、单个网页抓取任务、单份来源文件或抓取日期命名。产品按单个稳定SPU/型号分配知识ID，不得把一篇文章选择的多个型号拼成一个实体键；政策更新同一当前文件并把旧版移入历史；源证据按来源身份保存，不因被新文章复用而复制。正式知识只登记足以核验和复用的完整事实/规则、条件、结构及逐块来源；完整原文、上下文、表格和公式保留在证据层，写作时按定位回取。已有正式知识被使用时只更新集中使用数据，不重复沉淀。

`02_正式知识/20_产品介绍/`和`02_正式知识/50_行业知识与洞察/`根目录只允许各自的`01_*总览.md`，不得直接放置其他正式知识文件。预设子目录存在不等于落位正确；校验必须按内容类型和来源类型检查实际文件路径。

不再询问“要不要沉淀”或“沉淀到哪里”。无法追溯的新企业事实、来源冲突、过期数据和不可靠外部内容进入异常待处理，不写入正式知识。

### 10. 月度维护与项目交接

月末生成五部分维护简报：运行与规范、知识库基础情况、本月提取与沉淀、月度引用率、问题与闭环。运行与规范中检查当前电脑的MinerU API变量、到期日、剩余天数、本月在线检查、失败类型、API负责人和是否需要更换；当月已通过时复用本机检查状态。发现几项记录几项，不限制行动数量。检查待客户补充事项是否用通俗文字说明需求、当前阶段和下一责任人；检查源文与事实异常是否保留通俗结论和现场证据；汇总未完成`MAT`并由AI知识库专员逐项判断待处理视频、压缩资料、提取困难和不确定重复/版本关系。当前文章依赖或涉及重大事实风险的资料立即判断，不等待月末；已明确`暂不处理`的事项只在命中重开条件时再次提出。

收到客户解决方案、新版本资料或明确答复后，关联已有问题ID和异常ID，登记版本、来源、证据位置与公开使用范围，只重跑受影响范围。异常阶段只使用`待判断 / 等待材料 / 处理中 / 部分解决 / 已解决 / 已完成处置（原文未修复）`：只有替代证据已经修复原问题时才可标记`已解决`；只完成排除、限制和历史影响登记时标记`已完成处置（原文未修复）`，不得写成问题已解决；不同范围一部分修复、一部分仍不能使用时标记`部分解决`或拆分异常。客户专属产品参数、结构、能力或政策在未修复状态结束主动跟进前，必须先由知识库专员判断是否需要询问客户。已完成文章不静默重写，只登记历史影响和是否需要另行修订。详情和历史永久保留，达到重开条件时复用原异常ID。负责人变化时生成交接审核，除项目路径、负责人、任务、待客户补充事项、源文与事实异常、引用率缺失和最近问题外，必须在新负责人实际使用的电脑和Windows账号中完成API本地检查；新环境、Token新建或更换时完成在线检查。Token不由原负责人通过聊天转交，新负责人使用团队账号生成新Token，验证成功后再撤销旧Token。

运行中出现以下信号时，Codex随时根据当前对话和项目证据自动写入一条Skill反馈候选，不询问人工是否记录：用户指出规则或结果不合理、控制文件互相矛盾、同类人工绕行重复出现、校验器未拦截已确认错误、模板字段重复或规则无法按现有工具执行。自动记录必须标记`提出来源：Codex自动发现`、实际发现日期和自动总结依据，当前阶段设为`自动记录，待维护判断`；不得把Codex推断写成已确认Bug。人工可以随时主动提出Bug、反馈或改进建议，Codex直接记录为`提出来源：人工提出`并保存提出日期和对话摘要；人工明确认可一条自动候选时另记`人工认可：是`、认可人和日期，但人工认可不是记录或提交维护的前置条件，也不得覆盖首次提出来源。

每次准备结束一轮项目工作、向用户声明完成或推进文章节点前，必须执行一次`反馈信号检查`：回看本轮用户纠正、流程绕行、规则冲突和校验漏报；命中时先登记SKFB并同步当前待办，再结束本轮。项目校验器只能检查已经登记的反馈结构，不能证明对话中的反馈信号没有漏记；Skill行为回归必须包含“给出用户纠正后是否产生SKFB动作”的模拟对话测试。

每条反馈立即分配`[项目ID]-SKFB-001`格式的唯一编号，写入`05_数据与审核/30_异常与待决定/30_Skill运行反馈/01_Skill反馈台账.md`。阶段只使用`自动记录，待维护判断 / 人工提出，待维护判断 / 已纳入维护 / 维护中 / 已修复，待项目验证 / 已关闭 / 转为项目问题 / 不纳入Skill`。反馈只记录Skill行为，类型使用`缺陷 / 规则歧义 / 校验遗漏 / 模板与可读性 / 流程改进 / 环境兼容`；项目内容问题仍留在`CUS`或`ANM`台账。反馈证据可以链接项目文件和对话摘要，但提交维护前必须去除不必要的客户正文、账号、路径和其他敏感信息。自动登记动作本身不等于立即改规则；登记后由Codex自动复现，能确认是通用问题且位于授权维护范围内时自动进入维护、修改源版并回归；需要规则方向选择时交人工AI知识库专员或维护负责人决定，不找内容运营处理技术问题。未经授权不得修改其他Skill副本或向外发送反馈。

Skill反馈不得成为孤立台账。`20_当前待办.md`和`05_数据与审核/01_检查入口/01_当前待办.md`链接所有未关闭反馈；反馈详情回链相关文章ID、`CUS`、`ANM`、校验结果或控制文件；月度维护汇总待维护判断、维护中和待验证反馈；项目交接列出未关闭反馈；`30_版本与变更入口.md`提供反馈台账入口，并只在Skill版本迁移或已修复反馈实际应用到项目时追加项目级变更。每次新版迁移自动回归全部未关闭反馈；只有原复现不再成立、专项回归通过、全项目校验通过并记录修复版本与证据后才自动标记`已关闭`，不得仅凭更新了Skill文件关闭。

读取[文章就绪、月度维护与交接](references/readiness-and-maintenance.md)和[引用率与知识使用数据](references/governance-and-citation-metrics.md)。

## 正式知识模块

固定使用七个一级业务模块：

1. 公司概述
2. 产品介绍
3. 解决方案
4. 合作案例
5. 行业知识与洞察
6. FAQ
7. 其他

`行业知识与洞察`必须再分成`10_企业提供/`和`20_Codex外部调研/`。同一主题的两类来源分别建文件，不混写。

## 引用率与知识块使用

- 内容运营提供每篇`0%—100%`引用率；Codex只校验、记录和汇总。
- 月平均按纳入文章等权算术平均，保留两位小数。
- 月平均`≥15%`为正常，`<15%`为未达标，越高越好。
- 应纳入文章缺少引用率时标记`数据不完整，暂不判定`。
- 每篇终稿后自动记录知识块使用，不要求运营另行发起。
- 不按月给知识块评分；按季度或在低引用、反复推荐未使用、反复出错、合并/归档前专项检查。
