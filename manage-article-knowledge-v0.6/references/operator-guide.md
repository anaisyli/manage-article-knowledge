# 内容运营操作手册

本手册说明内容运营如何使用 `manage-article-knowledge v0.6`。它不是资料整理教程、写作教程或 SEO/GEO 规则。内容运营提供真实信息、文章要求和业务决定；知识库 Skill 负责扫描、检索、核验、沉淀、交付知识附件、接收终稿和维护治理记录。

> **先记住一句话**：人只处理真实信息和业务决定；正常处理由 Skill 连续完成。写作人员的日常入口仍然是“帮我写一篇……”。

## 先看这里：整套系统怎样工作

日常只需要提出写作要求，后面的步骤由已经完成一次性接入改造的各个 Skill 自动衔接：

1. **写作 Skill 先记下需求**：把本次任务保存到已确认的写作任务入口（本次写作需求记录）中；这一步用于防止任务丢失和重复建立。
2. **写作 Skill 完成简要大纲**：按本组原有选题和排重流程形成一份非空简要大纲，并在同一需求记录中标记 `大纲状态：已确认`；不要求完整列出所有 H2/H3。
3. **写作 Skill 提交任务**：把已确认的本次写作需求记录交给知识库 Skill，内部接口名称是 `writing_request`。
4. **知识库 Skill 准备资料**：查重、检索、文章前审核并完成合格正式 Claim 沉淀后，才在文章任务目录成对生成并校验 `30_本篇知识库资料.md`（人话名称：**本篇写作素材包**）和 `35_写作素材来源索引.md`。`30` 是本篇唯一交给写作 Skill 的知识库事实附件；写作 Skill 不创建或修改这些文件。
5. **写作 Skill 正式写作**：收到 `writing_ready` 和当前 `30_本篇知识库资料.md` 的绝对路径后，只读取这个 `30`，继续执行本组原有的选题、SEO/GEO、文风、图片和交付流程。
6. **写作 Skill 返回终稿**：把文章保存到约定的终稿位置，并返回终稿绝对路径。
7. **知识库 Skill 接收终稿**：将终稿规范化保存为 `40_最终文章.md`（人话名称：**最终文章**），并创建 `50_文章知识使用与Faithfulness记录.md`（人话名称：**文章知识使用与 Faithfulness 记录**）。
8. **Faithfulness Skill 审核**：只审核当前的 `40_最终文章.md` 和 `30_本篇知识库资料.md`，返回 `faithfulness_completed`。
9. **知识库 Skill 收尾**：继续导入审核结果，更新 Claim、知识缺口和文章状态；任务进入 `40_已完成` 后才返回 `article_completed`。

正常情况下，人工不需要逐步发送“先整理知识”“读取 30”“调用 Faithfulness”或“导入结果”。

有两种实际工作模式：

| 模式 | 适用情况 | 人工日常要做什么 |
|---|---|---|
| 已配置自动化 | 写作任务、终稿和 Faithfulness 入口已确认，写作 Skill 已接入 | 只提出写作要求；仅在系统提出具体歧义时决定 |
| 手动衔接 | 某个入口尚未建立，或暂时使用其他 AI 写作 | 提供文章计划和 `30`，回传终稿及审核结果位置 |

“自动”指 Skill 被调用或由自动化唤醒后连续完成后续步骤，**不**表示它会在无人调用时常驻监视文件夹。

## 第一部分：准备阶段

### 1. 需要准备什么

| 工具或对象 | 实际作用 | 谁负责 |
|---|---|---|
| Codex | 运行知识库流程、桥接各 Skill、执行月度审核 | 管理员确认可用；日常由内容运营调用 |
| Obsidian 项目 | 保存客户知识、文章任务、审核和治理记录 | 项目负责人提供项目路径 |
| 知识库 Skill v0.6 | 准备知识、生成 `30_本篇知识库资料.md` 和 `35_写作素材来源索引.md`、接收终稿、导入审核结果 | 已安装并由 Codex 调用 |
| 写作 Skill 或其他写作 AI | 按本组 SEO/GEO、文风和交付要求写文章 | 各运营组维护自己的流程 |
| Faithfulness Skill | 用当前 `40_最终文章.md` 和当前 `30_本篇知识库资料.md` 审核文章事实支撑 | 审核方或管理员安装、配置输出位置 |
| MinerU API | 按需解析复杂 PDF、PPT、表格、图示和版面 | 仅 API 负责人或 IT 配置 |
| 月度自动化 | 每月最后一个周五唤醒 Codex 批量运行复盘 | 知识库根目录负责人首次设置一次 |

知识库 Skill 不写文章、不决定标题、文风、SEO/GEO 或发布，也不把外部资料当作客户产品参数、认证、案例、价格或承诺的证据。写作 Skill 不修改知识库项目内的 `10/15/20/30/35/40/50`、正式知识、“35_写作素材来源索引”、Faithfulness 结果或知识库台账。

### 2. 第一次建立 Obsidian 知识库项目

第一次建库时，人工只发送下面五项：

```text
项目名称：
官网：
客户原始资料路径：
Obsidian项目路径：
内容运营负责人：
```

Skill 只会回显这五项并等待。人工明确回复 `确认建库` 后，Skill 才会扫描资料、访问官网、初始化项目和修改项目文件。

确认后，Skill 自动建立项目基础信息、唯一当前待办、来源台账和搜索索引、正式知识目录、文章任务目录、异常台账、覆盖与缺口视图、运行记录和版本入口。首次建库不要求同时提供周任务、终稿或 Faithfulness 路径；写作流程尚未建立时，接入状态保持 `待写作流程建立`。

### 3. 配置写作流程接入

建库信息和写作流程接入是两件事。建库确认项目本身；接入确认外部写作流程如何交换任务、终稿和审核结果。

每个项目只有一份接入配置：`01_工作台/40_写作与Faithfulness接入配置.md`。首次接入时，Codex 只在人工指定的写作项目范围内查找候选，不会扫描整个磁盘、文档或下载目录。

人工只需要提供或确认三个入口路径。其他判断由 Codex 根据真实样例、文件结构和固定规则自动完成；不要要求内容运营自己判断字段、状态或文章 ID：

| 人工只确认这个入口 | 你提供的内容 | Codex 自动完成 |
|---|---|---|
| 写作任务入口路径 | 周任务文件或目录的路径；如果没有固定文件，填写实际使用的桥接/提交入口 | 扫描真实样例，自动识别任务编号、标题、关键词、大纲、状态和可接收状态；自动写入字段映射、查重并建立文章 ID |
| 终稿入口路径 | 固定终稿目录，或写作 Skill 回传终稿的接收路径/日志位置 | 自动识别终稿格式和文章归属规则；保持外部原件不动，生成 `40_最终文章.md` |
| Faithfulness结果总目录 | 保存各篇审核结果的总目录 | 自动按项目 ID、文章 ID 和版本创建 `[总目录]\[项目ID]\[文章ID]\v[文章版本]\`，检查三个结果并更新 `50_文章知识使用与Faithfulness记录.md` |

人工不需要填写任务唯一键、可接收状态、字段映射、终稿识别规则、文章 ID/版本规则或 Faithfulness 版本目录规则。Codex 会把自动识别结果和依据写入接入配置；只有自动识别失败、出现冲突或无法安全唯一匹配时，才生成一个具体异常供负责人处理。

Codex 会从三个入口读取真实样例并写入接入配置。三个路径都可读取、识别规则可执行时，人工只需回复 `确认接入`；暂时没有写作流程时回复 `暂不接入写作流程`。人工不需要逐项确认 Codex 已经识别出的字段。

接入确认后，Skill 保存任务映射、文章身份规则和各入口。任务唯一键、终稿归属或路径变化时，只暂停受影响接口并标记 `异常，待重新确认`，不要求重新建库。

#### 文章身份和自动化边界

- 写作 Skill 可以回传文章 ID 和版本；若没有，知识库可以在任务映射或终稿绝对路径唯一确定时补齐内部文章 ID 和 `v1`。
- 不得按标题相似度、最新文件或目录顺序猜测文章归属；Codex 先用任务键、路径、日志和文章 ID 规则自动匹配，只有仍无法唯一对应时才要求人工确认。
- `已确认` 表示三个入口、识别规则和身份兜底规则均可确定；`部分接入` 只运行已经确认的接口。
- `writing_bridge.py` 可以接收没有固定任务文件的显式请求，也可以规范化每次返回的终稿绝对路径；这属于运行时桥接能力。
- 若希望项目状态为 `已确认` 并由配置自动检查，仍需在接入配置中登记可校验的任务入口、终稿入口和身份规则。否则保持 `部分接入`，按手动衔接流程运行。

#### 接入配置状态会怎样自动更新

`01_工作台/40_写作与Faithfulness接入配置.md`中的“自动状态摘要”由
`scripts/update_integration_status.py`维护。每次项目启动先记录一次检查；写作任务成功读取、终稿成功接收、Faithfulness结果成功导入、月度自动化配置完成或月度审核完成/失败时，系统追加对应的最近事件和时间。失败事件会把接入状态标为`异常，待重新确认`，并保留错误原因；重新确认接口后记录`interface_reconfirmed`恢复状态。

该更新器只更新摘要字段，不改三个入口路径、字段映射、识别规则、首次确认记录或文章明细。文章任务、运行账本、`50`和Faithfulness明细仍是详细记录的唯一来源。若某个旧项目没有摘要字段，更新器首次运行会在该文件中补齐，不需要人工手工维护。

后台需要补记事件时，使用统一入口：

```text
python scripts/update_integration_status.py --project <项目根路径> --event <事件名> [--error "错误原因"]
```

可用事件名包括`check`、`writing_task_success/failure`、`final_received_success/failure`、`faithfulness_import_success/failure`、`monthly_automation_configured`、`monthly_review_success/failure`和`interface_reconfirmed`。正常流程由各入口脚本自动调用，人工通常不需要手工执行。

### 4. 一次性接入现有写作 Skill

每个写作 Skill 只做一次。保留原有选题、SEO/GEO、文风、图片、发布和周计划流程，只增加以下接入规则：写作前先把本次写作需求记录持久化到写作任务入口（不要写入已安装 Skill 源目录或只读资料目录），提交 `writing_request`，收到知识库返回的 `writing_ready` 和当前“30_本篇知识库资料”后再写作；写作完成后返回文章正文文件的终稿绝对路径。写作 Skill 不创建或修改知识库项目内的 `10/15/20/30/35/40/50`、正式知识、Faithfulness 结果或治理台账。若另有DOCX/ZIP交付包，可同时返回其路径，但不能用文件夹或ZIP替代终稿绝对路径。接入改造完成后，日常写作不需要每次重新复制这段 Prompt。

把下面 Prompt 发给各组实际负责写作的 Writer 或写作编排 Skill；如果一个组还有 Reviewer、审计、打包或发布 Skill，不要把这段 Prompt 发给那些辅助 Skill。

```text
请在保留你原有写作流程的基础上，增加“企业知识库自动接入”规则，不要删除或重写原有规则。

每次收到“帮我写一篇……”或同类写作请求时：
0. 先检查当前 Skill 是否已有可持久化的本次写作需求记录入口。该入口可以复用现有周计划、排期表、任务文件、任务日志或任务目录；如果没有，必须在本次一次性接入改造中补上一个文件或目录。不得只把需求留在对话上下文中，也不得等文章写完后再补记。
1. 每篇文章在进入知识库交接前，先创建或更新本次写作需求记录。记录必须固定保存：任务唯一键、项目、原始写作请求、当前状态、本次写作需求记录的绝对路径、记录定位信息、标题或主题、产品或内容对象、选题方向、关键词、目标语言、限制和原始写作要求。大纲也必须写入记录，但只需是非空的简要大纲，能够说明主题、主要问题或基本组织方向，不要求完整列出所有 H2/H3。以上字段由 AI 按当前 Skill 原有流程自动填入；尚未形成的非门禁字段明确标记为“待定”或“未提供”，不得只留在对话上下文中。
2. 定位当前已安装的 manage-article-knowledge v0.6 Skill，并读取 references/skill-integration-handoff.md 中写作方适用的交接规则以及 references/handoff-contract.json；不要把某台电脑上的绝对安装路径写进你的 Skill，也不要执行其中标明为知识库内部的维护步骤。每次交接从该JSON读取当前`handoff_contract_version`，不要在写作Skill中另存一份可能过期的固定版本号。
3. 本次写作需求记录保存成功后，先继续执行该写作 Skill 原有的选题、排重和必要的人工确认；形成可准备知识的标题/主题和非空简要大纲后，将“大纲状态”标记为“已确认”，再根据当前项目接入配置，把当前`handoff_contract_version`、任务唯一键、该记录的绝对路径、记录定位信息、项目、标题或主题、产品或内容对象、选题方向、关键词、简要大纲、目标语言、限制和原有写作要求交给知识库 Skill。需求记录路径必须实际存在；同一任务唯一键的标题、基本大纲、限制或原始写作要求发生实质变化时，必须按文章版本归档合同更新后重新提交，不得静默覆盖旧任务。若人工已经直接给出标题/主题和足够的简要大纲，则无需额外选题确认；如果没有大纲，不得提交 writing_request。最终 H1 可以在不改变主题、读者问题和基本结构的前提下由原写作流程微调；若改变这些内容，必须更新大纲并重新提交。
4. 等知识库返回同一兼容`handoff_contract_version`的`writing_ready`和当前`30_本篇知识库资料.md`绝对路径后，先读取 handoff 第 4.0 节“`30_本篇知识库资料.md` 的六节读取方法”和第 4.1 节“写作 Skill 使用 `30` 的固定规则”，再读取当前 `30`，然后才开始正式写作。缺少版本或不兼容时停止该交接并报告具体错误，不猜测或绕过。
5. 严格按当前 `30` 文件内部的六个章节使用：第一至第三节提供可核验事实、目标语言表达和数据；第四节只用于大纲组织；第五节只用于生成控制和禁写边界；第六节用于资料不足时的省略、缩小或中性改写。当前 `30` 是本篇唯一的知识库事实附件；继续执行你原有的 SEO/GEO、文风、图片和交付流程。
6. 写作完成后，把终稿保存到约定位置，并返回同一`handoff_contract_version`和终稿绝对路径；有文章ID和版本时一并返回，没有时不要猜测。
   `writing_completed`只表示写作 Skill 已交付终稿，不表示整条文章流程完成；知识库还要继续接收终稿、完成 Faithfulness 交接、导入审核结果并将任务推进到 `40_已完成`。
7. 不要修改 35、正式知识、Faithfulness 结果或知识库治理台账。

接入改造完成后请说明：
- 修改了哪个 Skill 文件；
- 本组约定把本次写作需求记录保存在哪里；如果原 Skill 没有而本次新建了文件或目录，请说明新建位置；尚未配置项目入口时明确说明“未配置”，不得猜测实际路径；
- 最终文章约定保存在哪里，或采用什么终稿入口路径规则；尚未配置时明确说明“未配置”，不得猜测路径。

每次实际写作完成后，再在交付回执中返回本次写作需求记录的实际绝对路径、终稿绝对路径；如有DOCX/ZIP交付包，另报交付包绝对路径。
```

用一篇测试题验证：知识库侧先完成正式 Claim 沉淀并校验 `30/35`，再返回 `writing_ready`；写作侧只生成需求记录、读取当前 `30`、按六节规则写作并返回终稿绝对路径。`30` 的详细使用规则只维护在 `skill-integration-handoff.md`，不复制进每个写作 Skill。测试通过后，日常请求直接按已改造的 Skill 自动执行，不要求人工重复粘贴本 Prompt。

### 4.1 已接入写作 Skill 的升级规则

一次性接入完成后，后续是否需要再次修改写作 Skill，按下面规则判断：

| 变化类型 | 已接入且运行时读取唯一合同的写作 Skill | 仍使用旧版固定字段/旧流程的写作 Skill | 处理方式 |
|---|---|---|---|
| 仅修正文档说明、脚本实现或项目级模板，`handoff_contract_version`不变，事件必填字段和写作门禁不变 | 不需要修改 | 通常不需要修改 | 直接使用已安装 Skill 的最新文件；新任务重新加载 Skill 后生效 |
| 合同版本不变，但新增必填字段、改变`writing_ready`门禁、改变30读取规则或改变终稿回执字段 | 需要按新规则重新读取并确认 | 必须重新做一次接入升级 | 把“接入升级 Prompt”发给对应 Writer；升级完成并通过一篇测试题后再恢复日常写作 |
| `handoff_contract_version`变为不兼容版本，或事件含义/目录身份规则发生破坏性变化 | 必须与知识库、Faithfulness一起升级 | 必须与知识库、Faithfulness一起升级 | 先暂停受影响交接；三方升级到同一兼容版本并完成回归，不得让旧版本猜测或降级运行。当前`MAK-HANDOFF-1.1`把`external_task_key`纳入`writing_request`机器必填字段。 |

这里的“运行时读取唯一合同”是指写作 Skill 每次交接都会从当前已安装知识库 Skill 的`references/handoff-contract.json`读取版本，而不是在自身文件中写死一份版本号。只有满足这一点，合同版本不变的兼容更新才可以自动生效。已经按旧版 Prompt 接入、但没有这条运行时读取规则的写作 Skill，不能因为安装目录已同步就视为已升级。

需要升级旧写作 Skill 时，只发送下面这段一次；不要把它作为每次写作的日常指令：

```text
请升级本写作 Skill 的企业知识库接入，不要删除或重写原有写作流程。

请先读取当前已安装的 manage-article-knowledge v0.6 Skill 的：
- references/skill-integration-handoff.md
- references/handoff-contract.json

按当前唯一合同更新本写作 Skill，使其：
1. 每次写作先把本次写作需求记录保存到已确认的写作任务入口；
2. 运行时读取当前 handoff_contract_version，不在本 Skill 中复制或写死合同版本；
3. 按当前合同提交 writing_request，只有收到同一兼容版本的 writing_ready 和当前 30_本篇知识库资料.md 后才开始写作；
4. 只把当前 30 作为知识库事实附件，继续执行本 Skill 原有的 SEO/GEO、文风、图片和交付流程；
5. 写作完成后按当前合同返回 writing_completed、合同版本和终稿正文文件绝对路径；
6. 不创建或修改知识库项目内的 10/15/20/30/35/40/50、正式知识、Faithfulness 结果或治理台账；
7. 缺少合同、合同版本不兼容、项目或入口无法唯一确定时，明确报错并停止，不猜测、不降级。

完成后说明修改了哪个 Skill 文件、本次写作需求记录入口、终稿入口规则，并用一篇测试题验证升级后的交接。
```

升级完成后，日常写作只需提出正常写作要求。若某次交接返回`missing_contract_version`、`unsupported_contract_version`或其他合同字段错误，应先按错误中的`resume_condition`升级发出方，再使用原任务身份重新提交；不要手工补字段后继续写作，也不要复制旧版 Prompt 反复尝试。

### 5. 配置 Faithfulness 审核

Faithfulness 有两种用法：

| 用法 | 输入 | 输出及后续 |
|---|---|---|
| 单独审核 | 人工提供“40_最终文章”和当前“30_本篇知识库资料” | 输出 `prepared.json`、`judgments.json`、`faithfulness_summary.md`；不会自动更新知识库 |
| 知识库后置审核 | 知识库按唯一合同提供 `faithfulness_request`：当前“40_最终文章”、当前“30_本篇知识库资料”、项目ID、文章ID、版本、合同版本和专属结果目录 | 固定的 `deepeval-article-audit` 返回同版本 `faithfulness_completed`；知识库随后自动导入“50_文章知识使用与Faithfulness记录”、Claim 支撑和治理记录 |

后置审核的人工处理只有一个分支：

- 当前Codex已发现`deepeval-article-audit`：知识库自动调用，内容运营不需要指定路径或再次发送指令。
- 当前Codex未发现：必须在对话中说明“当前未安装 `deepeval-article-audit` Skill，无法继续本篇文章的 Faithfulness 审核；任务已保留在 `30_等待Faithfulness`，当前没有生成审核结论；请安装该 Skill，或提供其所在目录的绝对路径。”不能只返回`faithfulness_skill_not_found`字段。
- 内容运营提供本地目录：Codex先检查该目录的`SKILL.md`名称是否为`deepeval-article-audit`，校验通过后仅用于本次审核；不把本地绝对路径写入通用合同。

安装或目录校验成功后，从原任务的`faithfulness_request`继续，不需要重新提交终稿，也不需要人工说“继续”。

后置审核只接收当前“40_最终文章.md”和当前“30_本篇知识库资料.md”，不要加入“35_写作素材来源索引”、完整知识库、原始资料、写作要求或外部调研记录。

结果必须写入本篇版本专属目录：

```text
[Faithfulness结果总目录]\[项目ID]\[文章ID]\v[文章版本]\
  [文章ID]-prepared.json
  [文章ID]-judgments.json
  faithfulness_summary.md
```

知识库会校验文章 ID、版本、终稿哈希、`30` 哈希、结果计数和证据格式。终稿实质修改时，归档旧版本、递增版本并重新审核。

### 6. 配置 MinerU API

> 日常内容运营不接触 Token、命令或上传。

MinerU 只在当前文章确实需要、且本地方法无法可靠取得 PDF/Office 的正文、表格、公式、图示或版面关系时使用。输出只是技术提取稿，形成 Claim 前仍必须回到原文件核验。

首次配置只由 API 负责人或 IT 完成：

1. 在 <https://mineru.net/apiManage/token> 使用团队账号创建 Token，并记录到期日。
2. 定位当前已安装的 `manage-article-knowledge v0.6` Skill 根目录，打开其 `scripts` 子目录并运行 `initialize_mineru.cmd`；不要把某台电脑的绝对安装路径写入项目或 Skill。
3. 按提示把 Token 置于剪贴板后按 Enter；不要把 Token 粘贴进聊天或窗口。输入到期日 `YYYY-MM-DD`。
4. 等待初始化器完成本地 `probe` 和在线 `health-check`，随后完全退出并重新打开 Codex Desktop。

`Setup completed` 表示配置和在线验证完成；`Local setup completed. MinerU online verification is temporarily pending.` 表示本机配置已完成，网络验证稍后由 Codex 重试，不需重复输入 Token。

| 现象 | 负责人 | 处理原则 |
|---|---|---|
| Token 缺失、过期或鉴权失败 | API 负责人 | 检查团队 Token 和到期日，必要时重新初始化 |
| 429 或额度不足 | API 负责人 | 检查额度和并发，不要求内容运营转换文件 |
| 临时超时或服务不可用 | Codex | 最多重试 2 次，保留最近成功状态 |
| `WinError 10013`、socket 或沙箱权限错误 | Codex / IT | 按最小权限处理网络访问，不当作 Token 错误 |
| 单个文件或提取结构失败 | Codex；受阻时内容运营 | 先检查格式、页数、加密、损坏、版本和原件；仍无法处理再转 AI 知识库专员 |

Token 不得写进客户项目、Skill、对话、截图或运行账本。每台实际运行的电脑都需单独配置；Token 距到期 7 天和 1 天时提醒 API 负责人。

### 7. 配置月度审核自动化

月度自动化不是另一套审核程序，只做一件事：在每月最后一个周五唤醒一个能访问整个知识库根目录的 Codex 任务。被唤醒后，Codex 按 v0.6 Skill 逐个读取根目录下的项目、生成各自月报和记录异常。多个项目位于同一知识库根目录时，只配置一个总控自动化，不要为每个项目重复设置。

自动化只负责定时唤醒；逐项目月报检查、目录维护、异常记录和业务门禁仍由项目中的 v0.6 Skill 执行。

#### 推荐：让 Codex 代为创建一条总控自动化

配置前只确认三件事：

- 有一个能访问整个知识库根目录的 Codex 项目/任务；
- 知识库根目录的真实绝对路径，例如 `D:\知识库根路径`；
- 根目录下的项目已使用 v0.6 目录结构（至少有 `01_工作台` 和 `05_数据与审核`）。

在这个 Codex 项目/任务中发送下面一段。只替换 `D:\知识库根路径`，不要改其他内容：

```text
请为知识库根路径 D:\知识库根路径 创建一条总控月度审核自动化：每月最后一个周五，Asia/Shanghai 时区，按团队约定时间运行。目标使用当前能访问该根路径的 Codex 项目/任务。自动化被唤醒后，执行下面的月度复盘要求：

知识库根路径：D:\知识库根路径

定位当前已安装的 manage-article-knowledge v0.6 Skill，并读取：
references/monthly-and-handoff.md
references/runtime-checklist.md

只处理知识库根路径的直接子目录。对每个同时存在 `01_工作台` 和 `05_数据与审核` 的子目录，先读取其 `01_工作台\40_写作与Faithfulness接入配置.md`，再按当前月份和 v0.6 规则完成月度审核，检查：
1. 项目版本、目录、来源索引、正式知识和运行记录；
2. 写作任务、终稿、Faithfulness 三个接入入口的状态和积压；
3. 本月 Claim 沉淀、公共知识缺口、CUS、MAT、ANM、SKFB；
4. 每篇文章的 Faithfulness 结果和未关闭事项；
5. MinerU/API 状态和本月失败记录。

将每个项目的月报分别保存到该项目\05_数据与审核\40_月度与交接\YYYY-MM_月度知识库审核.md。
其中 YYYY-MM 使用本次运行日期对应的月份，例如 2026-09；不要保留方括号，也不要另建其他月份格式的文件名。

只自动完成有明确规则的检查、汇总和记录；需要业务决定时在对应项目生成处理单并说明负责人。缺少 v0.6 目录或配置的子目录只记录为“未识别项目”，不得修改其内容；一个项目失败不得阻塞其他项目。
不要为子项目另建自动化；不要修改客户原始资料、外部写作原件或历史审核结果，也不要把月报当成文章发布合格判断。创建完成后返回自动化名称、周期、时区和目标任务。
```

如果不能使用代建方式，手动在 `Automations` 中填写同样的配置项：名称 `知识库根目录-月度知识库复盘`、每月最后一个周五、`Asia/Shanghai` 时区、能访问知识库根目录的目标任务；Prompt 仍复制上面这一份。不要为子项目另建自动化。

#### 创建后只测试一次

保存自动化后，不要等到月底才知道配置是否正确：

1. 在该自动化的操作菜单中选择 `Run now`、`Test` 或“立即运行/测试运行”；这次运行只执行一次，不改变周期规则。
2. 打开知识库根目录下的每个可识别项目，检查是否分别生成：`该项目\05_数据与审核\40_月度与交接\YYYY-MM_月度知识库审核.md`。
3. 打开各项目月报，确认“统计月份”是当前月份，并且第一部分记录了计划日期、实际执行日期和自动化触发情况。
4. 检查各项目运行账本是否有本次月度审核记录；有项目缺少月报或运行记录，就不能认为批量测试成功。

如果界面没有 `Run now` 或 `Test`，就在总控目标任务中手动发送上面的 Prompt 做等价测试；测试完成后保留各项目月报，不要把手动测试误写成正式计划日期执行。

#### 以后怎么判断是否正常

- 自动化状态必须是启用/Active；暂停、删除、总控目标失效或知识库根路径不可读，都表示本月批量审核尚未执行。
- 运行时间到了但有项目没有月报时，先检查自动化状态、总控目标、知识库根路径和 Codex 运行记录，再检查对应项目；不要直接手工补写“已完成”。
- 错过计划日期时，下一次总控任务被启动或唤醒时由 Skill 为受影响项目补做，并在各项目月报第一部分记录计划日期、实际执行日期和逾期原因。
- 月报只记录知识库运行、来源、Claim、Faithfulness、缺口和异常情况，不等于文章发布合格、SEO/GEO合格或业务批准。

## 第二部分：实际操作阶段

### 8. 已全部配置好的自动化流程

人工只需在已接入的写作 Skill 中提出：

```text
帮我写一篇关于 XXX 的文章。
```

文章要求可包含标题或主题、关键词、大纲、目标语言、特殊限制和允许使用的本篇资料。Skill 会继续检索，并仅在缺少不可替代材料、事实冲突或需要业务决定时暂停。

正常流程：

```text
写作 Skill：先保存需求记录，再提交 writing_request
  → 知识库 Skill：查重、检索、审核，生成 20_文章前知识审核、30_本篇知识库资料、35_写作素材来源索引
  → 知识库 Skill：返回 writing_ready 和当前 30 文件绝对路径
  → 写作 Skill：读取当前 30，按原流程写作并返回终稿绝对路径
  → 知识库 Skill：生成 40_最终文章和 50_文章知识使用与Faithfulness记录
  → Faithfulness Skill：审核当前 40 和 30
  → 知识库 Skill：导入结果，更新 Claim、缺口和文章状态，任务进入 40_已完成
```

人不需要重复发送“继续”“读取 30”“好了可以写”“调用 Faithfulness”或“导入结果”。项目不明确、任务或终稿无法唯一归属、路径/字段失效、客户事实冲突、公开范围风险、缺少不可替代材料或外部工具确定失败时，Skill 才会提出具体问题；决定完成后从阻塞节点恢复。

### 9. 尚未全部配置好的手动衔接流程

未完整接入时，仍可按原方式工作：

```text
每周文章计划或人工文章要求
  → 交给知识库 Skill
  → 知识库 Skill 生成本篇 30
  → 人工把文章要求、固定 Prompt 和当前 30 交给其他 AI
  → 其他 AI 写作并返回终稿绝对路径
  → 人工把终稿交回知识库 Skill
  → Faithfulness 审核当前 40 和 30
  → 人工回传结果专属目录
  → 知识库 Skill 导入结果并沉淀记录
```

交给知识库 Skill：

```text
项目：
文章ID：有则填写，没有可留空
标题或主题：
关键词：
大纲：
目标语言：
特殊限制：
本篇是否禁止新的外部调研：允许 / 禁止
本篇是否禁止使用全部外部来源：允许 / 禁止
```

随文资料说明属于“项目长期事实资料”“仅本篇事实资料”“写作要求/非事实参考”或“禁止提取正文”。写作要求、风格、SEO/GEO 和结构参考不会进入事实索引、Claim、`30` 或 Faithfulness 证据上下文。

交给其他 AI 时，只附当前 `30_本篇知识库资料.md`，不要附加 `35`、完整知识库、客户原始资料或外部调研记录：

```text
请按照内容运营提供的文章要求完成写作，并把附件《30_本篇知识库资料.md》作为本篇唯一的知识库事实附件。

1. 文章目标、结构、文风、关键词、SEO/GEO和交付格式，以内容运营的文章要求为主；知识库资料不替代这些要求，也不要求逐条照抄。
2. 附件第一至第三部分是本篇经核验的事实、数据和目标语言表达。涉及客户、产品、型号、参数、认证、案例、能力、效果或商业承诺时，只能使用附件明确提供的内容；不得补造、扩大范围，或把通用行业信息写成客户事实。
3. 不得写入竞品品牌、型号、特殊产品、参数、价格、案例、排名或比较结论；通用行业知识必须去品牌化。
4. 第四至第六部分用于选材、组织和生成控制，不是必须写入正文的内容。不要复述 Claim 编号、来源定位、审核过程、资料缺口或使用边界。
5. 没有覆盖的具体事实应省略、缩小范围或中性改写。不要把 not supported、no evidence、cannot determine 等审核语言写进正文。
6. 可以自由完成标题组织、段落结构、过渡、总结、行业常识、一般原理和非客户专属解释；这些补充不得伪装成客户事实，也不得产生新的精确参数、型号结论、认证、案例、客户能力、效果或商业承诺。
7. 中途新增的事实文件必须先交知识库 Skill 登记、核验并更新当前 30，不能作为平行客户事实附件直接使用。

写作完成后，请返回完整终稿、文章正文文件的终稿绝对路径；如有DOCX/ZIP交付包，再单独返回交付包绝对路径。
```

回传终稿：

```text
文章已经完成。

项目：
文章主题：
终稿绝对路径：
交付包绝对路径（可选）：
文章ID：有则填写，没有则留空
文章版本：有则填写，没有则留空
```

知识库通过文章 ID、外部任务映射或终稿绝对路径确定归属，保持外部原件不动，并生成只含终稿文字和表格内容的内部 `40_最终文章.md`；文章配图不复制到知识库任务目录，仍留在写作 Skill 的外部交付包中。无法唯一确定时要求人工说明归属，不按标题猜测。Faithfulness 结果必须放在当前文章版本专属目录；只有结果被知识库导入后，`50`、Claim 支撑、unsupported 治理和文章状态才会更新。

### 10. 写作人员实际使用什么

写作人员正常只读本篇 `30_本篇知识库资料.md`：它是本篇唯一知识库事实附件；`35_写作素材来源索引.md` 仅供知识库追溯和 Faithfulness 映射，不能交给写作方。写作继续使用本组原有规则；当 `30` 未覆盖某个具体事实时，省略、缩小或中性改写，不自行补写。

## 第三部分：目录和文件怎么读

前面先按业务流程说明“知识附件、终稿和写后记录”分别做什么；本部分再集中说明它们在项目中的完整文件名和编号。日常先看用途，只有需要打开文件或排查状态时再按文件名定位。

### 11. 项目目录

| 区域 | 用途 | 内容运营通常看什么 |
|---|---|---|
| `01_工作台` | 项目基础信息、唯一当前待办、接入配置和版本入口 | 先看 `20_当前待办.md` |
| `02_源资料` | 客户原始资料、索引、按需提取和外部调研原文证据 | 查看资料是否登记、可否搜索、是否待处理 |

| `04_文章任务` | 每篇文章从知识准备到终稿、Faithfulness 和历史版本的过程 | 按进行中、等待终稿、等待 Faithfulness、已完成查看 |
| `05_数据与审核` | Faithfulness、覆盖与缺口、异常、月度交接和运行记录 | 需要追溯或处理异常时查看 |

`05_数据与审核` 中常用入口：`10_Faithfulness`、`20_知识库覆盖与缺口`、`30_异常与待决定`、`40_月度与交接`、`50_运行记录`、`60_版本归档`。当前项目节点的唯一事实源是 `01_工作台/20_当前待办.md`。

### 12. 一篇文章的文件

## 第四部分：资料和知识处理

### 13. 支持的资料格式

初始化先登记资料身份、版本和可搜索内容；只有当前文章实际命中某份资料，Skill 才处理当前问题所需的最小范围。内容运营不需要自行预处理文件。

| 资料格式 | 初始化或刷新时 | 当前文章命中后 |
|---|---|---|
| TXT、Markdown、CSV、JSON、HTML、XML | 本地读取并建立索引，保留标题、行、表格和位置 | 回到原文件核验，再提取最小 Formal Claim |
| DOCX、PPTX、XLSX | 建立文字索引，登记图片、图表、关系和嵌入对象 | 普通内容本地处理；复杂结构按需进入 MAT 或调用 MinerU |
| 可搜索文字 PDF | 提取正文并保留页码 | 回到页面核验文字、表格、单位和脚注 |
| 扫描 PDF、图片 | OCR 仅作为搜索线索 | 对照原页核验；复杂结构按需调用 MinerU |
| ZIP | 登记身份、指纹和成员名称 | 确实依赖时仅在安全临时目录检查必要成员 |
| RAR、7z、加密或损坏文件 | 登记真实状态，不猜测正文 | 本篇依赖时进入 MAT；无法处理再转 AI 知识库专员 |
| 音频、视频 | 登记身份和基础元数据，不自动转写或总结 | 本篇依赖时进入 MAT；已有转写稿仍需核对对应关系和准确性 |
| 网页 | 官网和已登记企业相关网站优先读取，保存 URL、日期和可访问状态 | 普通页直接核验；动态/视觉状态按需使用浏览器 |

格式本身不决定是否调用 MinerU；本地方法可靠时不调用，复杂结构确实影响当前文章时才按最小范围调用。

### 14. 知识缺口和外部调研

Skill 按以下顺序查找知识：正式 Claim、客户源资料、客户官网、内容运营提交且关系已确认的其他企业相关网站、既有外部公共知识。前五处都不能回答，才形成真实知识缺口。

| 情况 | 记录 | 通常由谁决定 |
|---|---|---|
| 公共技术、行业、方法或法规知识缺失 | 知识缺口 `gap_key` | Skill 按触发条件调研；本篇限制由内容运营决定 |
| 客户专属事实缺失或需要确认 | CUS | 内容运营/项目负责人 |
| 本地资料存在但未可靠处理 | MAT | Codex 先处理；受阻时内容运营，再转 AI 知识库专员 |
| 来源冲突、数字单位、OCR、版本或危险外推 | ANM | 需要业务或证据取舍时人工决定 |
| 规则冲突、模板不可用、校验漏报或流程错误 | SKFB | Codex 记录，维护负责人处理 |

外部调研只补公共行业知识，不能替代客户事实。项目级竞品限制始终生效：不以竞品品牌、型号、特殊产品或比较页为检索目标；偶然命中时不保存可识别名称、链接或原文。

写作后 Faithfulness 暴露的新事实会归组为知识缺口、CUS、MAT、ANM 或资料包覆盖遗漏；不会自动改写已完成文章，也不会把终稿反向当作知识来源。

## 第五部分：人工介入和异常处理

### 15. 哪些事需要人工

- 首次提供五项建库信息并回复 `确认建库`；
- 首次确认写作任务、终稿和 Faithfulness 三个入口；
- 每个写作 Skill 一次性完成接入 Prompt；
- 客户事实、公开范围、来源冲突和大纲缩减等业务决定；
- API 负责人首次配置或更换 MinerU Token；
- 知识库根目录首次配置月度自动化；
- 任务、终稿或审核结果无法唯一匹配；
- 外部资料无法可靠取得，或 Faithfulness 结果版本/哈希不匹配。

扫描、索引、检索、Claim、`30/35`、终稿规范化、`50`、审核结果导入、台账和月报不要求人工反复催办。

### 16. 常见问题

| 问题 | 正确处理 |
|---|---|
| 没有周任务文件 | 使用 `writing_bridge.py prepare` 或人工文章要求提交任务；项目仍保持 `部分接入`，直到有可校验的任务身份入口 |
| 没有固定终稿目录 | 使用 `writing_bridge.py finalize` 接收每次终稿绝对路径；项目自动接入仍需登记可检查的终稿入口，否则走手动衔接 |
| 写作方没有文章 ID/版本 | 不阻断；归属唯一后由知识库补齐 |
| 任务编号重复或终稿归属不清 | 停止受影响任务，说明候选；不要按标题或最新文件猜测 |
| Faithfulness 结果放错目录或哈希不匹配 | 维持等待状态，按当前 ID、版本和哈希重新放置/生成结果 |
| 路径或格式变化 | 将受影响接口标记 `异常，待重新确认`，只重做该接口 |
| 月度自动化错过 | 下次启动补做并记录原因；检查自动化是否暂停、删除或指向错误项目 |

Skill 会在文章目录生成 `文章前问题与处理单.md` 并同步 `20_当前待办.md`。内容运营只需提供材料或决定；处理完成后 Skill 从阻塞节点继续。

### 17. Skill 反馈台账

固定入口：`05_数据与审核/30_异常与待决定/40_Skill运行反馈/01_Skill反馈台账.md`。规则冲突、模板难用、校验漏报、自动流程错误或同一步骤反复绕行时，Codex 应主动记录 SKFB 候选。内容运营也可以直接说“把这个记录到 Skill 反馈台账”或“这是一个 bug，请登记 SKFB”，不必填写 ID、类型、状态或技术原因。

客户事实缺失属于 CUS，资料未可靠处理属于 MAT，来源或事实冲突属于 ANM，单篇业务决定留在文章处理单。记录 SKFB 不等于立即修改 Skill；只有用户或维护负责人明确同意后，才更新 Skill 和版本记录并完成自测、项目验证。
