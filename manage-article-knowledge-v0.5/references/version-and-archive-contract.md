# 当前版本与历史归档合同

## 1. 总原则

- 一个业务对象只有一个当前入口。当前文章、正式知识、控制文件和机器数据不得并行维护两个“当前版”。
- 会改变事实、文章要求、公开范围、证据、结论或后续复现能力的修改，必须先归档旧版，再更新当前版。归档失败时不得覆盖当前文件。
- 历史归档只读，不参与当前检索、写作输入、Faithfulness计算、当前待办或项目状态判断。恢复历史版本必须创建新的当前版本，不能直接编辑历史文件。
- 归档包必须包含`00_版本说明.md`，记录对象、人话名称、旧版本、归档时间、原因、替代版本或当前入口、原状态路径，以及归档文件的相对路径和SHA-256。
- 普通状态推进、台账新增一行、最近更新时间、链接或确定性排版修复不逐次建立文件快照；由当前台账、版本与变更入口和项目运行账本留痕。

修改前使用`scripts/archive_project_version.py`创建并校验归档包。文章传入当前任务目录和`--kind article`；正式知识文件使用`--kind formal-knowledge`；高影响控制文件使用`--kind control`。脚本只创建快照，不修改当前文件；快照成功后才执行当前版本更新。

## 2. 文章版本

同一篇预期交付物的修订继续使用同一文章ID，文章版本按`v1`、`v2`、`v3`递增。文章目的、受众或主题已经变成另一篇交付物时建立新文章ID，不把无关文章伪装成旧文章的新版本。

当前任务目录只保存一个现行文件组。`10/15/20/30/35/40/50`和处理单中的文章ID必须一致；存在的`当前版本`或`文章版本`字段也必须一致。`30`的资料版本和`35`的索引版本可以保留组件标识，但不得代替文章版本。

下列任一情况发生时，先把当前任务目录的完整可见状态归档，再从受影响步骤建立下一文章版本：

- 标题、大纲、关键词、目标语言、公开限制或其他文章要求发生实质变化；
- 来源、Claim、翻译、参数、单位、使用边界或排除结论变化，导致`20/30/35`需要重建；
- 已交付的`30/35`需要修改；
- `40_最终文章.md`正文发生任何修改；
- 已完成文章因资料变化、客户更正或审核问题重新打开。

文章历史固定保存到：

```text
04_文章任务/90_归档/10_文章历史版本/[文章ID]/[旧文章版本]_[YYYYMMDD-HHMMSS]/
```

归档的是修改前任务目录快照，不只保存单个`30`。这样旧大纲、审核、`30/35`、终稿和`50`记录仍能互相对应。归档完成后当前任务目录仍使用原文章ID，版本递增，并只重跑受影响步骤。旧Faithfulness结果立即失效；新结果导入后，CSV中的旧导入事件保留并标为`superseded`。

取消且不再继续的整篇任务放入`04_文章任务/90_归档/20_已取消任务/[文章ID]/`，写明取消原因和日期；不能把被替换的历史版本与取消任务混在一起。

## 3. 正式知识版本

正式知识文件在`03_正式知识/`中保持稳定路径和稳定主题名。新增Claim不一定需要归档；但删除或改写既有Claim、变更Claim状态/范围/来源/证据/边界、合并拆分主题或执行批量结构迁移前，必须归档旧文件。

历史固定保存到：

```text
05_数据与审核/60_版本归档/10_正式知识历史/[稳定对象ID]/[旧版本]_[YYYYMMDD-HHMMSS]/
```

更新当前文件时保留Claim ID；不能通过删除旧Claim来抹掉历史。已失效事实优先在当前文件中标记`已失效`并说明替代Claim；只有结构迁移确需移出时才只在历史包保留。受影响文章只回退受影响步骤，不批量改写无关文章或已完成文章正文。

## 4. 客户源资料版本

客户原文件在Vault外保持只读，本Skill不移动、覆盖或替客户保存版本。每个物理路径独立登记；SHA-256相同才可判定完全重复。疑似新旧版本只建立候选关系，未经人工确认不得决定主版本。

同一路径SHA-256变化时，来源刷新必须先把旧SHA-256、旧修改时间、旧大小、当前路径、新SHA-256和发现时间追加到：

```text
05_数据与审核/60_版本归档/40_源资料版本记录/source_version_history.jsonl
```

这份记录证明“检测到文件变化”，不等于保存了旧文件正文。若客户需要可恢复的源文件历史，必须由客户原资料存储或其版本管理系统保存；知识库不能声称可恢复一份从未留存的旧原件。变化后只复核受影响Claim、文章包和审核。

## 5. 控制文件和机器数据

项目基础信息、当前待办、四类治理台账、目录页和月度/交接文件只保留一个当前文件。普通事项新增、状态变化或关闭直接更新当前表并写运行记录，不建立逐次快照。发生模板迁移、字段删除、批量合并、目录重构或可能丢失人工内容的批量重写时，修改前归档到：

```text
05_数据与审核/60_版本归档/20_控制文件迁移历史/[对象ID]/[旧版本]_[YYYYMMDD-HHMMSS]/
```

机器文件按类型处理：

- `项目运行账本.jsonl`、`token_usage.jsonl`和`source_version_history.jsonl`只追加，不覆盖，不为每次追加复制文件；
- Faithfulness CSV保留每次导入行；新结果只把旧行标为`superseded`，不删除历史行；
- `source-index.sqlite`是可重建当前索引，普通刷新不保存数据库快照；脚本采用临时文件校验后原子替换；
- `source-index-exclusions.json`是高影响控制文件，条目新增、删除、指纹更新或批量改写前必须归档旧版；
- SQLite schema、CSV schema或其他机器数据结构迁移前，归档旧机器文件和数据说明到`05_数据与审核/60_版本归档/30_机器文件迁移快照/`。

## 6. 项目级记录和恢复

文章完成/重开、文章版本替换、正式知识结构迁移、控制文件迁移、机器schema迁移、Skill版本迁移、负责人或稳定路径变化必须追加到`01_工作台/30_版本与变更入口.md`，并在项目运行账本记录归档包、修改输入、输出和结果。普通单条治理事项进展不写成第二套版本流水。

恢复历史版本时执行：读取归档说明与哈希 → 归档当前版 → 把历史内容复制为新的当前版本 → 更新版本号和当前链接 → 使旧Faithfulness失效 → 运行项目校验。历史目录本身始终不修改。
