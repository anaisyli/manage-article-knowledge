# 内容运营操作手册

本手册说明内容运营如何使用 `manage-article-knowledge v0.5`。它不是资料整理教程，也不是写作教程。内容运营负责提供项目事实、文章要求、公开边界和最终文章；Skill负责登记、检索、核验、沉淀、交付知识附件和维护治理记录。

## 一、Skill能做什么

### 能做

- 把客户原始资料建立为可搜索的来源层，不改客户原文件；
- 根据具体文章标题、大纲和问题检索正式知识、客户资料、官网和已登记企业相关网站；
- 只对文章实际需要的内容建立最小Formal Claim，并保留原文证据；
- 在文章写作前检查标题、主问题和大纲是否有知识覆盖；
- 对公共知识缺口开展定向外部调研，并把可复用结果沉淀为外部公共知识；
- 生成唯一写作事实附件 `30_本篇知识库资料.md` 和内部追溯索引 `35_写作素材来源索引.md`；
- 接收另一个Faithfulness Skill的审核结果，记录文章事实支撑和后续治理事项；
- 维护知识缺口、CUS、MAT、ANM、SKFB、月度审核和项目交接记录。

### 不做

- 不替内容运营写文章，不替内容运营决定标题、文风、SEO/GEO或发布；
- 不把外部资料当作客户产品参数、产能、认证、案例、价格、MOQ或承诺的证据；
- 不把最终文章当作事实来源；
- 不在初始化时制作全部资料的清稿、翻译、摘要或正式知识；
- 不要求内容运营审批普通候选文件、页码范围、Claim、调研链接或每一步“继续”；文章阻塞事项先通过处理单交内容运营，视觉核验类先由Codex调用MinerU并对照原始PDF/PPT，内容运营明确无法处理后转AI知识库专员。
- 不要求内容运营配置Token、运行MinerU命令、处理OCR、压缩包、Office嵌入对象或音视频。

## 二、你只需要记住的三个入口

| 你要做什么 | 你提供/查看什么 |
|---|---|
| 新建项目 | 首轮五项信息，随后明确回复 `确认建库` |
| 准备一篇文章 | 文章ID、标题、关键词、大纲、目标语言、限制，以及允许提供的资料 |
| 交给写作或审核 | 写作只用 `30_本篇知识库资料.md`；审核结果回到该文章的 `50_文章知识使用与Faithfulness记录.md` |

项目中的当前待办只有一个入口：`01_工作台/20_当前待办.md`。四类异常台账是治理记录，不是让内容运营维护的第二套任务列表。

每次开始处理既有项目时，Codex会先做一次Skill版本检查：比较版本入口中的Skill SHA-256与当前Skill。发现Skill更新时，会同步项目版本入口，并在SKFB台账写入最近版本检测和开放反馈审计摘要；这一步不会自动关闭反馈，也不要求内容运营处理技术验证。

### 当前知识库结构和每部分职责

| 区域 | 主要负责什么 | 内容运营通常看什么 |
|---|---|---|
| `01_工作台` | 保存项目基础信息、唯一当前待办和版本/变更入口 | 先看`20_当前待办.md`；项目名称、官网、负责人等看`10_项目基础信息.md` |
| `02_源资料` | 登记客户原文件、搜索索引、排除规则、MinerU按需提取和外部调研原文证据 | 判断某份资料是否已登记、能否搜索、是否待处理；这里不是正式知识 |
| `03_正式知识` | 保存已经核验、可复用并带来源证据和使用边界的Formal Claim | 分为客户知识和外部公共知识；客户知识不能由外部资料代替证明 |
| `04_文章任务` | 保存每篇文章从知识准备到终稿、Faithfulness和历史版本的完整过程 | 按`10_进行中 → 20_等待终稿 → 30_等待Faithfulness → 40_已完成`查看状态；旧版本在`90_归档` |
| `05_数据与审核` | 保存Faithfulness、知识覆盖与缺口、异常治理、月度交接、运行记录和版本归档 | 用于复核、追踪问题和交接，不作为写作附件 |

`05_数据与审核`中最常用的入口：

| 子区 | 主要负责什么 |
|---|---|
| `10_Faithfulness` | 每篇文章的审核明细、Claim支撑关系和汇总 |
| `20_知识库覆盖与缺口` | 当前知识覆盖视图和唯一公共知识缺口明细 |
| `30_异常与待决定` | CUS客户补充、MAT资料处理、ANM源文/事实异常和SKFB Skill运行反馈 |
| `40_月度与交接` | 月度变化、未关闭事项和负责人交接 |
| `50_运行记录` | Skill执行、调研、沉淀和状态变化必须进入项目运行账本；token用量默认不记录 |
| `60_版本归档` | 正式知识、控制文件、机器文件和源资料版本的历史记录 |

内容运营不需要逐目录维护。当前工作统一看工作台；写作只取本篇`30_本篇知识库资料.md`；需要追溯、审核或处理异常时，再进入对应区域。

## 三、新项目：只做首轮五项填写

首次创建知识库时，只发送：

```text
项目名称：
官网：
客户原始资料路径：
Obsidian项目路径：
内容运营负责人：
```

Skill只回显这五项并暂停。只有明确回复 `确认建库` 后才会扫描资料、访问官网、运行初始化或索引脚本、读取旧库和修改项目文件。确认前不要补填完整项目模板，也不要要求Skill先展示初始化结果。

确认后Skill会自动建立项目目录、来源台账、SQLite搜索索引、项目基础信息、正式知识目录、异常台账、覆盖与缺口视图和运行记录。官网已知时会做一次轻量官网画像；官网不能证明的运营组、公开限制、AI知识库专员等字段不会猜测。

如果有子品牌站、集团站、区域站、平台店铺或企业主页，只需提供网站名称、URL和已知企业关系。Skill会登记并检查它们；关系不明时不会把它们当作客户专属来源。Codex自行找到的公共网站不会放进这张企业相关网站表。

## 四、准备一篇文章：一次提交，后台连续完成

提交以下信息即可，缺少可选项不必为了补齐而停住：

```text
文章ID：
标题：
关键词：
大纲：
目标语言：
特殊限制：
本篇是否禁止新的外部调研：允许 / 禁止
本篇是否禁止使用全部外部来源：允许 / 禁止
```

也可以同时提供随文文件。请说明它是：

- 项目长期事实资料；
- 仅本篇事实资料；
- 写作要求或非事实参考；
- 明确禁止提取正文。

没有明确限制的事实资料默认作为项目级通用资料，不会因为随某篇文章提交就自动限制为仅本篇。写作要求、风格、SEO/GEO和结构参考不会进入事实索引、Formal Claim、`30`或Faithfulness证据上下文。

收到一次完整文章需求后，Skill会自动连续完成：

`10_文章知识需求.md` → `15_检索与知识准备记录.md` → 必要Claim核验与沉淀 → `20_文章前知识审核.md` → `30_本篇知识库资料.md` → `35_写作素材来源索引.md`

正常情况下不需要回复“继续”。只有真实人工决定、外部工具失败或缺少不可替代材料时才会暂停，并生成 `文章前问题与处理单.md`，写清问题、影响、责任人、证据、处理选择和自动恢复条件。

发现文章命中疑似重复、跨格式或新旧版本候选时，Skill不会随机选文件。SHA-256相同的副本直接复用代表；视觉核验先由Codex调用MinerU并对照原始PDF/PPT。仍不能唯一判断，或SHA-256不同且影响当前事实时，才建立一个MAT，在文章处理单中列出候选并暂停Claim提取，先交内容运营；内容运营无法处理时转AI知识库专员。若候选组外已有明确安全来源，记录未采用原因后继续。

命中开放MAT时，`15_检索与知识准备记录.md`固定写`MAT依赖处理：待决定`并列出候选、关系信号、决定方和范围；决定前不整理任何候选文件。视觉核验由Codex完成后可自动改为`已决定`，其余事项由内容运营先处理，无法处理时转AI知识库专员。决定后Codex一次性提取、回源核验并生成Claim、30和35；人工无需重复说明或修改来源文件。

## 五、支持的资料格式与处理方式

初始化的目标是先登记资料身份、版本和可搜索内容，不是把每个文件全部清理、翻译或解析完成。只有当前文章实际命中某份资料时，Skill才处理完成该知识问题所需的最小范围。

| 资料格式 | 初始化或刷新时 | 当前文章命中后 |
|---|---|---|
| TXT、Markdown、CSV、JSON、HTML、XML | 本地确定性读取并建立索引，尽量保留标题、行、表格和位置 | 回到原文件核验命中范围，再提取最小Formal Claim |
| DOCX、PPTX、XLSX | 先做本地文字索引，并登记图片、图表、关系和嵌入对象数量 | 普通文字和表格本地处理；复杂版式、图表、公式或嵌入对象影响本篇时，先做只读容器检查，仍不可靠则进入MAT或按条件调用MinerU |
| 可搜索文字PDF | 本地提取正文并保留页码 | 回到对应页面核验文字、表格、单位和脚注后建立Claim |
| 扫描PDF、图片 | OCR只作为搜索线索，不能直接作为事实证据 | 必须对照原页核验；复杂表格、公式、图示或版面关系无法可靠读取时按需调用MinerU |
| ZIP | 登记压缩包身份、大小、指纹和成员名称，不默认递归解压 | 本篇确实依赖时，只在安全临时目录检查必要成员，不批量展开全部历史资料 |
| RAR、7z及其他压缩包 | 默认只登记；加密、损坏或当前环境不支持时标记处理状态 | 本篇依赖时进入MAT并形成文章阻塞；先交内容运营，无法处理时转AI知识库专员 |
| 音频、视频 | 只登记文件身份和基础元数据，不自动转写或总结 | 本篇依赖时进入MAT并形成文章阻塞；先交内容运营，无法处理时转AI知识库专员；可以接收已有转写稿，但仍要核对文件对应关系和准确性 |
| 网页 | 官网和已登记企业相关网站优先语义读取；保存页面身份、URL、日期和可访问状态 | 普通页面直接核验；折叠、标签、动态内容或视觉状态必要时使用浏览器；登录态关键页面只有在明确需要时才请求Web Clipper |
| 加密、损坏、缺页、版本不明或不支持的文件 | 登记真实状态，不猜测正文 | 当前文章依赖时进入MAT并形成文章阻塞；先交内容运营，无法处理时转AI知识库专员；处理后若发现数字、版本、OCR、冲突或危险外推问题，再关联ANM |

格式本身不决定是否调用MinerU。能用本地方法可靠取得的PDF或Office内容不调用；扫描、复杂版面或结构关系只有在当前文章确实需要时才按最小范围处理。内容运营不需要自己转换格式、运行OCR、解压复杂压缩包或解释嵌入对象，只需提供原文件并说明用途和限制。

## 六、MinerU API：什么时候用，第一次怎么配置

### 触发条件

MinerU不是看到PDF或Office文件就调用。顺序固定为：

1. 先用本地确定性方法提取；
2. 只有当前文章确实需要某份资料，且本地方法无法可靠取得正文、表格、公式、图示或版面关系时，才按需调用MinerU；
3. 只提交完成当前技术解析所需的最小资料范围，不批量解析历史资料；
4. MinerU结果只是技术提取稿，Claim前必须回到原文件或可靠固定渲染核验。

典型触发情况包括扫描PDF文字无法可靠读取、复杂表格或公式无法保留、图表/版面共同表达含义，或Office内容结构无法通过本地方法定位。仅仅“文件是PDF”不构成触发条件。

### 第一次配置：API负责人照着做

这是一台实际运行Codex的电脑上的一次性配置。内容运营本人不是API负责人时，只需把本节交给API负责人或IT，不要在聊天中发送Token。

1. 在浏览器打开MinerU的Token页面：<https://mineru.net/apiManage/token>。
2. 使用团队账号登录，创建Token，并记下页面显示的到期日。
3. 只复制单独一行Token值。不要复制`Bearer`、引号、说明文字或空行。
4. 在文件资源管理器打开：`D:\manage-article-knowledge\manage-article-knowledge-v0.5\scripts`。
5. 双击`initialize_mineru.cmd`，等待黑色窗口提示复制Token。
6. 确认Token仍在剪贴板后，回到黑色窗口按Enter。不要把Token粘贴进窗口；初始化器会从剪贴板读取，只显示字符数，并随后清空剪贴板。
7. 按提示输入到期日，格式必须为`YYYY-MM-DD`，例如`2026-12-31`。
8. 等待初始化器自动执行本地`probe`和在线`health-check`，不要另开命令行运行检测。
9. 看到`Setup completed`表示配置和在线验证完成；看到`Local setup completed. MinerU online verification is temporarily pending.`表示Token已在本机保存，只是当前网络或服务验证暂未完成。后一种情况不要重复输入或更换Token。
10. 完全退出Codex Desktop后重新打开。只关闭当前对话或窗口标签不够。
11. 第一次真实调用若出现网络或沙箱权限提示，API负责人或IT确认调用方是本Skill的`run_mineru.py`后，按团队安全规则允许该次访问。

Token和鉴权信息不得写入客户项目、Skill、对话、截图或运行账本。初始化器保存的是当前Windows用户环境配置，因此每台实际运行的电脑都要单独配置一次。

### 日常使用和换Token

- 内容运营日常只提交原文件和文章需求，不运行命令、不手工上传客户文件，也不需要判断是否调用MinerU；
- Codex在当前文章确实需要且本地提取不可靠时自动检查`probe`，必要时执行按需解析；每月没有成功记录或鉴权可疑时再做`health-check`；
- 解析输出统一进入`02_源资料/20_MinerU按需提取`，并关联原始资料ID、版本和处理范围；它仍是技术提取稿，形成Claim前必须回到原文件或可靠固定渲染核验；
- Token距到期7天和1天提醒API负责人；到期后停止调用，不绕过授权；
- 更换Token时先在MinerU页面创建新Token，在每台实际运行电脑上重新双击`initialize_mineru.cmd`完成配置，重启Codex并验证成功，最后再撤销旧Token。

### 出错时看哪一类

| 现象 | 谁处理 | 怎么办 |
|---|---|---|
| Token缺失、过期或鉴权失败 | API负责人 | 检查团队Token及到期日；需要时按首次配置步骤重新初始化 |
| 429或额度不足 | API负责人 | 检查团队额度和并发，不要求内容运营换文件格式规避 |
| 临时超时或服务不可用 | Codex | 最多重试2次；保留最近成功状态，不重复要求输入Token |
| `WinError 10013`、socket或沙箱权限错误 | Codex / IT | 按最小权限处理本机网络访问；这不等于Token错误或MinerU永久故障 |
| 上传403、处理或下载失败 | Codex / API负责人 | 按失败阶段检查临时上传、任务状态和下载，不让内容运营手工上传到其他服务 |
| 只有某个文件失败 | Codex先检查；文章受阻时交内容运营 | 检查格式、大小、页数、加密、损坏和版本；内容运营无法处理时转AI知识库专员 |
| 提取结果结构错误 | Codex先对照原文件 | 仍不能可靠处理且阻塞文章时先交内容运营；内容运营无法处理时转AI知识库专员 |

项目禁止使用MinerU或团队尚未批准该服务时，停止调用并转入MAT，不绕过授权。详细技术规则见[来源索引与复杂资料](source-index-and-materials.md)。

## 七、知识缺口、外部调研和人工问题

文章前审核会逐项检查标题、主问题及一级/二级主要大纲：`已覆盖 / 部分覆盖 / 未覆盖 / 无需事实支持`。

- 公共技术、行业、方法或法规知识缺失：进入唯一知识缺口CSV；核心章节或高风险事实首次进入 `待外部调研`，普通缺口首次 `观察中`，第二篇不同文章出现时升级；
- 客户专属事实缺失或需确认：进入CUS；
- 本地资料存在但尚未可靠处理：进入MAT；
- 来源冲突、数字/单位/OCR、版本或危险外推问题：进入ANM；
- 已有知识但没有放进本篇 `30`：记为资料包覆盖遗漏，修正后续任务准备，不重复调研；
- 纯结构、过渡、CTA、修辞或不可复用观点：才可归为 `writing_only`。

外部调研按具体 `gap_key` 定向开展，不需要内容运营逐链接审批。来源优先级、原文证据、失败路径、冲突和正式沉淀见 [外部调研执行与沉淀合同](external-research-contract.md)。登录、付费墙、反爬或正文取不到时，只记录失败和替代材料，不把搜索摘要当证据。

这里所说的“现有知识五个入口”是Skill后台依次检查的五处，不是内容运营要执行五次操作：

1. 已经沉淀的正式Claim；
2. 客户提供文件的本地搜索索引；
3. 客户主官网；
4. 内容运营提交且企业关系已确认的其他网站；
5. 以前已经沉淀的外部公共知识Claim。

这五处仍不能回答，才可能形成知识缺口。第六个入口才是本次新做外部调研，而且必须先登记缺口并达到`待外部调研`门槛。

外部调研有两轮发现入口，但不会在写作过程中临时插入一套不可追溯的研究：

1. **写作前发现**：检查完上述五个已有知识入口后，按标题、主问题和一级/二级主要大纲识别公共知识缺口，先登记`gap_key`和当前文章。达到调研触发条件且本篇允许新调研时，在同一文章知识准备事务中建立`RES-ID`、保存证据、形成可用Claim，再完成`20`和`30`；未达到条件或禁止调研的缺口保持`观察中`或`待外部调研`并在本篇缩小、删除或中性处理。
2. **写作后发现**：终稿的Faithfulness结果可能暴露写作者新增的事实。导入时把事实性或可复用的unsupported归到文章前已有缺口，或补建新的公共缺口、CUS、MAT、ANM或资料包覆盖遗漏。新增`待外部调研`项在导入后作为独立知识维护处理，`观察中`只累计不同文章次数；调研结果更新正式知识、缺口和`50`中的治理状态，但不改变原Faithfulness结果，也不会自动改写或重新审核已完成文章。

写作Agent自行联网取得的内容不自动等于本Skill的外部调研证据。只有已经登记问题、保存`RES-ID`原文证据与核验记录、形成Formal Claim并进入`30`的内容，才是本篇正式交付的知识支持。

## 八、写作交付：只交一个知识附件

当任务进入 `20_等待终稿` 后，内容运营或写作模型只使用：

`30_本篇知识库资料.md`

它包含可直接采用的事实、英文表达、数据表、大纲使用建议、生成控制和缺少资料时的安全处理方式。`35_写作素材来源索引.md`只供知识库内部追溯和Faithfulness映射，不交给写作者。写作者可以自由组织结构、过渡和一般解释，但不得新增客户专属参数、型号结论、认证、案例、能力、效果承诺或商业承诺。

缺少资料时，文章可以省略、缩小范围或中性改写，不要把 `not supported`、`no evidence`、`cannot determine` 等审核语言写进正文。Faithfulness不是文章质量或SEO/GEO评分，也不要求每句话都有逐句证据。

### 交给其他Agent或AI时使用的固定Prompt

内容运营在其他Agent或AI中创建写作任务时，只附加本篇的`30_本篇知识库资料.md`，然后把下面这段Prompt与实际项目级、文章级要求一起发送。不要把`35`、完整知识库、客户原始资料或外部调研记录一并附上。

```text
请按照内容运营提供的文章要求完成写作，并把附件《30_本篇知识库资料.md》作为知识库资料使用。

1. 文章目标、结构、文风、关键词、SEO/GEO和交付格式，以内容运营的文章要求为主；知识库资料不替代这些要求，也不要求逐条照抄或把每条素材全部写入。
2. 知识库资料第一至第三部分是本篇经核验的事实、数据和目标语言表达。涉及客户、产品或型号、参数、认证、案例、能力、效果或商业承诺时，只能使用附件中明确提供的内容；不得补造、扩大范围，或把通用行业信息写成客户事实。
3. 第四至第六部分用于选材、组织和生成控制，是参考信息，不是必须写入正文的内容。不要在文章中复述Claim编号、来源定位、审核过程、资料缺口或使用边界。
4. 当知识库没有覆盖某个具体事实时，直接省略该事实、缩小表述范围或改为不依赖该事实的写法。不要反复写“not supported”“no evidence”“cannot determine”“does not provide”“requires separate verification”等审核语言，也不要把资料不足本身写成文章主题。
5. 不要求文章每一句话都能在知识库中找到逐句证据。可以根据文章要求和模型已有常识，自由完成标题组织、段落结构、过渡、总结、行业常识、一般原理和非客户专属解释，使文章自然、完整、可读；这些补充不得伪装成客户事实，也不得产生新的精确参数、型号结论、认证、案例、客户能力、效果或商业承诺。对高风险或可能因产品、地区、标准、时间而变化的通用事实，优先采用知识库已有内容或经知识库流程更新后的当前《30_本篇知识库资料.md》。
6. 本篇标准事实附件只有《30_本篇知识库资料.md》。中途或随文章提供的新事实文件，必须先由知识库流程登记、核验并更新本篇知识库资料，不能直接作为平行客户事实附件交给写作模型。写作提示、风格要求和生成控制本身不作为事实证据。
```

这段Prompt不绑定某个写作Skill。发送时在它前面或同一条消息中附上项目级和文章级写作要求，并只附当前`30`。换用其他Agent、模型或写作平台时，仍保持“实际文章要求 + 固定知识库使用规则 + 唯一事实附件`30`”这三个部分。

## 九、与Faithfulness Skill联动

### 1. 内容运营先交终稿

写作完成后提供当前版本的 `40_最终文章.md`。Skill会立即创建 `50_文章知识使用与Faithfulness记录.md`，锁定终稿和 `30` 的SHA-256，并把任务转到 `30_等待Faithfulness`。

### 2. Faithfulness Skill的输入

Faithfulness Skill只接收：

- 当前 `40_最终文章.md`；
- 当前 `30_本篇知识库资料.md`。

不要把 `35`、完整正式知识库、原始资料、写作要求或外部调研记录加入Faithfulness的retrieval context，否则会改变实际写作上下文。Faithfulness判断的是“终稿事实被实际交付附件支持的比例”，不是文章是否写得好。

审核结果放在本篇版本专属目录，例如：

```text
D:\article-faithfulness-audits\[项目短码]\[文章ID]\v[文章版本]\
  [文章ID]-prepared.json
  [文章ID]-judgments.json
  faithfulness_summary.md
```

内容运营可以提交这个专属目录，或在 `50` 中登记它的稳定路径。不要把一个宽泛审核根目录交给Skill让它猜版本；不要重复提交终稿。

### 3. 导入结果后发生什么

Skill会校验文章ID、版本、终稿哈希、`30`哈希、结果计数和证据格式；不匹配就拒绝导入，不猜测、不静默修复。导入成功后会：

- 更新本篇 `50`；
- 写入文章Faithfulness明细和Claim文章支撑记录；
- 更新覆盖与缺口视图；
- 把unsupported按稳定问题归组；
- 必要时进入公共缺口、CUS、MAT或ANM；
- 成功后把任务转到 `40_已完成`。

每个unsupported必须且只能归组一次。`50`会分开显示分类、分类依据、关联事项/入口、当前处理和下一步。它不会把所有unsupported默认写成“无需处理”。

终稿任何实质修改都必须先归档旧版本、递增文章版本并重新执行Faithfulness。旧结果不能继续代表新文章。

## 十、收到人工问题时怎么做

只有以下情况通常需要内容运营决定：

- 是否公开敏感或客户专属信息；
- 缺失的客户事实是否必须保留在文章中；
- 冲突来源如何取舍；
- 核心大纲是否允许删减、缩小或改成中性表达；
- 是否允许本篇开展新的外部调研或使用外部来源。

Skill会在文章目录生成 `文章前问题与处理单.md`，并同步当前待办。内容运营只需在处理单中提供决定或材料；Codex会自动复核并继续，不需要再次说“继续”。

### Skill反馈台账：Codex可以主动记录，也可以由人工提醒

固定入口：`05_数据与审核/30_异常与待决定/40_Skill运行反馈/01_Skill反馈台账.md`。

以下情况显示为可能的通用Skill问题时，Codex应主动记录候选反馈，不必等内容运营提出：

- 用户纠正了Skill本应稳定执行的规则；
- 同一步骤反复绕路、漏做或需要多次提醒；
- Skill文件之间规则冲突，或实际输出与模板不一致；
- 模板难以理解、无法使用，或校验器没有发现明显错误；
- 自动流程产生了错误状态、错误路径、重复事项或遗漏联动。

内容运营也可以直接说：`把这个记录到Skill反馈台账`、`这是一个bug，请登记SKFB`，或说明希望反馈的问题。无需填写SKFB ID、类型、状态、复现步骤或技术原因；Codex负责检查现有反馈、合并同一根因、保存人话说明、复现依据、影响范围、项目对象入口、当前阶段和下一步。同一问题再次出现时追加到原SKFB，不重复建项。

记录反馈不等于立即修改Skill。Codex先判断它是通用Skill候选还是项目问题；只有用户或维护负责人明确同意修改Skill后，才更新Skill和版本记录。Skill自测通过后状态为`已修复，待项目验证`，原复现项目也验证通过后才能`已关闭`。

以下问题不要混进SKFB：缺少客户事实进入CUS；资料尚未可靠处理进入MAT；来源、数字、版本或事实冲突进入ANM；一次性的文章业务决定留在文章处理单或项目记录。分类不确定时，Codex先记录事实和影响，再完成归类，不把判断工作交给内容运营。

## 十一、月度审核与交接

内容运营不维护月报机器数据。Skill会自动汇总：

- 本月新增、升级、解决或关闭的公共知识缺口；
- 全部未关闭缺口和下一步；
- CUS、MAT、ANM、SKFB；
- 每篇文章的Faithfulness分布；
- MinerU/API状态、失败记录和待处理事项。

月度审核看本月变化；项目交接看所有未关闭事项、当前入口、责任人和恢复条件。两者都不把外部公共知识混入客户企业来源，也不把Faithfulness当作文章发布合格线。

## 十二、最短操作口诀

```text
新项目：填五项 → 确认建库
新文章：给标题/大纲/限制 → 等30
需要写作：只交30 + 固定Prompt + 项目/文章要求
写完文章：交40 → 等Faithfulness
审核完成：交专属结果目录 → Skill导入并归组
文章修改：归档旧版本 → 升版本 → 重新审核
```

内容运营只需提供真实信息和业务决定；扫描、检索、Claim、MinerU、外部调研、导入、台账和报告由Skill按规则处理。
